zkSecurity가 자체 AI 감사기 **zkao**를 OpenVM의 zkVM에 겨눠서, 게스트 라이브러리 `openvm-pairing`에서 **악의적 프루버가 임의의 페어링 등식을 위조할 수 있는 크리티컬 건전성(soundness) 버그**를 찾아냈다. CVE-2026-46669로 배정됐고 OpenVM 1.6.0에서 수정됐으며, 알려진 한 OpenVM 위에 빌드하던 파트너들은 모두 이 버전으로 업그레이드했다. 이건 "AI meets Cryptography" 시리즈의 두 번째 글로, 앞선 Cloudflare CIRCL 편에 이어진다.

한 가지 선을 명확히 해두자. 이건 **zkVM 증명 시스템 자체의 건전성 버그가 아니다.** 취약한 라이브러리를 쓰는 코드에만 영향을 준다. 또 AI가 낸 건 "후보 발견"이지 최종 리포트가 아니다. 사람 팀이 이슈를 검증하고 익스플로잇 가능성을 확인하고 영향 범위와 대상 프로젝트를 파악한 뒤 디스클로저를 처리했다. 이번엔 zkao가 상세 리포트와 최소 PoC까지 스스로 만들어줘서 아주 빠른 수동 트리아지만으로 "OpenVM 팀에 공유할 가치가 있다"는 판단이 섰다.

## TL;DR
- `openvm-pairing`의 페어링 체크가 스케일링 팩터를 부분체 $\mathbb{F}_{p^6}$로 제약하지 않아서, 프루버가 $c=1,\ u=f^{-1}$로 놓으면 거짓 페어링 곱도 통과시킬 수 있었다. 세 줄짜리 부분체 검사가 빠진 게 원인.
- 영향은 크립토 바닥을 통째로 흔든다 — BN254에선 Groth16·BLS 서명, BLS12-381에선 KZG 오프닝, 그리고 이더리움 `ecPairing`(0x08)을 흉내 내는 모든 OpenVM 게스트가 위조 결과를 낸다. L2 롤업·브리지·프라이버시 프로토콜이 전부 이 위험을 상속.
- 순진한 LLM 스캔은 두 세대(Opus 4.6/4.7, Codex 5.3/5.4)에 걸쳐 전부 Informative로 강등됐지만, 컨텍스트 엔지니어링을 넣은 zkao가 9시간 반 스캔 끝에 이 크리티컬을 찾았다 — zkVM은 라이브러리처럼 독립 원시함수로 분해되지 않는다는 가설의 실증.

## 무슨 일이 있었나

zkSecurity의 원래 실험 규칙은 "순진한 LLM이 진짜 버그를 먼저 찾은 뒤에만 zkao를 돌린다"였다. 그런데 OpenVM은 이 규칙이 깨진 케이스다. 4개월 전 그들은 다른 모든 대상과 똑같이 OpenVM을 스캔했다 — 심플한 프롬프트를 붙인 LLM, 그리고 자사 전문가 스킬을 붙인 LLM. Opus 4.6과 Codex 5.3으로 돌렸고, Opus 4.7과 Codex 5.4가 나오자마자 다시 돌렸다. 후보 발견들은 전부 "유효한 관찰"이긴 했고 모델은 자신만만하게 Critical/High 라벨을 붙였지만, **실제로 익스플로잇 가능한 건 하나도 없었다.**

그들의 가설은 이랬다. zkVM은 순진한 LLM 셋업이 300K, 심지어 1M 토큰 컨텍스트로도 감당하기엔 너무 복잡하다는 것. 모듈 간 의존성이 일반 라이브러리보다 훨씬 촘촘하다. 암호 라이브러리는 폴더 하나=암호 원시함수 하나로 매핑해서, 각 서브에이전트에 폴더를 던져주면 병렬로 감사할 수 있다. 서브에이전트가 몇 줄 읽고 관련 스킬만 적용해 마크다운에 findings를 쓰면 메인 에이전트가 그걸 꿰맨다 — Claude Code나 Codex 같은 도구에서 사람 개입 거의 없이 out-of-box로 돌아간다.

zkVM에선 이게 통하지 않는다. "낮게 달린 과일"을 빼면 서브에이전트의 쓸모 있는 출력은 버그 목록이 아니다. 증명 가능하게 안전한 모듈 A와 안전한 모듈 B의 **합성이 안전하지 않을 수 있기** 때문에, 격리 모드로 버그를 사냥하면 의미 있는 버그를 못 잡는다. 대신 서브에이전트의 출력은 "그 모듈에 대한 지식"이어야 한다 — 무엇을 가정하는지, 무엇을 호출자에게 위임하는지, 어떤 불변식(invariant)에 조용히 기대고 있는지. 문제는 이 지식을 잘 표현하는 게 어렵다는 것. 너무 짧으면 버그가 앉아 있는 구현 디테일을 건너뛰고, 너무 길면 다른 것과 합치기도 전에 메인 에이전트 컨텍스트가 넘친다. 저자들 말로는, 적어도 현재 시점의 에이전틱 코딩 도구들은 이 문제를 효율적으로 풀지 못한다.

그래서 이 상황이야말로 zkao를 돌릴 자리라고 판단했고 — 자기네 전문가의 감사 방식을 재사용 가능한 flow로 인코딩해둔 도구다 — 9시간 반 스캔 끝에 많은 findings가 나왔다. 시간이 없어 전부 깊게 보진 못했지만, 빠른 패스에서 하나가 즉시 튀었다. 게스트 라이브러리 중 하나의 페어링 체크에 있는 크리티컬 건전성 버그. 가설이 버텼고, 몇 달의 노력이 값을 했다.

## 버그: 페어링 체크가 스케일링 팩터의 부분체 검사를 빠뜨렸다

### 배경 — 왜 페어링이 바닥인가

페어링은 Groth16, KZG를 쓰는 PLONK, BLS 서명의 엔진이다. 이 프로토콜들에서 검증자는 보통 페어링 값 하나를 묻지 않는다. **페어링들의 곱이 1인지**를 묻는다:

$$\prod_i e(P_i, Q_i) = 1.$$

이 하나의 예/아니오 답에서 검증자는 SNARK 증명이 유효하다, KZG 오프닝이 맞다, 서명이 검증된다를 결론 내린다. 그러니 프루버가 **거짓 페어링 곱을 1처럼 보이게** 만들 수 있으면, 그 위에 쌓인 모든 게 더 이상 건전하지 않다.

페어링 $e(P,Q)$ 계산은 두 단계다(Weil 페어링 제외). 첫째, **밀러 루프**가 밀러 함수 $f_{r,Q}(P)$를 평가해 $\mathbb{F}_{p^{12}}^{*}$의 원소를 낸다. 페어링 곱이면 회로가 밀러 루프들을 다 돌려 출력을 곱하는데, 이 합산 출력을 $f = \prod_i f_{r,Q_i}(P_i)$라 하자. 함정은 $f$가 아직 페어링 곱이 아니라는 것이다. 이건 몫군 $\mathbb{F}_{p^{12}}^{*} / (\mathbb{F}_{p^{12}}^{*})^r$의 대표원 하나일 뿐이다. Novakovic–Eagen 논문의 핵심 관찰 중 하나: **밀러 루프 출력은 $r$제곱을 곱하는 것까지만 유일하다.** 즉 $f_1 = f_2 \cdot c^r$인 0 아닌 $c$가 있으면 둘은 같은 페어링을 가리킨다. 이 미정 인자 $c$가 직접 등식 검사를 까다롭게 만든다.

그래서 둘째 단계인 **최종 지수화**가 존재한다. $f$를 $h = \frac{p^{12}-1}{r}$로 올리면 모호성이 사라진다. 0 아닌 모든 $c$에 대해 $(f\cdot c^r)^h = f^h \cdot c^{p^{12}-1} = f^h$이기 때문이다(마지막 항은 $x^{p^{12}-1}=1$이라 사라진다). 이 지수화 후 결과는 $r$제곱근들의 군 $G_T$에 안착한다. 따라서 진짜 페어링 곱 검사는 $f^h = 1$이다.

문제는 $h$가 회로 안에서 올리기엔 너무 비싸다는 것이다. 그래서 프루버가 회로 **밖에서** $c$를 계산해 힌트로 넘기게 하고, 회로는 $f = c^r$만 싼값으로 검사한다($f^h$를 직접 계산하는 것보다 훨씬 싸다). $f^h=1$은 $f=c^r$인 0 아닌 $c$가 존재하는 것과 정확히 동치이므로 이게 최적화의 핵심 아이디어다.

OpenVM은 이걸 Novakovic–Eagen의 **residue-witness 트릭**으로 구현한다. 실제 최적화된 등식은 $f=c^r$과 약간 다르다:

$$ f \cdot u = c^{\lambda} \ \wedge\ u^{d^i} = 1.$$

여기서 $\lambda = m\cdot r$는 커브별 지수로, 그 구조 덕에 회로가 프로베니우스 사상을 통해 $c^\lambda$를 싸게 평가할 수 있다. $u$는 **스케일링 팩터**다(OpenVM 코드에선 BN254에서 `u`, BLS12-381에서 `s`). $d = \gcd(m,h)$, $i = v_d(h)$. 스케일링 팩터가 필요한 건 $\lambda$가 원래 $r$-residue 검사와 딱 맞아떨어지지 않기 때문이고, 논문 Theorem 3이 스케일링 팩터에 작은 단위근 관계 $u^{d^i}=1$을 요구해 이 틈을 메운다. 이 커브들에선 더 싼 길이 있다 — $u^{d^i}=1$을 직접 검사하는 대신 스케일링 팩터를 **진부분체** $\mathbb{F}_{p^6} \subset \mathbb{F}_{p^{12}}$로 제약하면 충분하다. OpenVM은 $\mathbb{F}_{p^{12}}$ 원소를 여섯 개의 $\mathbb{F}_{p^2}$ 계수 $[c_0,c_1,c_2,c_3,c_4,c_5]$로 저장하는데, $\mathbb{F}_{p^6}$ 부분체에 있다는 건 홀수 인덱스 계수가 0, 즉 $c_1=c_3=c_5=0$이라는 뜻이다. **보안이 걸린 부분체 검사 전체가 등식 세 개**다.

### 실제 버그

$f\cdot u = c^\lambda$ 관계는 $u$가 올바른 부분체로 제약될 때만 건전하다. 그런데 OpenVM은 힌트 $c$가 0이 아닌지만 검사하고 거기서 멈췄다. **스케일링 팩터가 $\mathbb{F}_{p^6}$에 있는지는 검사하지 않았다.** 수정 전 BLS12-381 경로:

```rust
// guest-libs/pairing/src/bls12_381/pairing.rs
let (c, s) = Self::pairing_check_hint(P, Q);
// ... s가 Fp6에 있는지 검사 없음 ...
let c_conj = c.conjugate();
if c_conj == Fp12::ZERO {  // c == 0만 거부
    return None;
}
```

BN254도 `if c == Fp12::ZERO { return None; }`로 패턴이 같았다. 회로는 0인 $c$는 거부했지만 **어떤 스케일링 팩터든 받아들였다.** 이 시점에서 최적화 등식은 더 이상 진짜 페어링 검사를 증명하지 못한다. 어떤 밀러 출력 $f$에 대해서든(거짓 페어링 등식에서 나온 것이라도) 프루버는 이렇게 놓으면 된다:

$$ c = 1, \qquad u = f^{-1}.$$

그러면 $c^\lambda = 1$이고 검사되는 관계는 $f\cdot f^{-1} = 1 = c^\lambda$가 되어 **통과한다.** 두 커브에 똑같은 치환이 먹힌다(BN254는 $u=f^{-1}$, BLS12-381은 $s=f^{-1}$). 보통 $f^{-1}$는 $\mathbb{F}_{p^6}$ 부분체가 아니라 완전한 $\mathbb{F}_{p^{12}}$ 원소인데 — 바로 이래서 부분체 검사가 있었다면 위조를 걸러냈을 것이다. 게다가 미묘한 제어 흐름 디테일도 있다. 최적화 루틴이 성공을 반환하는 바람에, 완전한 최종 지수화를 수행하는 느린 폴백 경로엔 도달조차 하지 않았다.

### 영향

임의의 페어링 검사를 위조한다는 건 많은 것이 서 있는 암호적 바닥을 깨는 것이다:

- **BLS12-381**: KZG 오프닝 증명을 위조할 수 있어 데이터 가용성, blob 검증, PLONK/KZG 검증자를 떠받치는 다항식 커밋먼트 스킴이 깨진다.
- **BN254**: 같은 위조가 Groth16 SNARK 검증자, BLS 서명 검사, 그리고 페어링 등식에 기대는 모든 브리지·프로토콜을 깬다.
- 이더리움 `ecPairing` 프리컴파일(주소 `0x08`)을 OpenVM 페어링 체크로 흉내 내는 zkVM 게스트는 위조 결과를 내며 **잘못된 EVM 실행**으로 이어진다. 따라서 OpenVM 게스트 프로그램 안에서 페어링을 검증하는 모든 L2 롤업·브리지·프라이버시 프로토콜이 이 문제를 상속한다.

zkao는 Critical로 평가했고 OpenVM 메인테이너들도 Critical로 확인했다. AI 심각도와 메인테이너 심각도가 이번엔 일치했다.

### 수정

수정은 빠진 부분체 멤버십 검사를 추가한 것이다. 스케일링 팩터의 홀수 인덱스 계수가 0임을 단언한다:

```rust
// 스케일링 팩터가 부분체 Fp6에 있어야만 정직한 힌트다
for i in [1, 3, 5] {
    if s.c[i] != Fp2::ZERO {
        return None;
    }
}
```

$f^{-1}$ 같은 스케일링 팩터는 보통 홀수 계수가 0이 아니므로 거부되고 위조가 사라진다. 수정은 커밋 `a720e2c`에 반영되어 OpenVM 1.6.0으로 출시됐다.

## 배운 것들

1. **순진한 LLM은 복잡한 코드베이스에서 벽에 부딪힌다.** 두 모델 세대에 걸쳐 plain LLM 패스가 낸 findings는 OpenVM에서 전부 Informative로 강등됐다. zkVM은 라이브러리처럼 독립 원시함수로 분해되지 않으므로, 에이전트가 위로 올려야 하는 단위가 "모듈에 대한 지식"인데 이걸 잘 표현하는 게 진짜 어렵다.
2. **zkao는 `cryptopsy`라는 flow로 이 버그를 찾았다.** 세부는 다음 글로 미뤘지만, 요지는 포괄적 분석과 "구현 ↔ 학술 문헌(알려진 공격·함정·암호분석 결과)" 사이의 왕복을 결합한다는 것 — 수동 감사 과정의 일부를 흉내 낸다.
3. **트리아지를 "LLM이 동작하는 PoC를 만들 수 있나?"로 대체하면 안 된다.** 자동 트리아지 초기 시도가 그거였다 — PoC가 돌면 버그가 진짜다. 실전에선 이 신호가 보기보다 훨씬 약했다. 모델은 리포트한 이슈가 진짜가 아닐 때도 통과하는 PoC를 아주 잘 만들었다. 말도 안 되는 주석, 숨은 가정, 패치된 헬퍼 함수, 비활성화된 검사, 목킹된 상태, 수상한 실행 플래그를 충분히 섞으면 거의 어떤 익스플로잇도 성공한 것처럼 보이게 만들 수 있다. 그런 PoC를 검증하는 게 원 리포트를 트리아지하는 것보다 더 오래 걸렸다.

## 왜 중요한가

개발자·창업자 입장에서 이 글의 값어치는 버그 하나가 아니라 **"AI 감사가 어디서 되고 어디서 안 되는가"의 실증적 경계선**이다. 세 가지가 겹친다.

첫째, 이건 프레임워크 버그가 아니라 **게스트 라이브러리 버그**다. zkVM 코어의 건전성은 멀쩡한데, 그 위의 페어링 유틸 세 줄이 빠져서 전체 신뢰 체인이 무너졌다. 롤업·브리지 팀에게 주는 교훈은 명확하다 — "검증된 zkVM 위에 올렸으니 안전하다"가 아니라, 내가 게스트에서 호출하는 크립토 프리미티브의 건전성까지 내려가서 봐야 한다. 특히 `ecPairing` 프리컴파일을 에뮬레이트하는 코드라면 OpenVM 1.6.0 이상인지 지금 확인할 값어치가 있다.

둘째, 최적화가 곧 공격면이다. residue-witness 트릭은 회로 비용을 줄이려고 "비싼 최종 지수화 → 싼 힌트 검증"으로 바꾼 것인데, 그 등가성이 성립하려면 힌트에 **부분체 제약**이라는 조건이 반드시 붙어야 한다. 그 조건 하나를 빠뜨리면 최적화 등식이 원래 검사와 더 이상 동치가 아니게 된다. 크립토 최적화를 도입할 때 "논문의 정리가 요구하는 부수 조건을 코드가 전부 강제하는가"가 감사의 핵심 질문이라는 걸 이 케이스가 교과서처럼 보여준다.

셋째, **AI 감사 도구를 어떻게 신뢰할지**에 대한 실무 신호다. 순진한 LLM은 자신만만하게 Critical을 붙이지만 익스플로잇 불가한 노이즈였고, "PoC가 돌면 진짜"라는 그럴듯한 자동 트리아지도 거짓 양성을 못 걸렀다. 진짜 값은 컨텍스트 엔지니어링(모듈 지식을 컨텍스트 넘침 없이 위로 나르는 하네스)과 문헌 대조 flow에서 나왔다. AI를 파이프라인에 넣더라도 "사람 검증 게이트"는 여전히 필수이며, 특히 요약·추론 층의 오류는 사람이 원문·PoC를 전수 대조해야 걸린다.

## 어떻게 써먹나

- **OpenVM 사용자**: 게스트에서 `openvm-pairing`(BN254 `u`/BLS12-381 `s` 스케일링 팩터)을 쓰거나 `ecPairing`(0x08)을 에뮬레이트한다면 **1.6.0 이상**으로 즉시 업그레이드했는지 확인. `a720e2c` 이전 버전이면 페어링 위조에 노출된다.
- **크립토 라이브러리 리뷰어**: residue-witness/final-exponentiation 최적화를 쓰는 페어링 체크를 볼 때, 힌트(0 검사)뿐 아니라 **스케일링 팩터의 부분체 멤버십**($c_1=c_3=c_5=0$)이 강제되는지, 그리고 최적화 경로가 성공 반환할 때 폴백 검증을 건너뛰지 않는지 확인하라. Theorem 3의 부수 조건이 코드에 다 있는지를 체크리스트로.
- **AI 감사를 도입하는 팀**: "동작하는 PoC = 진짜 버그"라는 트리아지 지름길을 믿지 마라 — 모델은 가짜 이슈에도 통과하는 PoC를 만든다. 복잡한 코드베이스에선 서브에이전트에 "버그 목록"이 아니라 "모듈이 무엇을 가정/위임/의존하는지"를 뽑게 하는 컨텍스트 설계가 관건이다.
