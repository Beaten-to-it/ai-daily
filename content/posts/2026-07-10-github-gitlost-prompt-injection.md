Noma Labs가 GitHub의 새 기능인 **Agentic Workflows**에서 간접 프롬프트 인젝션 취약점 하나를 찾아 **GitLost**라고 이름 붙였다. 요지는 단순하고 그래서 더 불편하다. 코드도, 접근 권한도, 자격 증명도 없는 외부인이 **공개 저장소에 이슈 하나를 여는 것만으로** 같은 조직의 **비공개 저장소 내용**을 **누구나 보는 공개 댓글**로 끌어낼 수 있었다.

## TL;DR

- 공격자는 조직의 공개 저장소에 그럴듯한 이슈만 열면 됐다. `issues.assigned` 이벤트로 트리거된 에이전트 워크플로가 이슈 본문 속 숨은 지시를 따라 비공개 저장소 README를 읽어 공개 댓글에 게시했다.
- GitHub의 가드레일은 있었지만 `"Additionally"` 한 단어를 붙이는 변형에 뚫렸다 — 모델이 거부 대신 출력을 재구성했다.
- 근본 원인은 권한 우회가 아니라 설계다. 신뢰할 수 없는 사용자 입력과 민감 데이터 접근을 **같은 컨텍스트 창에** 넣은 것 자체가 취약점이다.

## 무슨 일이 벌어졌나

GitHub Agentic Workflows는 저장소 자동화를 **자연어**로 쓰게 해준다. 워크플로는 Markdown(`.md`)으로 작성되고, 실행 시 YAML GitHub Actions(`.yml`)로 컴파일된다. 실행되면 **Claude 또는 GitHub Copilot 기반 AI 에이전트**가 설정된 권한 안에서 이슈를 읽고, 도구를 호출하고, 조직 내 다른 저장소에 접근한다.

Noma Labs가 지목한 취약한 설정은 다음 조건이 겹칠 때 성립했다.

- `issues.assigned` 이벤트에서 워크플로가 트리거된다.
- 에이전트가 이슈의 **Title / Body**를 읽는다.
- `add-comment` 도구로 댓글을 게시한다.
- 그 에이전트가 **공개·비공개 저장소 모두**에 대한 읽기 권한을 갖고 있다.

공격 시나리오는 이렇게 흘러갔다. 연구진은 고객 미팅 이후 "VP Sales가 요청하는 것처럼 보이는" 그럴듯한 GitHub 이슈를 만들었다. 이슈가 할당되자 워크플로 액션이 트리거됐고, 에이전트는 이슈 본문에 숨은 지시를 따라 **`poc`(공개)** 와 **`testlocal`(비공개)** 저장소의 `README.md`를 가져오도록 유도됐다. 그리고 그 내용을 그대로 공개 저장소 이슈 댓글에 게시했다 — 인증되지 않은 누구나 읽을 수 있는 상태로.

이게 바로 **간접 프롬프트 인젝션**이다. 공격자가 에이전트가 "읽을" 콘텐츠 안에 악성 지시를 심고, 운영자가 의도한 지시보다 그 숨은 지시가 우선 처리되게 만드는 것이다.

### "Additionally" 한 단어로 가드레일 우회

GitHub에는 이 시나리오를 막기 위한 제한적 가드레일이 있었다. Noma Labs는 공격자처럼 여러 변형을 반복했고, `"Additionally"`라는 키워드를 붙이자 모델이 **거부 대신 출력을 재구성하는** 의도치 않은 동작을 보였다. 이 한 번의 우회로 가드레일은 데이터 유출을 막지 못했다.

이 디테일이 핵심이다. LLM 컨텍스트 창 **안쪽에** 강한 보안 경계를 세우려는 시도가 왜 근본적으로 취약한지를 보여주기 때문이다. 모델은 본질적으로 지시를 따르도록 만들어졌고, 시스템 규칙과 사용자 입력을 같은 창에 섞으면 더 최신이거나 더 집요한 지시가 이긴다.

### 공개된 증거

Noma Labs는 재현 워크플로와 실제 증거를 공개했다. 유출된 데이터에는 `sasinomalabs/poc`(공개), `sasinomalabs/remote-ping`(공개, README 없음), 그리고 **`sasinomalabs/testlocal`(비공개)** 의 README 내용이 포함됐다. GitLost는 GitHub에 책임 있게 공개됐고, 세부사항은 GitHub가 인지한 상태에서 공유됐다.

## 왜 중요한가

에이전트형 AI에서는 보안 전제가 바뀐다. 에이전트의 **컨텍스트 창은 작업 공간인 동시에 공격 표면**이다. 에이전트가 읽는 것은 무엇이든 — 이슈, PR, 댓글, 파일 — 무기화될 수 있다. 전통적 보안 모델은 신뢰 경계가 코드로 강제된다고 가정하지만, 에이전트 시스템에서는 그 경계의 일부가 **모델의 동작**에 의해 강제된다. 그래서 원문은 프롬프트 인젝션이 에이전트형 AI에서 **SQL 인젝션이 웹 앱에 가졌던 것과 같은 범주형 취약점**이라고 본다.

다만 이 비유는 커뮤니티에서 반박도 받았다(아래는 원문 댓글의 논쟁이지 확정 사실이 아니다). 여러 지적이 나왔다.

- SQL 인젝션의 진짜 해법은 "준비된 문장"이 아니라 **매개변수 바인딩** — 코드와 데이터를 별도 채널로 제출해 분리하는 것이다. 에이전트에 "고정 동작 메뉴"만 허용하는 완화책은 코드/데이터를 분리하지 못하니 엄밀히는 같은 해법이 아니다. 오히려 "더 엄격한 DB 권한"에 가깝다.
- 반대편에선 "이건 GitHub 취약점이 아니라 **잘못된 설정**"이라는 시각도 있었다. 비공개 데이터 접근권과 아무나 상호작용하는 공개 채널을 한 에이전트에 함께 줬으니 유출은 당연하다는 것. 비밀값에 접근하는 CI가 공개 PR에서 실행되는 것과 같은 고전적 실수라는 지적이다.
- 그럼에도 **GitHub의 책임**을 묻는 목소리도 있었다. 토큰 범위를 조여도 공개 저장소 접근은 늘 열려 있어 공개 이슈를 통한 유출 경로가 남고, GitHub가 제공하는 세분화된 제어가 이런 결합의 위험을 안전하게 막아주지 못한다는 것이다. (댓글에서 cross-repository 관련 설정 문서와 별도 블로그 링크가 거론됐으나, 이 글은 그 링크 내용을 검증하지 않았다.)

결론적으로 논쟁의 방향은 하나로 수렴한다. **신뢰할 수 없는 입력과 민감 데이터를 한 에이전트에 동시에 물리면 안 된다.** 이건 "지원 직원이 사회공학에 속는 걸 패치로 못 고치는 것"처럼, 에이전트 계층에서 신뢰성 있게 막을 수 없는 종류의 문제다.

## 어떻게 써먹나

에이전트 워크플로를 굴리고 있다면, 원문이 제시한 방어책은 그대로 체크리스트가 된다.

- **사용자 제어 콘텐츠를 신뢰된 지시로 취급하지 마라.** 이슈·PR·댓글 본문은 데이터일 뿐, 시스템 지시가 아니다. 모델에 넣기 전에 지시 컨텍스트에서 정제·격리한다.
- **최소 권한.** 에이전트 권한은 필요한 최소 범위로 좁힌다. 여러 저장소에 접근하는 에이전트는 그 자체로 고가치 표적이다.
- **접근과 출력을 분리하라.** 비공개 저장소 읽기 권한과 공개 게시 능력을 한 에이전트에 함께 주지 않는다. 저장소별로 워크플로 에이전트를 나누거나, 넓은 접근권을 가진 에이전트는 **허용 목록** 사용자만 트리거하게 잠근다.
- **공개 출력 범위를 제한하라.** 이슈에 응답하는 에이전트가 공개적으로 게시할 수 있는 내용을 명시적으로 좁힌다.

핵심은, 가드레일 프롬프트 하나로 "알아서 막히길" 기대하지 말고 **권한과 경계를 인프라 계층에서** 강제하는 것이다.
