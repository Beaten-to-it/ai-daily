Claude Code나 Codex 같은 터미널 에이전트를 한 대가 아니라 두세 대에서 동시에 굴려본 사람이라면 아는 통증이 있다. 어느 세션이 끝났는지, 어디서 멈췄는지, 어느 놈이 승인 프롬프트를 띄워놓고 나를 기다리는지 확인하려고 터미널 창을 계속 왔다갔다 해야 한다. 그리고 여러 작업이 한꺼번에 끝나면 그때부터 진짜 지옥 — 서로 다른 브랜치를 손으로 합치는 머지 노가다가 시작된다. `vilmire`가 만든 **ADHDev 1.0**은 정확히 이 두 가지를 없애려는 도구다. 스탠드얼론 에디션은 AGPL로 공개됐고, 운영비는 클라우드 버전으로 번다는 구조다.

## TL;DR

- 이미 쓰고 있는 터미널 에이전트에 **데몬 + 웹 대시보드**를 붙여, 브라우저에서 큐에 넣은 태스크를 격리된 git 워크트리로 (여러 머신이면 머신 간에도) 분배한다.
- 작업이 끝나면 **Refinery** 파이프라인이 저장소 자체 검증(빌드/테스트/린트)과 패치 동등성을 확인한 뒤 **git fast-forward로만** main에 병합하고 워크트리까지 정리한다 — force-push 없음, 애매하면 병합 안 하고 사람에게 반환.
- 승인은 폰 푸시 원탭, 연결은 **WebRTC P2P + TURN 폴백**이라 포트포워딩·VPN이 아예 없고, 코드는 서버를 거치지 않는다(서버는 인증·시그널링·경량 세션 상태만).

## 무엇을 만들었나

핵심 발상은 "에이전트를 새로 만들지 않는다"이다. 이미 돌리고 있는 Claude Code·Codex 같은 터미널 에이전트 **위에** 얇게 얹는 관제 레이어다. 구성은 세 덩어리로 나눠 볼 수 있다.

**1) 분배 — 격리된 워크트리로.** 브라우저 대시보드에서 태스크를 큐에 넣으면 각 태스크가 독립된 git 워크트리에 배정된다. 워크트리가 격리돼 있으니 여러 태스크가 같은 저장소를 물어도 서로의 작업 트리를 밟지 않는다. 머신이 여러 대면 그 분배가 머신 경계를 넘어서 일어난다 — 맥 워커와 윈도우 워커에 태스크가 흩어져 병렬로 돈다.

**2) 병합 — Refinery.** 저자가 가장 공들인 부분이다. 작업이 끝났다고 바로 main에 붙이지 않는다. Refinery라는 파이프라인이 (a) 저장소가 원래 갖고 있는 검증 — 빌드/테스트/린트 — 을 돌리고, (b) 패치 동등성을 확인한 다음, (c) **fast-forward로만** main에 병합하고, (d) 다 쓴 워크트리를 청소한다. 여기서 설계 철학이 드러나는 문장이 있다: "force-push는 절대 안 하고, 애매하면 병합하지 않고 저한테 되돌립니다." 즉 충돌이나 비선형 히스토리가 생기는 상황에서 머지 커밋을 만들어 억지로 합치거나 리베이스로 재주를 부리지 않고, 그냥 멈춰서 사람을 부른다. 저자 표현으로는 "똑똑한 척 하지 않고 멈춰서 물어보는 쪽"이다.

**3) 조종 — 폰에서.** 승인 요청이 폰 푸시로 오고 원탭으로 처리된다. 저자는 핫스팟만 켜고 노트북은 가방에 넣은 채 폰으로만 승인·지시하며 돌아다닌 경험을 든다. 이게 가능한 이유가 연결 구조인데, WebRTC P2P에 TURN 폴백이라 사용자가 포트포워딩이나 VPN을 세팅할 필요가 없다. 채팅·명령·스크린샷은 브라우저와 데몬이 직접 주고받고, 서버는 인증과 시그널링, 가벼운 세션 상태만 맡는다 — **코드 자체는 서버를 통과하지 않는다.** 스크린샷을 채팅에 붙여넣으면 다른 머신에서 도는 터미널 에이전트의 컨텍스트로 그대로 들어간다는 디테일도 있다.

**MAGI — 교차검증 모드.** 읽기 전용 질문 하나를 여러 머신·여러 모델 리플리카에 동시에 던지고, 답이 어디서 갈리는지를 보여준다. 여기서 눈여겨볼 디자인은 "같은 머신에서 나온 합의는 두 번 세지 않고 할인한다"는 점이다. 단순 다수결이면 같은 환경·같은 모델 복제본들이 몰표를 던져 합의를 부풀릴 수 있는데, 동일 머신發 합의에 가중치를 깎아 그 착시를 줄이려는 것이다. 즉 MAGI가 노리는 건 '정답 투표'가 아니라 '**어디서 의견이 갈리는지**'를 드러내는 것 — 리뷰어가 파고들 지점을 찾아주는 용도에 가깝다.

저자는 이 프로젝트 자체를 ADHDev로 개발하는 도그푸딩을 하고 있고, 최근 7개 태스크짜리 프로토콜 마이그레이션을 맥·윈도우 워커가 나눠 작성해 전부 Refinery로 병합했다고 밝힌다.

## 왜 중요한가

'폰에서 코딩 에이전트 제어'는 이제 붐비는 카테고리다(GeekNews만 봐도 유사 도구들이 계속 올라온다). ADHDev가 그 안에서 갈라서는 지점은 **제어가 아니라 병합**이다. 대부분의 모바일 제어 도구는 "어느 세션이 뭘 하는지 보고 승인한다"는 관측·개입 문제를 푸는데, ADHDev는 거기에 더해 "여러 개가 동시에 끝났을 때의 통합"이라는, 병렬 에이전트 워크플로의 진짜 병목을 정면으로 겨냥한다.

그리고 그 통합을 푸는 방식이 **의도적으로 겸손하다.** ff-only는 기능이 아니라 제약이다. 자동 병합 도구가 흔히 빠지는 함정 — 충돌을 자동으로 '해결'하려다 조용히 잘못된 코드를 main에 밀어넣는 것 — 을 원천 차단하는 대신, 애매한 케이스를 전부 사람에게 되던진다. 자동화의 신뢰 문제를 '더 똑똑한 자동 해결'이 아니라 '안전한 곳까지만 자동화하고 나머지는 멈춤'으로 접근한 것이다. 자율 에이전트를 실제 저장소에 붙일 때 이 선택은 보수적이지만 사고를 안 낸다는 점에서 설득력이 있다.

연결 설계(P2P + TURN, 코드 non-through-server)도 그냥 편의가 아니라 채택 장벽·프라이버시 얘기다. 팀 인프라에 포트를 열거나 VPN을 강제하지 않고, 소스가 중앙 서버를 경유하지 않는다는 건 개인 개발자·소규모 팀이 자기 코드를 남의 클라우드에 태우지 않고도 이 워크플로를 쓸 수 있다는 뜻이다.

## 어떻게 써먹나

- **셀프호스트 한 줄:** `npm i -g adhdev` 후 `localhost:3847`에 대시보드가 뜬다 — 계정 불필요(저자 코멘트 기준). 스탠드얼론은 AGPL이라 라이선스 조건만 확인하면 자체 인프라에서 돌릴 수 있다.
- **적합한 상황:** 머신 2~3대에 에이전트를 흩뿌려 병렬로 돌리고, 이동 중 폰으로 승인만 쳐주면서 결과를 안전하게 main에 모으고 싶을 때. 특히 태스크를 잘게 쪼개 여러 워커에 나눠주는 병렬 워크플로와 궁합이 맞는다.
- **알고 들어갈 한계:** 저자 스스로 인정하듯 **단일 머신 도구보다 셋업이 무겁다.** 여러 머신·데몬·시그널링을 엮는 구조라 1인 1머신이면 오버킬일 수 있다. 그리고 머지가 순수 ff-only라, 충돌이 잦은 팀 브랜치 전략에선 "멈춰서 물어봄"이 자주 발동해 손이 더 갈 수 있다 — 이건 버그가 아니라 설계 선택이다.
- 저자가 ff-only 머지 설계와 MAGI 교차검증의 실효성에 대한 설계 질문을 환영한다고 했으니, 도입 검토 시 자기 팀 시나리오를 들고 이슈로 물어보는 것도 방법이다.
