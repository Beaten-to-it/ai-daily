## TL;DR
- soliestre가 **코드를 빌드 산출물로 강등하고 한국어 "명세"를 git의 단일 진실원(SSoT)으로 커밋**하는 방식으로 PWA 앱(Rimlog)과 셀프호스트 서버를 만들어 공개했다. 앱 골격 40줄·AI 카드 25줄·서버 한 장짜리 명세가 코드를 생성한다.
- 생성 코드에 **명세 해시를 박아** 명세만 고치거나 코드만 고치면 pre-commit이 커밋을 막는다. 실측상 **사람이 유지하는 줄 수가 60~82% 감소**했는데, 정작 생성된 코드 자체는 원본보다 길어지기도 한다 — 줄어드는 건 "사람이 읽고 고치는 쪽"뿐이다.
- 서버 백엔드는 nvidia 무료 API(기본)·`claude -p`/`codex exec` 자식 프로세스 호출(구독 재활용)·openai/google 키 프록시 중 선택. 다만 명세↔코드 정합 검증(정적 diff → property 기반 동적)의 캘리브레이션과 headless DOM 거짓 양성 문제는 저자도 아직 미해결이라고 밝힌다.

## 무슨 일인가

GeekNews에 올라온 soliestre의 Show GN 글이다. 문제의식은 AI 코딩을 해 본 사람이면 다 아는 통증에서 출발한다. **결과물 코드는 리포에 남지만, 그 코드를 만들어 낸 대화와 의도는 증발한다.** 석 달 뒤 "이게 왜 이렇게 돼 있지?"라고 물어볼 대상이 없다는 것.

그래서 저자는 방향을 뒤집었다. **의도를 담은 명세를 git에 커밋하고, 코드는 명세로부터 굽는(brew) 빌드 산출물로 취급한다.** 검증 삼아 작은 앱을 끝까지 만들어 공개했다 — Rimlog라는 PWA다. 독서·학습 기록을 남기면 AI가 예전 메모를 이어 붙여 주는 물건인데, 서버 없음·가입 없음·데이터는 브라우저에만 있다. 저자 본인 표현대로 "앱은 평범"하고, 공유하고 싶은 건 **만든 방식**이다.

방식 리포의 `eux/` 폴더에는 한국어 명세 3장이 들어 있다. 이 명세는 코드가 아니라 이런 자연어 문장으로 돼 있다:

> saveCapture : 캡처 폼(소스명·인용·내 생각·태그) 저장 — captures 맨 앞 삽입 + 로컬 스토리지 반영 + "저장됐어요" 토스트 + 기록 탭으로 전환.

이 파일을 **EstreUX**라는 도구에 넣으면 코드가 나온다(저자는 이 동작을 "brew"라고 부른다). 핵심 장치는 두 가지다.

1. **해시 게이트.** 생성된 코드에는 원본 명세의 해시가 박힌다. 명세만 고치거나 코드만 고치면 pre-commit 단계에서 커밋이 거부된다. "명세가 낡는 순간 거짓말이 되는" 문제 — spec-driven 방식이 늘 실패하는 지점 — 를 사회적 약속이 아니라 커밋 게이트로 강제한다.
2. **줄 수 실측.** 프레임워크에 원래 있던 152줄짜리 숫자 키패드를 28줄 명세로 되돌리는 식으로 재 봤더니, 사람이 유지해야 하는 줄 수가 60~82% 줄었다. 여기서 오해하면 안 되는 부분: **생성된 코드 자체는 원본보다 길어지기도 한다.** 줄어드는 건 총 코드량이 아니라 사람이 읽고 손대는 표면적이다. 측정 기록은 리포에 남겨 뒀다고 한다.

## 서버도 명세 한 장

Pages 데모는 서버리스라 AI가 태그 겹침(tag overlap) 폴백으로만 동작한다. 제대로 돌리려고 셀프호스트 서버를 붙였는데, 이것 역시 **명세 한 장에서 brew한 의존성 0짜리 node 단일 파일**이다. 백엔드는 골라 쓴다:

- **nvidia (기본):** `build.nvidia.com`의 무료 API. 카드 등록 없이 키를 주고, OpenAI 호환에 분당 40회쯤이라 개인 일지엔 넉넉하다.
- **claude-cli / codex-cli:** 요청마다 `claude -p` / `codex exec`를 자식 프로세스로 부른다. **이미 내고 있는 Claude/ChatGPT 구독을 API 키 없이 재활용하는 경로**다.
- **openai / google:** 단순 키 프록시.

키와 인증은 서버에만 있고 브라우저로는 나가지 않는다. 커밋 이력을 처음부터 따라가면 스캐폴드→명세→생성→다듬기 순서가 그대로 남아 있어, 이 방식이 실제로 어떻게 굴러갔는지 재구성할 수 있게 해 놨다.

저자 스스로 아직 확신이 없다고 밝힌 지점도 정직하게 적어 뒀다. 명세↔코드 정합 판정을 정적 diff에 더해 **property 기반 동적 검사**로 확장 중인데 가중치 캘리브레이션이 미완이고, **headless DOM 환경에서 프레임워크 렌더가 실브라우저와 달라 생기는 거짓 양성** 클래스를 발견해 검증 환경을 실브라우저로 승격하는 게 숙제로 남았다.

## 왜 중요한가

"영어(자연어) 명세로 LLM과 대화한다"는 담론(Spec Kit, CodeSpeak 등)은 많지만, 대부분 **명세와 코드가 시간이 지나면 갈라진다**는 근본 문제에서 무너진다. 이 프로젝트가 흥미로운 건 그 드리프트를 **해시 + pre-commit이라는 기계적 게이트**로 막았다는 점이다. 명세를 SSoT로 두겠다는 선언이 아니라, 둘이 어긋나면 커밋 자체가 안 되게 만든 실행이다.

또 하나는 유지보수 비용에 대한 재정의다. 저자는 "코드가 줄었다"가 아니라 **"사람이 읽고 고치는 표면이 줄었다"**를 측정치로 내민다. AI가 코드를 계속 뱉는 시대에 진짜 병목은 코드량이 아니라 사람의 이해·수정 부담이라는 관점 전환이고, 이건 실측 숫자로 뒷받침돼 있어 흘려듣기 어렵다.

## 어떻게 써먹나

- **자연어 명세를 SSoT로 실험하고 싶다면,** 이 리포의 `eux/` 명세 3장 + 해시 게이트 구조가 참고할 만한 최소 레퍼런스 구현이다. 핵심은 "명세만/코드만 고치면 pre-commit에서 막는다"는 규율을 도구화한 부분이다.
- **`claude -p` / `codex exec`를 앱 백엔드로 붙이는 구독 재활용 패턴**은 개인 도구·프로토타입에서 API 과금을 우회하는 실전 경로다. 다만 저자 본인도 레이트·약관·레이턴시 측면의 리스크를 열린 질문으로 남겨 뒀다 — 개인 일지 규모를 넘어서면 약관·동시성에서 걸릴 여지가 있으니 프로덕션엔 그대로 옮기지 말 것.

참고로 저자는 독자에게 두 가지 열린 질문을 던진다: **명세를 SSoT로 둘 때 명세의 표현력이 코드를 못 따라가는 지점은 어디였나**, 그리고 **`claude -p`를 앱 백엔드로 쓰는 구독 재활용이 실사용에서 걸릴 지점(레이트·약관·레이턴시)은 무엇인가**. 같은 고민을 해 본 사람이라면 논의해 볼 지점이다.
