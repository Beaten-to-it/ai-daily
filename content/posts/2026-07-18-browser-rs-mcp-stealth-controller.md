## TL;DR
- 에이전트마다 크롬을 하나씩 띄우는 기본 구조는 에이전트당 500MB~1GB RAM을 먹어, 5개만 굴려도 브라우저만으로 2.5~5GB가 나간다 — browser-rs-mcp는 브라우저 하나에 모든 에이전트를 raw CDP로 붙이고 서버가 owner 단위로 탭을 격리해 이 곱셈을 끊는다.
- Rust로 다시 짜고 브라우저를 내장하지 않는(기존 크롬에 붙는) 구조라 서버 바이너리는 단일 6MB이며, `Runtime.enable` 같은 탐지되기 쉬운 CDP 도메인을 켜지 않고 패치된 가짜 브라우저 대신 사용자의 진짜 크롬 + persistent profile을 그대로 쓴다.
- raw CDP 기반 62개 tool(접근성 트리 ref, action settle-diff, network/cookies/storage/PDF/upload/iframe/WebAuthn)을 stdio와 HTTP/SSE로 노출한다.

## 본문

멀티 에이전트를 실전에서 굴려본 사람이라면 브라우저 자동화의 진짜 병목이 CPU도 네트워크도 아닌 **메모리**라는 걸 안다. 통상적인 셋업은 "에이전트 하나에 크롬 하나"가 기본값이다. 문제는 이 기본값이 에이전트당 500MB에서 1GB의 RAM을 잡아먹는다는 것이다. 에이전트를 다섯 개만 병렬로 돌려도 브라우저 프로세스만으로 2.5~5GB가 증발한다. 에이전트 수에 비례해 이 오버헤드가 선형으로 곱해지니, "에이전트를 늘린다 = 메모리가 늘어난다"가 구조적으로 박혀 있는 셈이다.

여기에 더해, 흔히 쓰는 Playwright는 CDP(Chrome DevTools Protocol) 세션 자체가 세션 하나당 약 180MB를 기본으로 소비한다. 이건 브라우저 프로세스가 먹는 메모리와는 별개다. 즉 실제로 페이지를 렌더링하는 비용을 빼고도, 브라우저를 제어하는 CDP 레이어 자체가 이미 무겁다는 뜻이다. 저자 maestrojeong이 GeekNews에 Show GN으로 공개한 browser-rs-mcp는 바로 이 구조를 깨는 데서 출발한다.

핵심 발상은 단순하다. **브라우저는 딱 하나만 띄운다.** 그 위에 에이전트가 몇 개가 됐든 raw CDP로 직접 붙고, 서버가 owner(소유 에이전트) 단위로 탭을 강제 격리한다. 에이전트 A가 연 탭을 B는 건드릴 수 없다. 인스턴스 하나로 N개의 에이전트를 감당하기 때문에, 에이전트가 늘어나도 브라우저가 쓰는 메모리는 늘지 않는다. 앞서 말한 선형 곱셈이 상수로 바뀌는 지점이 여기다.

구현 언어와 배치 구조도 바꿨다. Playwright 계열의 무거운 런타임 대신 Rust로 다시 짰고, 브라우저를 프로젝트 안에 내장하지 않는다. 대신 사용자가 이미 띄워둔 크롬에 `--connect`로 붙는 방식을 택했다. 그 결과 서버 자체는 의존성을 주렁주렁 달지 않은 **단일 바이너리 6MB**로 떨어진다. 배포·기동 관점에서 이건 "브라우저 엔진을 통째로 번들하는" 접근과는 체급이 다른 이야기다.

탐지 회피 전략도 눈여겨볼 만하다. 저자는 Patchright의 접근에 착안했다고 밝힌다. 자동화 탐지에 자주 걸리는 `Runtime.enable` 같은 CDP 도메인을 아예 켜지 않고, 패치된 가짜 브라우저를 새로 만드는 대신 **사용자의 진짜 크롬과 persistent profile을 그대로** 사용한다. 봇 탐지 우회의 통상적인 실패 지점이 "너무 깨끗한, 방금 만든 것 같은 프로필"과 "자동화 티가 나는 CDP 시그널"이라는 점을 감안하면, 실제 사람이 쓰던 프로필 위에서 최소한의 CDP만 노출하는 방향은 합리적인 선택이다.

기능 표면은 얇지 않다. raw CDP 기반으로 62개의 tool을 제공하는데, 접근성 트리 기반 ref(요소 참조), 액션 후 DOM이 안정될 때까지 기다렸다가 변화를 잡아내는 action settle-diff, 그리고 network·cookies·storage·PDF·upload·iframe·WebAuthn까지 실무에서 필요한 조작들을 포괄한다. 프로토콜은 로컬 통합에 쓰는 stdio와 원격/스트리밍에 쓰는 HTTP/SSE 양쪽을 지원한다. 설치는 curl로 받아 셸에 파이프하는 원라인 스크립트 방식으로 안내되며(`curl -fsSL … | sh` 형태), Windows 빌드와 crates.io 등록은 아직 남은 과제로 언급돼 있다.

## 왜 중요한가

멀티 에이전트가 "논문 속 데모"에서 "실제로 여러 개를 상시 굴리는 운영"으로 넘어가는 순간, 지금까지 무시하던 상수들이 벽으로 돌아온다. 에이전트당 1GB 브라우저는 프로토타입에선 안 보이지만 10개, 20개 스케일에선 비용 곡선을 그대로 결정한다. browser-rs-mcp가 던지는 메시지는 "브라우저 인스턴스를 에이전트 수에서 분리하라"는 것이고, owner 단위 탭 격리는 그걸 멀티테넌시로 안전하게 만드는 최소 장치다. 6MB 단일 바이너리 + 기존 크롬 연결 구조는 컨테이너·CI·엣지처럼 무거운 브라우저 번들을 넣기 싫은 환경에서 배포 마찰을 크게 줄인다. MCP 표준을 따르므로, 특정 에이전트 프레임워크에 묶이지 않고 tool 서버로 끼워 넣을 수 있다는 점도 채택 장벽을 낮춘다.

## 어떻게 써먹나

- **다수 에이전트를 한 머신에서 병렬로 돌리는 경우:** 에이전트마다 크롬을 띄우는 대신 이걸 공유 컨트롤러로 두고 owner 격리에 기대면, RAM 예산을 에이전트 수와 디커플링할 수 있다. 스케일 테스트 전에 단일 브라우저 + N owner 구성으로 메모리 상한부터 잡아보라.
- **기존 크롬 세션(로그인·프로필)을 그대로 재사용해야 하는 경우:** `--connect`로 이미 열린 크롬에 붙는 구조라, 매번 로그인 상태를 다시 만들 필요가 없고 봇 탐지에도 상대적으로 강하다. persistent profile을 쓰는 워크플로에 맞다.
- **배포 무게가 중요한 환경(CI·컨테이너·엣지):** 브라우저를 번들하지 않는 6MB 바이너리라 이미지 크기와 콜드 스타트가 가볍다. 단, 실행 머신에 크롬이 별도로 있어야 한다는 전제는 확인하고 들어가라.
- **설치 시 주의:** `curl … | sh` 파이프-투-셸 방식은 편하지만 스크립트를 신뢰 검증 없이 실행하는 셈이다. 운영 도입 전이라면 스크립트를 먼저 내려받아 내용을 읽고, Windows·crates.io 미지원 같은 미완 항목을 감안해 도구 성숙도를 평가하는 게 좋다.
