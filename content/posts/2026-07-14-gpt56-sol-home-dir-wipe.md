## TL;DR

- Codex에서 gpt-5.6-sol 에이전트가 디버깅용 임시 폴더를 만들려고 소문자 `$home` 변수를 선언했는데, PowerShell이 대소문자를 구분하지 않는 탓에 사용자 프로필 경로(`C:\Users\<username>`)를 가리키는 내장 자동 변수 `$HOME`과 같은 변수로 취급돼 충돌했다.
- 그 결과 임시 폴더 대신 실제 홈 루트를 대상으로 `Remove-Item ... -Recurse -Force`가 실행됐고, 열려 있던 파일들의 시스템 잠금 덕분에 "Directory is not empty" 에러로 중간에 멈췄지만 `.ssh`·`.config`·`.npm` 일부는 이미 수정·삭제된 뒤였다.
- 교훈은 모델 성능 문제가 아니다. 추론 모델에게 호스트 터미널 직접 접근을 허용하는 순간 쉘의 변수 스코프·대소문자 규칙이 그대로 파괴적 위험 벡터가 되며, 엄격한 샌드박싱·컨테이너 격리는 선택이 아니라 전제 조건이 된다.

## 무슨 일이 있었나

한 사용자가 GeekNews에 올린 사고 보고를 요약하면 이렇다. Codex에서 최신 플래그십으로 소개된 gpt-5.6-sol 에이전트를 쓰던 중, 에이전트가 디버깅 작업을 위해 임시 기준(baseline) 디렉터리를 만들려 했다. 이를 위해 에이전트는 다음과 같은 PowerShell 블록을 생성해 실행했다.

```powershell
$home = Join-Path $env:TEMP 'temporary-build-folder'
if (Test-Path -LiteralPath $home) {
    Remove-Item -LiteralPath $home -Recurse -Force
}
```

코드만 보면 "임시 폴더 경로를 잡고, 이미 있으면 지운다"는 평범한 정리 루틴이다. 문제는 변수 이름 선택에 있었다. 보고자에 따르면 PowerShell에서 `$HOME`은 현재 사용자의 프로필 디렉터리를 직접 가리키는 **내장 자동 변수(built-in automatic variable)**다. 게다가 PowerShell은 변수 이름의 대소문자를 구분하지 않기 때문에, 에이전트가 새로 선언한 소문자 `$home`이 기존 전역 `$HOME`과 동일한 이름으로 충돌했다는 것이 사고자의 설명이다.

사고자의 서술로는, `Remove-Item` 라인에 도달했을 때 경로가 의도한 임시 폴더가 아니라 실제 사용자 루트로 평가됐고, 최종적으로 에이전트가 실행한 명령은 다음과 같았다.

```powershell
Remove-Item -LiteralPath 'C:\Users\<username>' -Recurse -Force
```

즉 "임시 빌드 폴더를 청소"하려던 코드가 홈 디렉터리 전체를 재귀·강제 삭제하는 명령으로 바뀌어 있었다.

## 어떻게 최악을 면했나

전체 삭제라는 참사를 막은 건 코드의 안전장치가 아니라 운영체제의 우연한 잠금이었다. 그 순간 열려서 사용 중이던 파일들에 시스템 잠금이 걸려 있었고, 삭제가 진행되던 도중 `WriteError: Directory is not empty` 에러를 뱉으며 멈췄다. 덕분에 디렉터리가 통째로 사라지는 상황은 피했다.

다만 "면했다"는 게 무손상을 뜻하지는 않았다. 에이전트는 곧바로 자기 실수를 감지해 작업을 중단(abort)하고 자체 감사에 들어갔고, 확인 결과 `.ssh`, `.config`, `.npm` 등 몇몇 설정 파일과 도트파일은 이미 수정됐거나 사라진 상태였다. 개발 환경에서 이 세 디렉터리가 어떤 의미인지 생각하면 — SSH 키·각종 앱 설정·패키지 캐시와 인증 — 부분 손상만으로도 충분히 하루를 날릴 만한 피해다.

## 왜 중요한가

이 사건의 핵심은 "모델이 멍청해서"가 아니다. 보고자 스스로도 gpt-5.6-sol이 긴 호흡의 작업(long-horizon task)에서 놀랍도록 끈질기고 유능했다고 평가한다. 오히려 유능한 에이전트가 **평범해 보이는 정리 스크립트 한 줄**에서 파괴적 명령을 만들어냈다는 점이 무섭다.

- **변수 섀도잉은 사람도 자주 밟는 지뢰다.** 내장 자동 변수(`$HOME`, `$PROFILE`, `$PWD` 등)를 사용자 변수로 덮어쓰는 실수, 그리고 대소문자 미구분에서 오는 이름 충돌은 PowerShell을 오래 쓴 사람도 겪는다. 에이전트라고 면역이 있을 이유가 없고, 오히려 코드를 빠르게 대량 생성할수록 밟을 확률이 올라간다.
- **`-Recurse -Force`의 파괴력은 경로 하나에 달려 있다.** 명령 자체는 정당하다. 위험은 "무엇을 지우느냐"가 실행 시점에 변수 평가로 결정된다는 데 있다. 에이전트가 경로 변수의 출처를 오해하는 순간, 정당한 명령이 곧 재앙이 된다.
- **터미널 직접 접근 = 신뢰 경계 붕괴.** 모델의 추론 품질과 무관하게, 호스트 쉘에 직결된 에이전트는 쉘의 모든 함정(스코프·대소문자·자동 변수·와일드카드 확장)을 그대로 상속한다. 성능이 좋아질수록 이 위험은 줄어드는 게 아니라, 더 대담하고 자동화된 실행으로 오히려 커진다.

## 어떻게 써먹나

GPT-5.6 계열이든 다른 모델이든, CLI 에이전트를 만들거나 붙일 계획이라면 이 사고에서 뽑을 실무 조치는 분명하다.

- **호스트 홈을 애초에 못 보게 한다.** 에이전트 실행은 전용 컨테이너/VM 안에서, 프로젝트 작업 디렉터리만 바인드 마운트하고 `$HOME`·`.ssh`·`.config`는 마운트에서 제외한다. "지울 수 있는 것"의 최대 범위를 물리적으로 줄이는 게 프롬프트 가드레일보다 확실하다.
- **파괴적 명령에 확인 게이트를 건다.** `Remove-Item -Recurse -Force`, `rm -rf`, `git clean -fdx` 같은 삭제 계열은 자동 승인 대상에서 빼고, 실제 평가된 절대 경로를 사람이 보는 단계에서 확인하게 한다. 특히 삭제 대상 경로가 홈·시스템 루트·부모 디렉터리로 해석되면 무조건 차단하는 규칙을 둔다.
- **임시 폴더 이름에 예약·자동 변수를 쓰지 않도록 규약을 박는다.** 에이전트가 생성하는 스크립트에서 `$home`, `$env`, `$profile` 같은 이름을 로컬 변수로 쓰지 못하게 하고, 임시 경로는 `New-TemporaryFile`/`[System.IO.Path]::GetTempPath()`처럼 충돌 여지 없는 API로 잡게 한다.
- **되돌릴 수 있게 설계한다.** 삭제 대신 휴지통/격리 폴더 이동, 작업 전 스냅샷, 홈·설정의 정기 백업. 이번 건도 "우연한 파일 잠금"이 아니라 준비된 롤백이 최후 방어선이었어야 한다.

한 가지 덧붙이면, 이건 단일 사용자의 사고 보고(gist 스크린샷 첨부)이지 벤더가 확인한 인시던트는 아니다. 그럼에도 여기서 드러난 실패 유형 — 내장 자동 변수와의 이름 충돌, 실행 시점에 결정되는 삭제 경로, 호스트 터미널 직결 — 은 모두 실재하는 위험이라 교훈은 그대로 유효하다.
