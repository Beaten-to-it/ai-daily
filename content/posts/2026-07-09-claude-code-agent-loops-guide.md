코딩 에이전트를 쓰다 보면 어느 순간 깨닫게 된다. "코드 읽어 → 고쳐 → 테스트 돌려 → 결과 보여줘"를 매번 사람이 손으로 타이핑하고 있다는 것을. Claude Code 팀은 이 수동 반복에서 벗어나, **정지 조건이 충족될 때까지 에이전트가 스스로 작업 사이클을 반복하는 운영 패턴**을 "루프"라고 부르고, 이걸 네 종류로 정리한 글을 냈다. 핵심은 "매 프롬프트를 지시하는" 방식에서 "언제 멈출지만 정해주면 알아서 도는" 방식으로의 이동이다.

## TL;DR

- Claude Code 팀은 에이전트 루프를 **트리거 방식 / 정지 방식 / 사용하는 primitive / 적합한 작업 유형** 네 기준으로 분류하고, 이를 **Turn-based · Goal-based · Time-based · Proactive** 네 유형으로 나눈다.
- 각 유형은 위임 대상이 다르다 — Turn-based는 *검증*을, Goal-based는 *정지 조건*을, Time-based는 *트리거*를, Proactive는 *프롬프트 자체*를 에이전트에 넘긴다. 대응하는 명령이 `/goal`, `/loop`, `/schedule`이다.
- 모든 작업에 복잡한 루프가 필요한 건 아니다. 가장 단순한 해법부터 시작하고, 루프의 출력 품질은 결국 **주변 시스템(코드 청결·검증 skill·토큰 관리)**에 좌우된다는 게 반복되는 메시지다.

## 루프란 무엇이고, 왜 굳이 분류하나

Claude Code 팀은 루프를 "정지 조건이 충족될 때까지 작업 사이클을 반복하는 에이전트"로 정의한다. 그리고 루프를 볼 때 네 가지를 묻는다: **어떻게 트리거되는가, 어떻게 정지되는가, 어떤 Claude Code primitive를 쓰는가, 어떤 작업에 가장 잘 맞는가.** 이 격자가 있으면 "이 작업에 어떤 루프를 걸어야 하나"가 취향 문제가 아니라 판단 가능한 문제가 된다.

먼저 못 박아두는 전제가 있다. 복잡한 루프가 항상 필요한 건 아니라는 것. 단순한 해법을 우선 쓰고, 패턴은 선택적으로 얹으라는 얘기다. 이건 뒤에 나올 토큰 관리 원칙과 그대로 연결된다.

### Turn-based — 검증을 위임한다

가장 기본형이다. **사용자 프롬프트로 트리거**되고, Claude가 작업 완료를 판단하거나 추가 맥락이 필요할 때 **정지**한다. 정기 스케줄에 속하지 않는 짧은 작업에 맞는다. 사실 우리가 매번 던지는 프롬프트 하나하나가 이미 수동 루프인데, 팀은 이걸 "agentic loop"라 부른다 — Claude가 맥락 수집 → 액션 → 확인 → (필요 시) 반복 → 응답을 한 턴 안에서 돈다. "like 버튼 만들어줘"라고 하면 코드 읽고, 편집하고, 테스트 돌린 뒤 결과를 반환하고, 그다음은 사람이 확인하고 다음 프롬프트를 쓰는 식이다.

여기서 턴 수를 줄이는 지렛대가 **검증의 skill화**다. 사람이 손으로 하던 확인 절차를 `SKILL.md`에 인코딩하면 Claude가 스스로 확인하는 범위가 넓어진다. 글에 나온 `verify-frontend-change` 예시가 구체적이다 — UI 변경을 "완료" 선언하기 전에 엔드투엔드로 검증하라는 규칙이다:

- 편집이 성공했다는 것만으로 완료 보고 금지, 사람 리뷰어처럼 검증한다.
- dev 서버를 띄우고 편집한 페이지를 브라우저로 연다.
- 바꾼 요소를 직접 조작(버튼·입력·토글 클릭)하고 상태 변화와 전후 스크린샷을 확인한다.
- 브라우저 콘솔에 신규 에러·경고가 0인지 본다.
- Chrome Devtools MCP로 성능 트레이스를 돌리고 Core Web Vitals를 감사한다.
- 어느 단계든 실패하면 고친 뒤 1단계부터 재실행하고, "부분 검증" 상태로 반환하지 않는다.

정량적으로 확인 가능한 작업일수록 자체 검증이 쉬워진다는 점, 그리고 결과를 측정하거나 조작할 도구·커넥터가 붙어 있어야 한다는 점이 전제다.

### Goal-based (`/goal`) — 정지 조건을 위임한다

실시간 수동 프롬프트로 트리거되지만, **목표 달성 또는 최대 턴 수 도달 시 정지**한다. 검증 가능한 종료 기준이 있는 작업에 맞는다. 한 턴으로 부족한 복잡한 작업에서 에이전트는 반복(iterate)할수록 성능이 오르는데, `/goal`로 완료 상태를 정의해두면 Claude가 "이만하면 됐지" 하고 조기 종료하지 않는다. 정지를 시도할 때마다 **evaluator 모델**이 조건 충족 여부를 확인하고, 목표에 닿거나 지정 턴 수에 도달할 때까지 재작업한다.

핵심은 **결정론적 기준**과 **명시적 턴 상한**이다. 통과 테스트 수, 특정 점수 임계치 같은 것. 그리고 "5회 시도 후 정지" 같은 상한을 반드시 건다. 예시가 이 조합을 잘 보여준다:

> `/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries.`

목표(90점)와 상한(5회)이 둘 다 박혀 있어서, 못 넘기면 무한히 도는 게 아니라 5회에서 멈춘다.

### Time-based (`/loop`, `/schedule`) — 트리거를 위임한다

**지정된 시간 간격으로 트리거**되고, 사용자 취소나 작업 완료(PR 병합, 큐 비움) 시 정지한다. 작업 내용은 동일하고 입력만 바뀌는 반복 작업, 또는 외부 시스템과의 인터페이스에 맞는다. "매일 아침 Slack 메시지 요약" 같은 것, 혹은 리뷰·CI 실패가 발생하는 PR을 간격마다 확인하고 반응하는 것.

`/loop`은 프롬프트를 간격마다 재실행한다:

> `/loop 5m check my PR, address review comments, and fix failing CI`

중요한 실무 포인트 하나 — `/loop`은 **내 컴퓨터에서** 돌기 때문에 세션을 종료하면 멈춘다. 계속 돌아가야 하는 routine이면 `/schedule`로 만들어 클라우드로 옮길 수 있다. 관리 요령은 간격을 너무 짧게 잡지 말고, 가능하면 시간이 아니라 **이벤트 기반**으로 반응하게 하는 것이다.

### Proactive — 프롬프트 자체를 위임한다

**이벤트나 스케줄로 트리거**되고 실시간 사람 개입이 없다. 개별 작업은 목표 달성 시 끝나지만, routine 자체는 사용자가 끌 때까지 산다. 버그 리포트 처리, 이슈 분류, 마이그레이션, 의존성 업그레이드처럼 잘 정의된 반복 흐름에 맞는다.

비용 관리의 핵심은 **모델 라우팅**이다 — routine은 더 작고 빠른 모델로 돌리고, 판단이 필요한 지점에만 가장 강력한 모델을 쓴다. 여러 primitive에 auto mode, dynamic workflows(research preview)를 조합해 장기 실행 루프를 짠다. 글에 나온 통합 프롬프트 예시가 이 조합의 끝판이다:

> `/schedule every hour: check the project-feedback channel for bug reports. /goal: don't stop until every report found this run is triaged, actioned, and responded to. When fixing a bug, use a workflow to explore three solutions in parallel worktrees and have a judge adversarially review them.`

`/schedule`이 트리거를, `/goal`이 정지 조건을, dynamic workflows가 병렬 탐색과 적대적 심판을 맡는다. 네 유형이 하나의 파이프라인으로 합쳐지는 그림이다.

## 루프를 지탱하는 두 시스템: 코드 품질과 토큰

글이 반복해서 강조하는 건 "루프 출력 품질은 주변 시스템에 좌우된다"는 것이다. 즉, 프롬프트를 아무리 잘 짜도 시스템 설계가 나쁘면 결과가 안 나온다.

**코드 품질** 쪽 원칙: 코드베이스를 청결하게 유지하면 Claude가 기존 패턴·컨벤션을 따라간다. 팀 기준의 "좋은 상태"를 skill로 인코딩해 자체 검증 수단을 준다. 프레임워크·라이브러리 문서를 접근하기 쉽게 둔다. 그리고 **리뷰는 새 맥락의 second agent**에게 맡긴다 — 메인 에이전트의 추론에 오염되지 않아 편향이 적기 때문이다(내장 `/code-review` skill이나 GitHub용 Code Review). 결정적으로, 개별 결과가 기준에 못 미치면 그 이슈만 땜질하지 말고 **시스템 자체를 개선하도록 인코딩**하라는 것.

**토큰 관리** 원칙: (1) 작은 작업에 다중 에이전트·루프를 남발하지 말고 적합한 primitive·모델을 고른다. (2) 성공·정지 기준을 구체화해 조기 도달을 막는다. (3) dynamic workflows는 수백 개 에이전트를 만들 수 있으니 대규모 실행 전 작은 범위로 파일럿한다. (4) 결정론적 작업은 추론시키지 말고 스크립트를 실행한다(예: PDF skill이 폼 채우기 스크립트를 제공해 매번 코드를 재생성하지 않음). (5) 감시 대상의 변경 빈도에 간격을 맞춰 routine을 과잉 실행하지 않는다. (6) `/usage`(skills·subagents·MCP별), 인자 없는 `/goal`(현재 턴 수·토큰), `/workflows`(에이전트별 토큰, 중지 가능)로 사용량을 계측한다.

## 왜 중요한가

이 글의 진짜 가치는 새 기능 소개가 아니라 **분류 격자**다. 그동안 "에이전트를 자동화한다"는 말은 뭉뚱그려져 있었는데, 여기서는 "무엇을 위임하는가"로 축을 잡는다 — 검증(Turn-based), 정지 조건(Goal-based), 트리거(Time-based), 프롬프트(Proactive). 자기 워크플로를 이 축에 대보면 "지금 내가 어디까지 위임했고, 다음에 뭘 위임할 수 있는가"가 선명해진다.

또 하나, "프롬프트를 잘 쓰는 것"에서 "프롬프트하는 시스템을 설계하는 것"으로 무게중심이 옮겨간다는 점이다. `verify-frontend-change` skill이나 evaluator 모델, second-agent 리뷰가 다 그 얘기다 — 좋은 결과는 좋은 한 방의 프롬프트가 아니라 검증·정지·리뷰가 인코딩된 시스템에서 나온다. 반대로, 무한 루프와 토큰 폭발이라는 실질적 리스크도 같은 자리에서 나오기 때문에 정지 기준·모델 라우팅·파일럿이 선택이 아니라 필수로 붙는다.

## 어떻게 써먹나

글이 제시하는 시작법이 간단하다. **이미 하는 작업 중 본인이 병목인 것 하나**를 골라 위임 가능한 부분을 판단하는 것이다. 세 가지 질문으로 유형이 갈린다:

- **검증 체크를 작성할 수 있는가?** → Turn-based. 손으로 하던 확인 절차를 `SKILL.md`로 인코딩해 Claude의 자체 확인 범위를 넓힌다.
- **목표가 충분히 명확한가(테스트 통과 수·점수 임계치 등 결정론적으로)?** → Goal-based. `/goal ... , stop after N tries`로 완료 상태와 상한을 함께 박는다.
- **작업이 스케줄로 도착하는가?** → Time-based/Proactive. 로컬이면 `/loop`, 계속 돌려야 하면 `/schedule`로 클라우드 routine화하고, 판단 지점만 강한 모델로 라우팅한다.

권장 순서는 "가장 단순한 해법 → 병목 하나 위임 → 루프 실행 후 정체·과잉 실행 지점 관찰 → 반복 개선"이다. 처음부터 Proactive 풀오토를 짜지 말고, 검증 skill 하나 붙이는 것부터 시작해도 이미 루프 엔지니어링의 출발점이다.
