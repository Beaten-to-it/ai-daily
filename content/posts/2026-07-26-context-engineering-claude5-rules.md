## TL;DR

- Anthropic이 Claude Opus 5·Fable 5 같은 신세대 모델용으로 **Claude Code 시스템 프롬프트의 80% 이상을 삭제**했는데도 코딩 평가 점수에 측정 가능한 손실이 없었다. 모델의 판단력이 좋아지면서 예전의 방어용 규칙 뭉치가 오히려 짐이 됐다는 얘기다.
- 규칙(rule)→판단(judgement), 예시(examples)→인터페이스 설계, 전부 앞에 몰아넣기→점진적 공개(progressive disclosure), 반복→간결한 툴 설명, CLAUDE.md 수동 메모→자동 메모리, 단순 스펙→풍부한 레퍼런스. 과거 베스트 프랙티스 6개가 통째로 뒤집혔다.
- 실무 처방은 "덜어내기"다. CLAUDE.md는 가볍게 두고 토큰 대부분을 코드베이스의 함정(gotcha)에 쓰고, 검증·리뷰 같은 조건부 지침은 스킬로 빼서 필요할 때만 부르라는 것. `claude doctor`(`/doctor`) 명령이 이 다이어트를 자동으로 도와준다.

## 무슨 글인가

Anthropic의 Thariq Shihipar가 2026년 7월 24일 올린 글이다. 핵심 주장은 단순하고 도발적이다. **모델이 똑똑해지면 프롬프트/컨텍스트는 더 짧아져야 한다.**

먼저 용어 정리부터. 우리가 Claude에 메시지를 보낼 때 실제로 모델이 받는 것은 우리가 친 프롬프트 한 줄이 전부가 아니다. 시스템 프롬프트, Skills, CLAUDE.md 파일, 메모리 등 여러 소스에서 조립된 컨텍스트가 함께 들어간다. 이 컨텍스트를 어떻게 구성하느냐가 결과 품질을 크게 좌우하는데, 이걸 다루는 일이 '컨텍스트 엔지니어링'이다.

프롬프트와 컨텍스트의 결정적 차이는 **일반성**이다. 프롬프트는 지금 이 요청에만 쓰이니 구체적이어도 된다. 반면 컨텍스트는 수많은 요청에 두루 적용되므로 그만큼 구체적일 수 없다. 사용자가 다음에 뭘 물을지 모르는 상태에서 범용 가이드를 짜야 하고, 게다가 모델 능력이 계속 진화하니 어제 맞던 가이드가 오늘 틀리게 된다. 여기서 이번 글의 관찰이 나온다.

## 핵심: 과잉 제약(overconstraining)을 걷어내기

Anthropic이 자기네 Claude Code 내부 사용 트랜스크립트를 뜯어보니, 한 번의 요청 안에서 서로 충돌하는 지시가 겹겹이 쌓여 있었다고 한다. 시스템 프롬프트는 "코멘트 달지 마(DO NOT add comments)"라고 하는데, 스킬은 "적절히 문서화해라"라고 하고, 사용자 요청은 또 다른 걸 원한다. 대개 Claude는 사용자 의도를 읽어 정답에 도달하지만, 이 겹치고 충돌하는 메시지들을 먼저 정리하느라 불필요하게 더 많이 생각해야 했다.

저자의 진단은 이렇다. 이 제약들은 **한때는 필요했다**. 구세대 모델에서 가드레일을 빼면 최악의 시나리오(파일 삭제 같은)가 나오거나 코멘트를 엉뚱하게 다는 일이 잦았고, 그래서 "많은 경우 지침이 틀리게 되는" 트레이드오프를 감수하면서라도 강한 규칙을 박아 넣었다. 그런데 신세대 모델은 판단력이 좋아져서 명시적 규칙 없이도 주변 맥락과 판단으로 이런 결정을 잘 처리한다. 그래서 상당수를 지울 수 있었다는 것이다. 저자는 이걸 "Claude 족쇄 풀기(unhobbling)"라고 부른다.

또 하나의 배경은 도구가 늘었다는 점이다. 예전엔 CLAUDE.md가 메모리·정보·가이드의 단일 소스였지만, 이제는 memory, artifacts, skills가 생겨서 세션 간 컨텍스트를 싣고 나르는 방법이 다양해졌다. 한 파일에 다 욱여넣을 이유가 사라진 것이다.

## Then / Now — 뒤집힌 6가지 통념

글의 알맹이는 "예전엔 이랬는데 이젠 이렇다" 6쌍이다.

**1) 규칙을 줘라 → 판단하게 두라.** 예전 시스템 프롬프트는 "기본은 코멘트 없음. 여러 문단짜리 docstring이나 여러 줄 주석 블록은 절대 쓰지 마 — 한 줄 짧게. 사용자가 요청하지 않으면 기획·결정·분석 문서를 만들지 마" 식이었다. 하지만 어떤 프롬프트에선 이게 틀린다. 사용자가 문서화를 선호할 수도, 아주 복잡한 코드 일부엔 여러 줄 주석 블록이 필요할 수도 있다. 새 시스템 프롬프트는 규칙 대신 원칙을 준다. **"주변 코드처럼 읽히는 코드를 써라 — 코멘트 밀도, 네이밍, 관용구를 주변에 맞춰라."** 절대 명령 대신 상황 판단의 기준을 준 셈이다.

**2) 예시를 줘라 → 인터페이스를 설계하라.** 예전 툴 사용의 1번 규칙은 "사용법 예시를 줘라"였다. 그런데 신세대 모델에선 예시가 오히려 탐색 공간을 특정 방향으로 **가둔다**는 걸 발견했다. 예시 대신 툴·스크립트·파일의 **설계** 자체를 고민하라는 것 — 어떤 파라미터를 주고 그걸 얼마나 표현력 있게 만들 수 있는가. Todo 툴을 보면, status를 `pending`/`in_progress`/`completed` 열거형으로 두는 것만으로 사용법이 암시되고, "한 번에 하나만 in_progress로 유지"라는 제약이 원하는 동작을 정의한다. 잘 설계된 시그니처가 예시를 대체한다.

**3) 전부 앞에 몰아넣어라 → 점진적 공개.** Claude Code가 코딩 중심이라 시스템 프롬프트엔 코드 리뷰·검증 방법이 상세히 들어 있었다. 늘 필요하진 않지만 필요할 땐 결정적인 정보다. 이제 Claude Code는 '적시 로딩'을 잘하게 됐다. 검증과 코드 리뷰를 **별도 스킬로 분리**해 필요할 때만 부른다. 툴도 마찬가지로 일부는 '지연 로딩(deferred loading)'이라, 에이전트가 쓰기 전에 `ToolSearch`로 전체 정의를 찾아야 한다. 덕분에 Task 툴처럼 많은 툴을 두되 쓰기 전엔 컨텍스트를 잡아먹지 않게 한다. 우리 CLAUDE.md·Skill.md에도 같은 원리를 적용하라는 것. "Claude가 못 찾을까 봐 모든 관행을 한 파일에 다 넣어라"는 통념 대신, **적시에 로드되는 파일 트리**를 만들라고 한다.

**4) 반복해라 → 간결한 툴 설명.** 구세대 모델은 지시를 반복해줘야 하거나, 컨텍스트 시작보다 끝쪽 지시를 더 잘 따르는 경향이 있었다. 그래서 시스템 프롬프트에 툴 참조를 넣고 툴 설명에도 또 넣는 중복이 생겼다. 이제 이런 중복 예시를 지우고, 툴 사용법은 시스템 프롬프트가 아니라 **툴 설명(tool description)에** 두면 된다.

**5) CLAUDE.md에 메모리 → 자동 메모리.** 예전엔 `#` 핫키로 CLAUDE.md에 자동 기록해 저장하라고 권했다. 이제는 Claude가 작업과 사용자에게 관련된 메모리를 **알아서 저장**한다.

**6) 단순 스펙 → 풍부한 레퍼런스.** 플랜 모드에서 Claude Code는 마크다운 플랜 파일에 크게 의존했고, 스펙을 코드베이스에 저장해 긴 프로젝트 내내 참조하게 하는 것도 정석이었다. 그런데 Claude가 점점 더 복잡한 레퍼런스를 다룰 수 있게 됐다. 단순 마크다운 대신 아티팩트 기능으로 만든 **HTML 아티팩트**를 참조하거나, **코드 자체**를 레퍼런스로 줄 수 있다. 스펙이 상세한 **테스트 스위트**일 수도, 포팅할 다른 코드베이스의 함수일 수도 있다. **루브릭(rubric)**도 레퍼런스의 한 형태로, "좋은 API 설계란 무엇인가" 같은 취향을 동적 워크플로와 검증 에이전트를 띄워 확인하게 해준다.

## 그래서 내 컨텍스트에 어떻게 적용하나

저자가 컴포넌트별로 정리한 처방:

- **시스템 프롬프트**: 제품 맥락에 강하게 묶인다. "지금 어떤 제품 안에서 무슨 일을 하는가"를 알려준다. Claude Code 사용자라면 건드릴 일이 거의 없지만, **자체 에이전트 하네스를 만든다면 여기에 시간을 많이 쏟아라.**
- **CLAUDE.md**: 가볍게 유지하라. 레포가 뭐 하는 곳인지 짧게 쓰고, 토큰 대부분은 **코드베이스 안의 함정(gotcha)**에 써라(예: "타입은 이 단일 파일에만 있고 다른 데엔 없다"). 파일 시스템이나 레포만 봐도 알 수 있는 **뻔한 것**은 적지 마라. 점진적 공개를 적극 써서, 검증 방법 같은 지침이 여럿이면 검증 스킬로 만들어 CLAUDE.md에서 참조하라.
- **Skills**: 필요할 때 정보를 찾게 해주는 가벼운 가이드로 생각하라. 아주 중요한 영역이 아닌 한 과잉 제약을 피하라. 긴 스킬은 여러 파일로 쪼개 점진적 공개를 최대한 활용하라. 스킬은 **너·팀·제품 고유의 의견·지식·베스트 프랙티스**를 담을 때 가장 좋다.
- **References**: `@`로 파일을 멘션해 참조로 넣을 수 있다. 가능하면 **코드 파일을 선호하라** — Claude가 아주 잘 아는 언어로 된 명확·고정밀 지시가 되기 때문이다. 예컨대 디자인은 설명이나 스크린샷보다 **HTML 목업**이 더 나은 결과를 낸다.

마지막으로 "그냥 단순화해봐라"라고 권하며, 시스템 프롬프트·스킬·CLAUDE.md 전반을 자동으로 정리해주는 새 명령 `claude doctor`(Claude Code 안에서 `/doctor`)를 소개한다.

## 왜 중요한가

지난 2년간 축적된 프롬프트 엔지니어링 '상식'의 상당 부분이 특정 세대 모델의 약점을 메우려던 임시방편이었음을, 만든 쪽에서 공식화한 글이다. "예시를 많이 줘라", "중요한 건 반복해라", "규칙을 강하게 박아라", "CLAUDE.md에 다 넣어라" — 이 모든 게 신세대 모델에선 **역효과**라는 실증적 주장이고, 근거로 자기네 시스템 프롬프트 80% 삭제 + 코딩 평가 무손실을 든다.

실무자 입장에서 이건 유지보수 비용의 방향을 바꾼다. 그동안 우리는 프롬프트/설정을 **더하는** 쪽으로 최적화해왔다. 문제가 생기면 규칙을 하나 더 붙이는 식이다. 이 글은 그 축적된 규칙 더미 자체가 이제 **충돌·과잉 제약이라는 부채**가 됐다고 말한다. 특히 CLAUDE.md·룰셋을 오래 굴려온 팀일수록, "우리 설정에 서로 싸우는 지시가 몇 개나 되나"를 한 번 점검할 때가 됐다.

## 어떻게 써먹나

- **충돌 감사부터**: 시스템 프롬프트·CLAUDE.md·스킬에서 서로 어긋나는 지시("문서화해라" vs "주석 금지")를 찾아 제거하거나, 절대 명령을 판단 기준으로 바꿔라("절대 X 하지 마" → "주변 코드에 맞춰라").
- **CLAUDE.md 다이어트**: 뻔한 정보(디렉터리 구조, 명령어 등 레포만 봐도 아는 것)를 빼고, 토큰을 함정·비직관적 제약에 재배치하라. 조건부 지침(검증 절차 등)은 스킬로 분리해 참조만 남겨라.
- **예시 대신 시그니처**: 자체 툴을 만든다면 사용 예시를 나열하기 전에 파라미터 이름·열거형·제약이 사용법을 스스로 설명하게 설계하라.
- **레퍼런스를 코드로**: 디자인은 스크린샷 설명보다 HTML 목업, 스펙은 산문보다 테스트 스위트/포팅 대상 함수로 주는 편이 고정밀이다.
- **자동 점검**: Claude Code 사용자라면 `/doctor`로 현재 스킬·CLAUDE.md의 군살을 자동 진단해보라.

한 가지 유의점. 이 글은 자기네 최신 모델(Opus 5·Fable 5 세대)을 전제로 한 관찰이다. 구세대 모델을 여전히 쓰거나, 파일 삭제 같은 최악 시나리오를 막아야 하는 고위험 영역이라면, 저자도 "아주 중요한 영역은 예외"라고 못 박았듯 방어용 제약을 성급히 걷어내지 말 것. "덜어내라"는 원칙이되, 무엇을 덜어낼지는 여전히 판단의 몫이다.
