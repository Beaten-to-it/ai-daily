## TL;DR

- Ghostty·Zig·Tenacity 같은 일부 유명 오픈소스가 GitHub를 떠나거나 읽기 전용 미러만 남겼다. 방아쇠는 하나가 아니라 **잦은 장애**(2025년 5월부터 1년간 major outage 48건·다운타임 112시간), ICE 관련 **20만 달러 계약** 논란, 그리고 "AI를 받아들이든지 이 바닥을 떠나라"는 CEO 발언으로 대표되는 **AI 강제 통합**에 대한 반발이 겹친 결과다.
- 대안 생태계는 이미 실사용 가능한 수준이다. Codeberg(독일 비영리, Forgejo 기반), GitLab·Gitea·Forgejo 셀프호스팅, 이메일 워크플로의 Sourcehut까지 있고, `act runner`나 Apple 러너로 CI/CD까지 자립한 사람들이 "한 번 세팅하면 손 갈 일이 거의 없다"고 증언한다.
- 다만 "대탈출"이라는 프레임은 걸러 들어야 한다. 6억 개가 넘는 저장소 중 손에 꼽는 프로젝트일 뿐이고, Ghostty조차 발표 후 수개월째 실제 이전 계획이 안 보인다. 상당수가 **무료 GitHub Actions 크레딧** 때문에 남아 있다. 진짜 신호는 숫자가 아니라 GitHub 평판이 무너졌다는 **추세**다.

## 무슨 일이 벌어지고 있나

howtogeek 기사를 GeekNews가 정리한 이 글의 요지는 간단하다. GitHub는 2025년에도 저장소 6억 개, 커밋 거의 10억 건, "매초 신규 가입자 1명"이라는 압도적 지표를 가진 부동의 1위 플랫폼이다. 그런데 그 안에서 일부 오픈소스 프로젝트가 조용히, 혹은 요란하게 짐을 싸기 시작했다는 것이다.

떠난(혹은 떠나는) 명단이 상징적이다.

- **Ghostty** — 크로스플랫폼 터미널 에뮬레이터. 유지관리자 Mitchell Hashimoto가 2026년 4월 이탈을 발표했다. 즉시 옮기는 게 아니라 GitHub 의존성을 점진적으로 걷어내고 현재 URL에는 읽기 전용 미러를 남기는 방식이다.
- **Zig** — "C의 정신적 후계자"를 표방하는 시스템 언어. 2015년 첫 커밋 이래 GitHub에서 무탈하게 굴러왔지만 2025년 11월 이탈을 선언하고 Codeberg를 택했다.
- **Tenacity** — 오디오 편집기. 2023년 이전을 알렸고 지금 GitHub엔 미러만 있다.
- 여기에 **Dillo**(웹 브라우저), **Hare**(언어)가 합류했고, **GNOME·Apache**의 상당수 소프트웨어는 애초에 GitHub를 안 쓰고 처음부터 자체 호스팅을 골랐다. Linux 커널도 GitHub엔 읽기 전용 미러만 있고 본진은 따로 있다는 점을 이 글은 상기시킨다.

## 떠나는 이유는 하나가 아니다

기사가 꼽는 원인은 세 갈래다.

**첫째, 장애.** 가장 반복적으로 나오는 기술적 불만이다. IncidentHub 집계로 2025년 5월부터 1년간 GitHub의 "major outages"가 48건, 누적 다운타임이 112시간이었다. HN 댓글에서 한 사람은 "회사에서 뭔가 느리거나 내려갈 때마다 GitHub 농담이 나온다"고 했다. 예전엔 서비스가 너무 좋아서 이념적으로 강하게 동기부여된 사람 말고는 떠날 이유가 없었는데, 지금은 그 반대라는 얘기다.

**둘째, 정치.** Zig 창시자 Andrew Kelley는 GitHub와 미국 이민 단속 기관(ICE)의 관계를 문제 삼았다. GitHub의 ICE 관련 20만 달러 계약은 2019년에도 직원들의 비판을 받은 사안이다. Microsoft 인수 이후 이런 방향성 논란이 더 민감해졌다는 진단이 붙는다.

**셋째, AI.** GitHub는 Copilot 통합을 계속 확대해 왔고, 2025년 CEO Thomas Dohmke는 "Either you embrace AI, or get out of this career(AI를 받아들이든지, 아니면 이 커리어에서 나가라)"라고 말했다. Hashimoto는 GitHub가 더 이상 "일하기 즐거운 장소가 아니고, 작업과 배포를 방해하는 곳처럼 느껴진다"고 했다. 참고로 GNU 진영은 이탈 이전에 아예 GitHub를 이념적으로 거부해 왔다 — 웹 UI가 자유 소프트웨어가 아닌 JavaScript를 요구하고 "나쁜 라이선스 관행"을 조장한다는 이유다.

## 대안은 이미 준비돼 있다

이 글이 유용한 지점은 대안 목록이 추상적 구호가 아니라 실사용 후기와 함께 나온다는 것이다.

- **Codeberg** — Zig가 고른 곳. 이슈 추적·정적 페이지·CI/CD를 제공하고, 뒤에서 도는 소프트웨어가 **Forgejo**다. 독일 비영리가 운영해서 "OpenAI식으로 갑자기 방향을 트는" 리스크가 낮다는 게 지지자들의 논리다. 단, 자유·오픈소스 프로젝트만 받는다.
- **GitLab** — 셀프호스팅의 대표주자. 한 댓글은 800명 넘는 사용자를 몇 년째 GitLab Omnibus로 운영 중인데 "1년에 한두 번 개입이 필요한 업데이트가 있을 뿐 매우 안정적"이라고 했다.
- **Gitea / Forgejo** — 가볍고 단순한 셀프호스팅. 한 사용자는 Gitea를 직접 호스팅하며 Docker·NPM 레지스트리로 쓰고, GitHub Actions 대신 `act runner`를 돌리고, 전부 tailnet 안에 넣어 두고 "필요한 게 다 들어 있다"고 만족했다. Forgejo 쪽에서는 자기 Mac에서 **Apple 러너**를 돌려 무료 GitHub Actions 크레딧을 다른 데 쓰게 된 걸 최대 이득으로 꼽았다.
- **Sourcehut** — 완전 오픈소스. 이메일 기반 워크플로가 특징이고 자체 포지 운영도 가능하다.
- 이탈을 돕는 **Give Up GitHub** 캠페인(Software Freedom Conservancy)도 있다.

버전 관리 도구 자체를 두고도 얘기가 오간다. Git이 워낙 깊게 자리 잡아 대안이 안 나온다는 아쉬움 속에서 **pijul**, **jj**(LFS 미지원이 아쉽지만 유망), 큰 파일 처리에 특화된 **Oxen**(Git LFS 대안) 같은 이름이 언급됐다.

## 판단: 걸러 들어야 할 부분

이 글의 미덕은 반대 목소리를 같이 실었다는 데 있다. 개발자·창업자라면 이 균형을 그대로 챙기는 게 낫다.

- **"Why X does Y" 프레임 경계.** 한 HN 댓글은 이런 제목이 "X가 Y를 한다"는 전제를 증명 없이 참인 척한다고 지적했다. "개발자들이 떠난다"고 해놓고 실제로는 수십만 저장소 중 의미 있는 몇 개만 나열한다는 것이다. `일부`라는 단어를 끼워 넣으면 맞는 문장이 된다.
- **Ghostty 사례의 온도차.** 발표 후 두 달 반이 지나도록 어디로 옮길지, 뭘 할지 논의조차 없다는 비판이 있었다. 선언과 실행은 다르다.
- **경제적 접착제.** 여러 프로젝트가 남아 있는 이유가 무료 GitHub Actions 크레딧이라는 증언이 나왔다. 떠나면 CI/CD 비용을 감당하기 어렵다는 뜻으로, "GitHub가 돈을 주고 붙잡지 않았다면 이탈 숫자는 더 컸을 것"이라는 해석이다.
- **대안도 완벽하진 않다.** Codeberg가 올해 초 스크래퍼(LLM 학습용 크롤러)를 막으려고 사람으로 확신되지 않는 방문자에게 저장소 대신 무작위 텍스트/봇 검증(Anubis류)을 보여주기 시작했는데, 이걸 두고 "좋은 싸움"이라 반기는 쪽과 "결국 GitHub로 돌아갔다"는 쪽이 갈렸다. AI 스크래퍼로 인한 부하는 GitLab 셀프호스팅 운영자에게도 "현재 가장 큰 문제"였다.

## 왜 중요한가

핵심은 이탈 규모가 아니라 방향이다. 예전의 GitHub는 이념적 이유가 아니면 떠날 까닭이 없을 만큼 좋았고, 그래서 위협받은 적이 없었다. 한 댓글의 표현처럼 "평판은 매우 가치 있는 자산인데 GitHub는 몇 달 만에 훌륭했던 평판을 망가뜨렸다." 소수의 상징적 프로젝트가 실제로 짐을 싸고, 나머지 다수가 "무료 크레딧만 아니면 나도 떠날 텐데"라고 말하기 시작했다는 것 — 그게 뉴스가 되는 이유다. 개발 인프라의 사실상 표준이 "당연히 여기"에서 "굳이 여기일 필요가 있나"로 미세하게 이동하는 순간이고, 그 이동을 뒷받침할 대안(Codeberg·Forgejo·GitLab·셀프호스팅)이 이미 실사용 수준까지 성숙했다는 점이 겹친다.

## 어떻게 써먹나

- **탈GitHub를 검토 중이라면 "전면 이주"부터 하지 마라.** 후기들의 공통 패턴은 *전체 미러링 → 많이 쓰는 것부터 전환 → GitHub는 발견 가능성·백업용으로 유지*다. Gitea/Forgejo에 미러를 두고, 공개 프로젝트만 GitHub에 병행 푸시하는 워크플로가 현실적이다.
- **CI 비용이 발목이라면** GitHub Actions를 그대로 버리지 말고 `act runner`나 셀프 러너(예: 자체 Mac의 Apple 러너)로 무거운 잡을 옮겨 무료 크레딧을 아끼는 하이브리드가 실전 검증됐다.
- **호스팅 서비스를 원하면 Codeberg**, **가볍게 직접 굴리려면 Forgejo**, **규모·권한 관리가 필요하면 GitLab**이 무난한 출발점이다. 단 Codeberg는 FOSS 프로젝트만, 그리고 봇 차단 정책이 있다는 점을 미리 감안하라.
- **비공개 코드**는 WireGuard/tailnet 뒤 셀프호스팅이 보안 계층을 하나 더 얹어 준다는 게 다수 의견이다.
- **큰 바이너리**가 문제라면 Git LFS 대신 Oxen 같은 대안을 후보에 올려라.
