에이전트를 여러 개 굴리다 보면 결국 부딪히는 문제가 있다. 이 녀석들이 호출하는 API가 수십 개인데, 그때마다 진짜 API 키를 에이전트 코드나 환경변수에 박아 넣게 된다. 에이전트가 하나 늘 때마다 키 사본이 하나 더 생기고, 로그로 새고, 프롬프트 인젝션으로 유출될 표면이 넓어진다. OneCLI는 이 지점을 겨냥한 오픈소스 프로젝트다.

## TL;DR

- **에이전트에겐 가짜 키만 준다.** OneCLI는 AI 에이전트와 외부 서비스 사이에 놓이는 크리덴셜 게이트웨이로, 실제 키는 한 번만 저장해 두고 에이전트에는 플레이스홀더(`FAKE_KEY`)를 준다. 요청이 게이트웨이를 지날 때 진짜 키(`REAL_KEY`)로 바꿔치기해 주입하며, 에이전트는 실제 시크릿을 끝까지 보지 못한다.
- **Rust 게이트웨이 + Next.js 대시보드 + AES-256-GCM 시크릿 스토어** 구성. 시크릿은 저장 시 암호화되고 요청 시점에만 복호화되며, 호스트·경로 패턴으로 매칭해 헤더나 URL 쿼리로 주입된다. HTTPS는 MITM 가로채기로 처리하고, Bitwarden 같은 볼트도 연동한다.
- Apache-2.0 라이선스, 스타 약 2.6k. `curl | sh` 한 줄 또는 docker compose로 로컬 실행. 다만 **모든 실제 키와 복호화 키를 한곳에 쥔 게이트웨이 자체가 단일 고가치 표적**이 된다는 구조적 트레이드오프가 따른다.

## OneCLI가 하는 일

핵심 아이디어는 "저장은 한 번, 주입은 어디서나, 에이전트는 키를 절대 못 봄"이다. 사용자는 진짜 API 크리덴셜을 OneCLI에 한 번 저장하고, 에이전트에게는 `FAKE_KEY` 같은 가짜 값을 건넨다. 에이전트가 게이트웨이를 통해 HTTP 호출을 날리면, 게이트웨이가 그 요청을 알맞은 크리덴셜에 매칭시켜 가짜 키를 진짜 키로 교체하고, 복호화한 뒤 아웃바운드 요청에 끼워 넣는다. 에이전트 입장에서는 그냥 평범한 HTTP 호출을 한 것뿐이고, 키 교체는 전부 게이트웨이가 처리한다.

만든 이유도 분명하다. 에이전트마다 원본 크리덴셜을 쥐여주는 것 자체가 보안 리스크이므로, 인증을 한곳으로 모아 **접근 관리·키 로테이션·에이전트별 사용 감사**를 한 지점에서 하겠다는 것이다. 시크릿을 코드 곳곳에 뿌리는 대신 게이트웨이라는 좁은 목으로 몰아넣는 셈이다.

### 아키텍처

- **Rust 게이트웨이**: 아웃바운드 요청을 가로채 크리덴셜을 주입하는 빠른 HTTP 게이트웨이. 에이전트는 `Proxy-Authorization` 헤더에 액세스 토큰을 실어 인증한다. HTTPS 트래픽은 MITM 가로채기로 다룬다.
- **웹 대시보드**: 에이전트·시크릿·권한을 관리하는 Next.js 앱. 게이트웨이가 "이 요청엔 어떤 크리덴셜을 넣어야 하는가"를 판단할 때 쓰는 API를 제공한다.
- **시크릿 스토어**: AES-256-GCM으로 암호화해 저장하고 요청 시점에만 복호화한다. 호스트·경로 패턴으로 매칭해 헤더 또는 URL 쿼리 파라미터로 주입한다.

프로젝트 구조상 `apps/web`은 대시보드+API(포트 10254), `apps/gateway`는 Rust 크리덴셜 주입 게이트웨이(포트 10255)로 나뉘고, DB는 Prisma ORM(PostgreSQL)을 쓴다.

### 실행과 인증 모드

가장 빠른 길은 `curl -fsSL https://onecli.sh/install | sh`로, 앱과 PostgreSQL을 한 번에 띄운다. 수동으로는 리포를 클론해 `docker compose ... up -d --wait`로 올린다. 이후 `localhost:10254`에서 에이전트를 만들고 시크릿을 등록한 뒤, 에이전트의 HTTP 게이트웨이를 `localhost:10255`로 가리키면 된다.

인증은 두 모드다. 로컬은 로그인 없는 **싱글유저 모드**(별도 `.env`나 `NEXTAUTH_SECRET` 불필요)로 돌고, 팀 단위로 쓰려면 `NEXTAUTH_SECRET`과 구글 OAuth 자격증명을 넣어 **멀티유저 모드**로 전환한다. 에이전트마다 스코프가 지정된 자기 액세스 토큰을 갖는다. 암호화 키(`SECRET_ENCRYPTION_KEY`)는 지정하지 않으면 자동 생성된다.

## 왜 중요한가

에이전트 시대의 "키 흩뿌리기(key sprawl)" 문제를 정면으로 다룬다는 점에서 의미가 있다. 기존에도 HashiCorp Vault, Doppler 같은 시크릿 매니저는 있었지만, 그것들은 대개 애플리케이션이 "키를 받아 와서 직접 들고 호출"하는 모델이다. OneCLI는 한 발 더 나가 **키가 애플리케이션(에이전트) 프로세스에 아예 도달하지 않게** 만든다. 에이전트가 탈취되거나 프롬프트 인젝션으로 조종당해도, 그 프로세스 메모리엔 진짜 키가 없다는 게 핵심 방어 가치다. 인젝션으로 시크릿을 뱉게 만드는 공격 표면 자체가 줄어든다.

동시에 냉정히 볼 트레이드오프도 있다.

- **게이트웨이가 단일 고가치 표적이 된다.** 모든 실제 키와 이를 복호화하는 능력이 이 한 프로세스에 모인다. 게이트웨이가 뚫리면 분산돼 있던 리스크가 한 번에 실현된다. "여러 곳의 작은 노출"을 "한 곳의 치명적 노출"과 맞바꾼 것이므로, 그 한 곳을 지키는 운영 역량이 전제다.
- **HTTPS MITM은 CA 신뢰를 요구한다.** 게이트웨이가 TLS를 종단하고 안을 들여다봐야 키를 갈아끼울 수 있다. 곧 에이전트가 게이트웨이의 CA를 신뢰하도록 세팅해야 하고, 이는 그 자체로 신뢰 앵커를 하나 심는 일이다.
- **저장 시 암호화의 실효는 키 보관 위치에 달렸다.** `SECRET_ENCRYPTION_KEY`가 자동 생성된다면, 그 키가 암호문과 같은 호스트에 있을 때 at-rest 암호화의 방어 가치는 제한적이다. 프로덕션에선 이 키를 어디에 두느냐가 실제 보안 수준을 가른다.
- **`curl | sh` 설치와 출처 확인.** 편의성은 좋지만, 진짜 크리덴셜을 맡길 도구인 만큼 설치 스크립트·이미지 출처를 손으로 검증한 뒤 올리는 게 원칙이다.

즉, 이 프로젝트는 "에이전트에서 키를 없앤다"는 확실한 이득을, "게이트웨이 한 점에 신뢰를 집중한다"는 비용과 교환한다. 그 교환이 유리한지는 운영 환경에 달렸다.

## 어떻게 써먹나

- **로컬 에이전트 실험**이라면 싱글유저 모드로 5분 안에 붙여볼 수 있다. `curl | sh` 또는 docker compose로 올리고, 대시보드에서 에이전트를 하나 만든 뒤 시크릿을 등록하고, 에이전트의 HTTP 클라이언트가 `localhost:10255`를 프록시로 타게 한 다음 코드에는 `FAKE_KEY`만 넣어 두면 된다.
- **여러 에이전트를 굴리는 팀**이라면 멀티유저(구글 OAuth) 모드로 에이전트별 스코프 토큰을 발급해, 어떤 에이전트가 어떤 API에 접근하는지 한곳에서 관리·감사하고 키 로테이션을 중앙화할 수 있다.
- **이미 Bitwarden 같은 볼트를 쓰고 있다면** 볼트 연동으로 서버에 시크릿을 상주시키지 않고 필요 시점에 온디맨드로 주입하는 구성을 검토할 만하다.
- 다만 프로덕션 투입 전엔 위 트레이드오프(암호화 키 보관 위치, 게이트웨이 격리·모니터링, CA 신뢰 범위)를 설계에 명시적으로 넣는 것을 권한다.
