## TL;DR

- VHK는 코딩 에이전트가 아니라 **어떤 에이전트 위에든 얹는 CLI 하네스**로, 규칙·스펙·증거·기억을 repo 안에 고정해 모델을 통째로 갈아타도 흩어지지 않게 한다.
- 핵심은 **증거 게이트**다 — `receipt`가 tsc·test·build 종료코드 같은 기계 증거로 "다 됐다"는 거짓 완료를 잡는다(판정에 LLM을 안 쓴다).
- MIT 라이선스 1인 프로젝트로 v2.9.0까지 왔고, `RULES.md` 하나로 8개 툴 규칙 파일을 동기화하며 한국어 자연어 라우팅을 지원한다.

## 무엇인가

바이브코딩을 오래 하면 도구를 자주 갈아탄다. Claude Code로 시작했다가 Cursor로, 다시 Codex로. 그때마다 두 가지가 반복된다. 첫째, 규칙 파일과 맥락이 도구마다 흩어진다(`.cursorrules`, `CLAUDE.md`, `copilot-instructions`가 제각각 논다). 둘째, 에이전트는 "다 끝냈다"고 보고하는데 실제로는 테스트조차 돌지 않은 경우가 잦다.

VHK(제작자 byh3071)는 이 두 통증을 겨냥한 CLI 하네스다. 중요한 구분: **VHK는 코딩 에이전트가 아니다.** 코드를 대신 짜주는 물건이 아니라, 네가 쓰는 에이전트가 무엇이든 그 위에 얹혀서 규칙·스펙·증거·기억을 repo 안에 파일로 못박아 두는 층이다. 모델을 통째로 교체해도 이 파일들은 repo에 그대로 남으므로, 도구를 바꾸는 비용이 "맥락을 처음부터 다시 세팅하는 비용"으로 번지지 않는다.

기능은 네 갈래다.

- **규칙 동기화.** `RULES.md` 하나만 관리하면 `.cursorrules`, `CLAUDE.md`, `copilot-instructions` 등 8개 툴의 규칙 파일을 자동으로 맞춰준다. 규칙의 단일 출처(single source of truth)를 두고 나머지를 파생시키는 구조다.
- **증거 게이트.** `verify` / `review` / `receipt` / `preflight` 네 개의 관문이 있다. 이 중 `receipt`가 설계의 핵심으로, `tsc`·test·build의 **종료코드 같은 기계 증거**로 거짓 완료를 판정한다. 제작자가 명시한 대로 이 판정에는 LLM을 쓰지 않는다 — 즉 "된 것 같다"는 모델의 자기보고가 아니라 프로세스 종료코드라는 결정적 신호로 통과 여부를 가른다.
- **자가 진화.** 세션마다 쌓인 교훈을 `memory`/`pattern`에 모아 규칙 후보로 승격시킨다. 쓸수록 그 프로젝트에 맞게 규칙이 다듬어진다는 주장이다.
- **풀사이클.** 아이디어 검증 → 개발·검증 → 배포 후 콘텐츠·운영·판매 초안까지 명령으로 이어진다. 단, 실제 게시와 결제는 사람이 한다고 못박았다.

여기에 한국어 자연어 라우팅이 붙는다. `vhk 저장해줘`, `vhk 출고점검` 같은 한국어 명령을 인식한다. 제작자는 1인 프로젝트라 한국어가 우선이고 영문 문서는 아직 따라오는 중이라고 솔직히 밝혔다.

설치는 `npm i -g @byh3071/vhk`. 저장소는 GitHub `byh3071-cpu/vhk`(MIT 라이선스, MCP 35 tools, Node 22+), 현재 버전 v2.9.0.

## 왜 중요한가

가장 눈에 띄는 설계 판단은 **"거짓 완료 판정에서 LLM을 배제"**한 대목이다. 에이전트가 "다 됐다"고 말하는 것과 빌드가 실제로 통과하는 것은 다른 사건인데, 많은 하네스가 이 판정마저 또 다른 LLM에게 맡긴다. VHK는 종료코드라는 결정적 층에 게이트를 두어 이 문제를 우회한다 — 채점자(측정자)를 조종간(모델)과 분리한 셈이고, 이건 프롬프트로 강제할 수 없는 종류의 신뢰다.

두 번째는 **"에이전트를 대체하지 않는다"**는 포지셔닝이다. 코딩 능력 자체는 프런티어 모델에 맡기고, 모델이 잘 못 하는 반복·기억·게이트만 repo 층에서 잡는다. 이 분리 덕에 도구 교체가 규칙·증거·기억의 손실로 이어지지 않는 것이 핵심 가치 제안이다. 함께 언급된 harness-starter-kit·re_gent·Framein 등과 같은 "에이전트 아래 레이어" 흐름의 한 갈래로 볼 수 있다.

## 어떻게 써먹나

- 여러 코딩 도구를 오가며 규칙 파일이 계속 어긋난다면, `RULES.md` 단일 출처 + 자동 동기화가 직접적인 처방이다.
- 에이전트의 "완료" 보고를 신뢰하지 못해 매번 손으로 테스트를 돌려 확인한다면, `receipt` 게이트로 종료코드 기반 확인을 워크플로에 박아둘 수 있다.
- Node 22+ 환경에서 `npm i -g @byh3071/vhk`로 설치해 소규모 repo에 얹어보고, 게이트가 실제 CI 신호와 어긋나지 않는지부터 확인하는 게 안전한 도입 순서다.
