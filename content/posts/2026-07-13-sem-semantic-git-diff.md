Git은 지금도 세상을 **줄(line) 단위**로 본다. `git diff`는 "23~41번째 줄이 바뀌었다"고 말해줄 뿐, "`parseConfig` 함수가 수정됐고 `loadDefaults`는 이름만 바뀌었다"는 식으로는 말해주지 않는다. `sem`(Ataraxy-Labs)은 이 층위를 한 칸 끌어올린다. 줄이 아니라 **코드 엔티티**(함수·메서드·클래스)를 비교해서, 무엇이 추가·수정·삭제·이동·이름 변경됐는지를 보여주는 시맨틱 버전 관리 도구다.

## TL;DR

- `sem`은 Git diff를 줄 단위가 아니라 **함수·클래스 엔티티 단위**로 다시 보여준다 — tree-sitter로 파싱하고 엔티티 ID → AST 구조 해시 → 토큰 유사도(80% 초과) 순으로 전후 코드를 이어붙여 **리네임과 이동까지 감지**한다.
- 설정 없이 아무 Git 레포에서 동작하고, 엔티티 캐시는 OS 캐시 디렉터리(SQLite)에 저장돼 **작업 트리를 더럽히지 않는다**. 32개 언어 + JSON/YAML/TOML/CSV/Markdown을 지원하고 미지원 파일은 청크 diff로 폴백한다.
- `diff`·`impact`·`blame`·`log`·`context`뿐 아니라 **MCP 서버**와 **pre-commit 훅**, **PR용 GitHub Action**까지 묶여 있어 사람 리뷰와 코딩 에이전트 양쪽의 워크플로에 바로 꽂힌다.

## 무엇을 하는가

`sem`의 출발점은 diff의 **의미 손실**이다. 리팩터링 한 번이면 수백 줄이 빨강·초록으로 뒤덮이지만, 정작 "이 커밋에서 실제로 달라진 동작이 뭐냐"는 질문엔 사람이 눈으로 diff를 재구성해야 답이 나온다. `sem`은 그 재구성을 도구가 대신한다.

내부 동작은 세 단계로 이해하면 된다. 먼저 tree-sitter로 소스를 파싱해 함수·메서드·클래스를 개별 엔티티로 뽑는다. 그다음 변경 전후 스냅샷의 엔티티를 이어붙일 때, **① 엔티티 ID → ② AST 구조 해시 → ③ 토큰 유사도 80% 초과** 순서로 매칭한다. 이 매칭 사슬이 핵심인데, 이름이 바뀌어도(ID는 달라졌지만 구조/토큰이 같으면) "삭제 후 추가"가 아니라 **리네임**으로, 파일 간에 옮겨진 함수도 **이동**으로 판정할 수 있다. 줄 단위 diff가 구조적으로 표현하지 못하는 바로 그 두 가지다.

엔지니어링 측면에서 눈여겨볼 결정은 **캐시를 저장소 바깥에 두는 것**이다. 엔티티 캐시는 SQLite로 OS 캐시 디렉터리에 보관되어 워킹 트리에 `.sem/` 같은 흔적을 남기지 않는다. `.gitignore`를 건드릴 필요도, 동료의 diff에 도구 부산물이 섞일 일도 없다. 게다가 Git 밖에서도 **임의의 두 파일 비교**가 가능해서, 버전 관리에 올라가 있지 않은 파일에도 같은 엔티티 diff를 적용할 수 있다.

지원 명령은 용도별로 잘 갈라져 있다.

- **`sem diff`** — 작업 트리/스테이징/특정 커밋/커밋 범위/임의의 두 파일을 비교. 일반 텍스트·Markdown·JSON 출력을 지원해 사람이 읽든 파이프라인이 먹든 대응된다.
- **`sem impact`** — 특정 함수를 바꿨을 때 영향받는 의존 코드·호출자·테스트를 찾아준다. "이거 고치면 어디가 깨지지?"에 대한 정적 답.
- **`sem blame`** — `git blame`을 엔티티 층위로. 함수/클래스/메서드의 **마지막 수정자**를 알려준다.
- **`sem log`** — 한 엔티티가 git history를 거치며 어떻게 변해왔는지 추적한다. 엔티티를 지정하지 않으면 저장소의 **hotspot**(자주 바뀌는 것)과 **co-change pair**(반복적으로 함께 바뀌는 쌍)를 분석한다. "이거 건드리면 저것도 잊지 말라"는 암묵적 결합을 데이터로 드러내는 셈이다.
- **`sem entities`** — 현재 폴더 아래 모든 엔티티를 나열.
- **`sem context`** — 에이전트에 필요한 주변 코드만 **토큰 예산에 맞춰** 구성해준다.

언어 커버리지는 TypeScript·Python·Go·Rust·Java·Swift·SQL·C/C++ 등 32개 언어에 JSON/YAML/TOML/CSV/Markdown까지. 파서가 없는 파일은 청크 단위 diff로 떨어지므로, 지원 밖 파일이 섞여도 전체가 무력화되진 않는다. 라이선스는 MIT OR Apache-2.0로 상업 채택 장벽이 낮다.

## 왜 중요한가

`sem`이 겨냥하는 진짜 소비자는 사람만이 아니라 **코딩 에이전트**다. LLM 에이전트에게 코드베이스를 이해시킬 때 가장 비싼 비용은 "필요한 조각을 찾느라 파일을 통째로 읽어 토큰을 태우는 것"인데, `sem`은 그 조각을 함수·의존 관계 단위로 미리 잘라준다. `sem mcp`는 `diff`·`impact`·`context`·`entities`·`blame`·`log`를 그대로 **MCP 도구**로 노출해, 에이전트가 전체 파일 대신 필요한 함수와 그 호출 관계만 조회하게 만든다. 컨텍스트 윈도가 아무리 커져도 "관련된 것만 넣는" 게 항상 이기는 전략이라는 점에서, 이건 에이전트 시대의 diff 형태에 가깝다.

사람 리뷰 쪽 이득도 구체적이다. 줄 diff는 "포맷만 바꿨는지, 로직을 바꿨는지"를 리뷰어가 직접 판별해야 하지만, 엔티티 diff는 그 구분을 도구가 해준다. 특히 PR용 GitHub Action은 **포맷/주석만 바뀐 PR도 구분**해서, 대량 리포맷 커밋에 실제 로직 변경이 숨는 리뷰의 고질병을 줄여준다.

## 어떻게 써먹나

셋업은 `sem setup` 한 방이 출발점이다. 실행하면 기존 `git diff`가 엔티티 단위 출력으로 바뀌고, **staged 변경의 영향 범위를 보여주는 pre-commit 훅**이 설치된다. 커밋 직전에 "이 스테이징이 어떤 함수의 호출자·테스트를 건드리는지"를 자동으로 경고받는 구조라, `sem impact`를 사람이 매번 부르지 않아도 된다. macOS·Linux에서는 여기에 더해 **Claude Code에 상주 의존 그래프와 프롬프트 시작 시 컨텍스트 훅**을 연결해, 에이전트가 매 프롬프트마다 저장소를 재분석하는 비용을 없앤다.

팀 워크플로에는 두 지점을 추천한다. ① **PR 게이트** — GitHub Action을 붙이면 PR마다 변경된 함수/클래스/메서드를 **하나의 고정 댓글로 갱신**해준다(매번 새 댓글이 쌓이지 않는다). ② **에이전트 브리지** — 코딩 에이전트를 쓰는 팀이라면 `sem mcp`로 붙여 에이전트의 코드 탐색을 파일 통독에서 엔티티 조회로 바꾼다. 캐시가 레포 밖에 있고 설정이 사실상 없다는 점 덕에, 우선 로컬에서 `sem diff`·`sem log`(hotspot·co-change) 정도만 돌려보며 자기 코드베이스의 결합 구조를 관찰하는 것부터 시작해도 부담이 적다.
