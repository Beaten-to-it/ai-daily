Addy Osmani가 정리한 "에이전트 자율성 수준" 논의를 개발자·창업자 관점에서 다시 풀어본다. 요지는 단순하다. **자율성은 자랑거리가 아니라 위험·되돌림 가능성에 맞춰 보정(calibrate)하는 운영 변수**라는 것.

## TL;DR
- 에이전트 자율성은 한 줄 사다리가 아니라 **agency(한 에이전트를 사람에게서 얼마나 멀리 보내나)** × **orchestration(여러 에이전트를 얼마나 조율하나)** 두 축으로 봐야 하고, 이를 겹쳐 0~5단계(Assist → Supervised action → Scoped task → Goal-driven → Parallel → Managed-by-exception)로 읽는다.
- Anthropic의 Claude Code 분석(2025-10~2026-04, 약 23.5만 명·약 40만 세션)에서 **사람이 계획 결정의 약 70%, Claude가 실행의 약 80%**를 맡았다 — "높은 자율성"은 사람을 루프에서 빼는 게 아니라, 매 스텝 실행자에서 다음 방향을 정하는 자로 역할을 옮기는 것이다.
- 성숙한 팀의 자세는 자율성 과시가 아니라 **calibrated autonomy** — 실행 전 "계약"(목표·범위·비목표·권한·정지조건·증거·에스컬레이션·예산)을 박고, 자율성 수준을 작업 이름이 아니라 **검증 프로세스**에 맞춰 올린다.

## 왜 한 축 사다리가 깨지는가

에이전트형 엔지니어링의 무게중심이 **프롬프트 작성에서 운영 설계**로 넘어갔다. 소프트웨어 팩토리, 목표(goal), 루프, 백그라운드 세션, 서브에이전트, 훅, 샌드박스, 그리고 에이전트가 에이전트를 승인하는 구조가 전면에 나온다. Claude Code와 Codex가 그 변화를 보여주는 대표 제품으로 다뤄진다.

Steve Yegge의 "Welcome to Gas Town"에서 나온 단일 축 사다리는 **한 에이전트에 대한 신뢰를 숫자 하나로** 표현하는 데 유용하다. 2026년 초까지는 작업이 위임에서 오케스트레이션으로 넘어가는 상황에서도 이 단일 축이 위험의 대략적 대리 지표로 작동했다. 문제는 여러 에이전트를 동시에 돌릴 수 있게 되면서 생긴다. 단일 단계 숫자로는 "다중 에이전트 역량"을 설명할 수 없다.

원문이 짚는 핵심은, 자율성 논의가 **서로 다른 두 질문을 습관적으로 섞는다**는 점이다. (1) 단일 에이전트를 사람에게서 얼마나 멀리 보낼 수 있나, (2) 여러 에이전트를 얼마나 잘 조율하나. 이 둘을 떼어내려면 두 축이 필요하다.

- **agency**: 한 에이전트가 제안·제한된 작업·목표 달성을 얼마나 자율적으로 하나. 낮으면 후보 행동을 제안하고 사람 결정을 기다리고, 중간이면 범위를 제한한 채 증거와 함께 계속 보고하며, 높으면 실험·학습·테스트·차단 처리·질문·다른 접근 시도까지 하고 이를 **증거로** 되돌린다.
- **orchestration**: 하나의 스레드에서 시작해 여러 작업 트리, 나아가 백로그·이슈 트래커·스케줄 기반 지속 작업까지 얼마나 조율하나. 낮으면 에이전트 하나·스레드 하나, 중간이면 각자 분리된 worktree에서 다른 목표를 도는 여러 에이전트, 높으면 오케스트레이터가 큐를 지속 작업으로 바꾸고 사람은 실패 시에만 개입하는 management by exception이다.

## 세 시대, 여섯 단계

여섯 단계를 아래에서 위로 읽으면 두 축을 함께 끌어올리는 것처럼 보이고, 세 개의 시대로 묶인다. ① 사람이 운전석에 있고 에이전트가 보조하는 시대, ② 에이전트가 제한된 작업·목표를 맡되 사람이 조정·검증하는 시대, ③ 시스템이 여러 에이전트에 작업을 배분하고 사람은 문제 생길 때 개입하는 오케스트레이션 시대. 실무에선 하루 동안 이 단계들을 오가는 게 자연스럽다.

- **Level 0 — Assist**: 제안은 좋고 때론 완벽하지만 실행은 항상 사람이 결정. 자동완성·인라인 편집·아직 아무도 소유 안 한 변경을 채팅에서 논의하는 상황. 비용 큰 오류, 아주 작은 변경, 판단을 형성 중일 때 적합. 검증은 대체로 로컬.
- **Level 1 — Supervised action**: 에이전트가 대신 편집·명령 실행하되 중요한 실행 전 허가를 요청. 대부분의 기본 자세. 각 승인이 곧 독립 검증이다. **주된 실패 모드는 승인 피로** — 무엇을 승인하든 다 비슷하게 느껴진다. Codex의 Auto-review는 경계 조건의 최종 승인을 별도 리뷰어 에이전트에 위임해 이 문제를 친다.
- **Level 2 — Scoped task delegation**: 명확한 목표·제약·완료 정의를 가진 제한된 작업을 넘김. 사람은 가까이서 중단할 수 있지만 대부분 손 떼고 있음. 검증이 **사람 직접 확인에서 에이전트가 만들 수 있는 증거**(통과한 자동 테스트, 타입, 린트, 스크린샷, 재현 절차, 예시 기반 출처)로 이동. 소프트웨어 엔지니어링의 중심에 가까운 단계.
- **Level 3 — Goal-driven autonomy**: 조건이 충족될 때까지 목표 달성에 필요한 일을 수행. Codex의 Goal mode는 plan→act→test→review를 반복하다 성공 기준을 못 맞추면 멈추고, Claude Code는 `/goal`·`/loop`·`/schedule`이 여기 해당. **정지 조건이 자동화 가능하게 측정 가능해야** 쓸모 있다. "사용자 경험 개선" 같은 모호한 목표는 부적합하고, "명시적 `any` 없는 엄격한 TypeScript 빌드 보장"처럼 구체·측정·자동화 가능해야 한다. 프로덕션 버그를 찾으려면 에이전트가 프로덕션 유사 환경에 있어야 한다.
- **Level 4 — Parallel delegation**: 여러 에이전트가 작업의 분리된 조각을 병렬로. **최대 병목은 분해(decomposition)**, 최대 실패 모드는 **거짓 병렬성** — 겹치는 조각을 동시에 건드리면 더 많은 작업 대신 merge conflict와 중복 결정만 는다. 에이전트를 격리(각자 소유 파일·상태·리뷰 큐)해야 하고, 토큰 비용은 동시 실행 수에 비례하며, 어느 지점부터는 오케스트레이션 세금 때문에 에이전트 추가의 한계 비용이 오른다.
- **Level 5 — Managed-by-exception orchestration**: 사람은 성공 정의와 정책만 정하고, manager agent가 트리거(새 이슈·작업·시계)에 깨어나 작업자 에이전트를 배치·모니터·검증·재시도하고, 조건 되면 더 유능한 에이전트나 사람에게 에스컬레이션한 뒤 PR 같은 산출물과 증거를 외부 시스템에 반환. **팩토리** 비유(입력=이슈 트래커/백로그, 출력=해결된 이슈들). OpenAI는 Linear 보드를 중심에 둔 Symphony spec을 제안했고, 각 이슈가 자체 에이전트 workspace와 spec 파일을 갖는다. 이 단계에선 **독립 검증**(구현자/리뷰어 분리, 테스트 실행자/QA 분리, 보안 검사 분리, 수락용 프로세스 게이트 분리)이 더 중요해진다.

원문이 던지는 실전 감별 질문이 좋다. 사람이 넘기는 일로 계속 바쁜 단일 에이전트는 **대시보드 붙은 Level 4**에 가깝고, 자동 접수·재시도가 있고 충분한 증거 없이는 진행 안 하는 보수적 에이전트는 **실제 게이트가 있는 Level 5**에 가깝다. 즉 단계는 라벨이 아니라 검증 구조가 결정한다.

## 실행 전 "계약"과 지표

원문의 실무 핵심은 여기다. **모든 에이전트 실행 전에 계약을 박아라.** 포함 항목: 목표(활동/기법이 아니라 결과), 범위(도메인·허용 기법), 비목표(포함하지 않을 것), 도구·권한, 정지 조건(가능하면 측정 가능한 변수), 증거(완료를 독립 확인할 테스트·스크린샷·로그·DB 레코드), 에스컬레이션(누가 언제 개입/실행), 예산(시간·노력·토큰, 시도 횟수·병렬성 한도 포함).

그리고 지표를 **사전에** 간결한 문서로 배치하면 자율성이 더 신뢰 가능해진다(사후에 붙이는 것만으론 부족). 추적할 만한 예시: 개입 간 평균 시간, 수락 작업 기준 최장 무인 실행 시간, 샌드박스 실행 vs 에스컬레이션 비율, 자동 승인 vs 거절 비율, 사람 지시 하나당 에이전트 행동 수, 명확화 요청률·중단 요청률, 수락 변경당 리뷰 시간, 신뢰 수준별 재작업률·결함 유출률, 수락 변경당 토큰 비용.

"큰 AI 시스템이 실제로 높은 자율성으로 도는가"를 판별하는 세 질문도 명쾌하다. **무엇을 잘못하는지 얼마나 빨리 아나 / 하고 있는 일을 얼마나 깔끔하게 되돌리나 / 그게 옳다는 걸 무엇이 증명하나.** 답이 "빨리 못 알고, 되돌리기 어렵고, 요약을 믿어야 한다"라면 그건 높은 자율성이 아니라 그냥 방치다.

## 네 가지 안티패턴

- **Autonomy as status**: 자율성 등급이 무의미한 지위 배지가 되어, 검증이 못 받치는 수준으로 에이전트를 돌림. → 옳은 수준을 고르고 선 안 넘는 사람을 칭찬·보상하라.
- **Permission laundering**: 승인 피로 때문에 필요 이상으로 넓은 권한을 부여. → 샌드박스 프로필, 범위 제한 쓰기 루트, 허용 명령 목록, 훅, Auto-review로 경계를 강화.
- **Summary substitution**: 에이전트의 작업 요약이 리뷰를 대체. → 수동 리뷰와 같은 증거 패킷(diff·테스트·로그·스크린샷·리뷰어 발견·위험·빈틈)을 묶어라.
- **Fleet cosplay**: 수십 개를 병렬로 돌리지만 사람이 모든 의존성을 계속 수동 조율. → 공유 상태·소유권 규칙·의존성 추적을 넣고, 더 작은 WIP 제한으로 조율 단계를 문서화·자동화.

## 데이터가 말하는 것

Anthropic의 넓은 분석은 **2025년 10월~2026년 4월, 약 23.5만 명의 약 40만 세션**을 다뤘다. 세션마다 프롬프트당 요청 행동 수, 자동 승인 항목, 중단 빈도 같은 결정을 파악할 수 있었고, 결과는 **사람이 계획 결정의 약 70%, Claude가 실행의 약 80%**를 맡는 양상. Claude Code 관련 연구에선 가장 어려운 작업 일부에서 **Claude가 사용자 중단보다 2배 이상 자주 명확화 질문**을 했고, 경험 많은 사용자(약 750 세션)는 50개 미만 세션 사용자보다 자동 승인과 중단을 더 자주 쓰며 진행을 지켜보는 경향을 보였다.

## 어떻게 써먹나

원문이 제안하는 **보정 연습**이 그대로 실무 체크리스트다. 최근 에이전트 도움을 받은 작업 10개를 꺼내 각각 — 자율성 수준 / 위험 / 되돌림 난이도 / 검증 요건 충족용으로 생성된 증거 / 리뷰 시간 / 재작업 여부 / 다음에도 같은 수준이 적절한지 — 를 적어본다.

올릴 때는 **한 번에 한 축씩**. 시작점은 "방어 가능한 성공 증거를 만드는 하나의 제한된 작업을 도는 단일 supervised agent". 여기서 세 방향으로 점진 확장한다. ① 읽기 중심 탐색을 병렬화, ② 제한된 파일 소유권 규칙을 가진 별도 worktree에 쓰기 에이전트 추가, ③ 반복 자동화를 넣은 뒤 이슈·음성 등에 기반한 에이전트 주도 오케스트레이션 추가. 각 상승은 새 실패 모드(단일 장기 실행의 드리프트·컨텍스트 부패·목표 이탈, 백그라운드의 오래된 가정·약한 인수인계, 과도 병렬의 conflict·중복 결정, 과도 반복의 조용한 토큰 지출, managed-by-exception의 긴 리뷰 큐·알림 피로)에 대응하는 새 안전장치를 요구한다. 대응은 "더 세게 믿기"가 아니라 **범위 좁히기, 더 나은 증거, 더 싼 롤백, 더 강한 게이트, 더 명확한 소유권 규칙**이다.

단계별 적합처를 한 줄로: L0=섬세한 작업·판단 형성 중, L1=잘 이해된 경계 근처의 대부분 탐색, L2=미지의 의존성·돌발 문제가 있는 대부분의 제한된 작업, L3=성공 조건을 충분히 명확히 말할 수 있을 때, L4=성공 조건대로 깔끔히 나눌 수 있을 때, L5=여러 성공 조건 사이 조율·커뮤니케이션이 완전히 인코딩된 뒤.

**한 줄 관전평.** 이 글의 진짜 메시지는 "검증은 계속 병목으로 남는다"이다. 도구와 자신감이 아무리 올라도, 성숙한 팀의 자세는 **calibrated autonomy** — 언제 작업하고 언제 검증하고 언제 질문할지 아는 루프를 설계하는 것이다. 결제 엔진 리팩터링(강한 테스트·리뷰어 에이전트·깔끔한 롤백)이 정답 기준 없는 문서 자동화보다 더 높은 자율성을 지원할 수 있다는 예가 핵심을 압축한다. **위험과 되돌림 가능성이 자율성의 상한을 정한다.** (개인적으로는, 이 프레임이 "그린 테스트를 통과한 AI 구현도 커밋 전 적대 리뷰에서 결함이 나온다"는 실무 경험과 정확히 맞물린다 — Level이 올라갈수록 구현자/리뷰어 분리 같은 독립 검증이 선택이 아니라 게이트가 되는 이유다.)
