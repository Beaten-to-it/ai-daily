LLM 코딩 도구가 실수를 자주 낸다는 지적에 가장 흔히 돌아오는 반론은 이렇다. "그러니까 사람이 전부 리뷰하면 되잖아." 이 글(softwaremaxims.com, 약 1년 전 작성)은 그 반론이 왜 문제를 해결하지 못하는지를, 코드 리뷰에 관한 기존 실증 연구를 근거로 파고든다.

## TL;DR
- 효과적인 코드 리뷰의 실증적 상한은 한 세션 약 1시간·400 LOC다. 이 기준을 LLM 코드에 그대로 적용하면 "전면 검토"는 오류를 걸러주기 전에 먼저 **생산성의 상한선**으로 작동한다.
- 초기 증거는 사람이 LLM 생성 코드에서 결함을 **더 적게** 찾으면서 "다 찾았다"는 **확신은 더 강해진다**고 가리킨다 — 검토만으로 오류가 걸러진다는 보장이 없다는 뜻이다.
- 필요한 건 "내겐 효과가 있었다"는 일화가 아니라 재현 가능한 실증 연구다. LLM 코드의 결함 탐지율·검토 속도·하루 지속 가능량을 직접 측정해야 도구의 실효성을 근거로 판단할 수 있다.

## '인턴' 비유와 전면 검토라는 해법

논의의 출발점은 널리 쓰이는 '인턴' 비유다. LLM 코딩 도구는 환각·오타를 내고, 요청과 무관한 방향으로 작업을 진행하기도 한다. 그래서 사용자는 결과가 어느 정도 틀렸을 것으로 예상하고, 무엇을 하는지 제대로 이해하지 못한 채 일한다고 간주하라고 권한다. 여기서 따라 나오는 대응이 "주니어 코드처럼 숙련된 사람이 전부 리뷰하면 된다"는 것이다. 인간이 더 잘 알고 최종 책임도 지며, 어차피 코드베이스에 들어가는 모든 코드는 원래 리뷰 대상이라는 논리다.

글쓴이가 문제 삼는 건 이 해법 자체의 처리 한계다. 그리고 여기서 '리뷰'가 한 덩어리가 아니라는 점을 짚는다. 여러 사람에게 분산된 가벼운 리뷰는 변경 지식을 공유하고 표면적 규칙을 적용하는 데는 좋지만, LLM 코드를 감독하는 기준으로는 부족하다. LLM은 복잡한 코드를 만들고 결함은 세부에 숨으므로, 위원회식으로 몇 시간씩 모든 줄을 뜯어볼 필요까지는 없어도 **상당히 깊고 완전한 리뷰**가 요구된다.

## 코드 리뷰의 경험적 한계, 그리고 그 산수

핵심은 코드 리뷰에 관해 이미 알려진 실증적 한계다. 효과적인 한 세션은 대략 1시간을 넘기지 않고, 그 시간에 제대로 볼 수 있는 양은 최대 400 LOC 정도다. 1시간을 넘긴 리뷰는 코드 크기와 무관하게 효과가 빠르게 떨어지는데, 단순히 대부분을 이미 봤기 때문이 아니라 높은 집중을 1시간 유지하면 피로가 쌓여 휴식이 필요해지기 때문이다. 세션 사이 회복 시간을 직접 조사한 연구는 못 찾았고, 하루 2회 정도가 제안되긴 하나 확정된 수치는 아니다. 400 LOC/H는 절대 기준은 아니지만, 이보다 빠른 리뷰가 결함을 효과적으로 잡아낸 사례가 실증 데이터에 거의 없어 사실상 실효 최대 속도로 볼 수 있다.

이 한계를 LLM 코드에 대입하면 산수가 나온다. 최선의 경우에도 생성된 400 LOC마다 숙련 개발자 1시간이 필요하다. 개발자가 낼 수 있는 리뷰 세션은 주당 약 10~40회이고, 그 시간은 회의·설계·장애 대응·직접 쓸 코드 사고와도 나눠 써야 한다. 최상의 조건이라면 하루 수천 LOC도 가능하지만, 현실적 시나리오에서는 **일일 처리량이 1,000 LOC 미만**일 수 있다. 여기엔 보일러플레이트·테스트·마이그레이션·설정 파일이 다 포함되고, 테스트 파일 하나만도 400 LOC를 넘길 수 있다. 즉 코드가 아무리 단순하고 검토하기 쉬운 최상의 조건이어도, 리뷰가 곧 생산성 향상의 천장이 된다.

## 인간 코드 리뷰와 LLM 코드 리뷰는 같지 않다

여기서 더 불편한 지점이 나온다. 위 수치들은 전부 **사람이 쓴 코드를 사람이 리뷰**한 상황에서 나온 것이고, 같은 효율이 LLM 코드에도 적용된다는 증거는 없다. 오히려 초기 증거는 반대를 가리킨다. LLM 생성 코드를 검토한 사람은 결함을 더 적게 찾으면서도 "다 찾았다"는 확신은 더 강해지는 경향을 보인다. 그렇다면 (인간 작성자 + 인간 리뷰어) 조합보다 (LLM + 인간 리뷰어) 조합이 더 낮은 품질을 내면서도, 후자의 리뷰어가 자기 성과를 더 높게 평가하는 상황이 가능하다. 전면 리뷰가 생산성 이점을 깎을 뿐 아니라, 빈번한 오류를 실제로 해결한다는 확실한 근거조차 부족하다는 얘기다.

게다가 이 산수엔 아직 **결함을 고치는 비용은 빠져 있다.** 검토하고 문제를 표시하는 비용만 따진 것이다. LLM이 결함을 몇 개 내든, 심지어 아주 높은 품질을 내더라도, "모든 결과를 검토한다"는 조건 아래서는 검토 비용과 생산성 한계가 동일하게 남는다.

글쓴이가 특히 모순으로 꼽는 건, 옹호론이 "사람이 쓰기 고통스러운 코드를 도구가 대신 써준다"를 장점으로 내세운다는 점이다. 한 사례는 앞으로 필요한 Bash 코드의 100%를 LLM에 맡기자고 한다. 그런데 셸 스크립트야말로 파싱이 느슨하고 의미가 과도하게 중첩돼, 구두점 하나 오타가 무해할 수도, 컴퓨터 전체를 날릴 수도 있는 코드다. 오류가 나기 쉽고 검토는 어렵고 치명적 실수는 알아채기 힘들다. 무작위로 틀리는 도구에 가장 검토하기 어려운 코드를 맡긴 뒤 "사람이 확인하면 된다"는 방식은, 그 출력이 정말 효과적으로 검토 가능한 대상인지 먼저 입증하지 못한 채 가장 안 좋은 사례를 대표 유스케이스로 내세우는 셈이다.

## 이 글이 요구하는 건 '증거'다

글의 결론은 도구를 폐기하자는 게 아니다. 저자는 지식재산권·자원 소비 같은 부수 쟁점이나 "결과물이 다 형편없다"는 평가에 초점을 두지 않는다고 명시한다. 문제는 **현재의 과학적 근거만으로는 LLM 도구가 개발자를 더 좋게/빠르게 만든다고 확인하기 어렵다**는 것이고, 옹호론이 이 문제를 정면으로 다루기보다 회의론자를 비정상 취급하는 태도가 더 큰 불만이라는 것이다. TDD·타입 시스템·CI/CD·DevOps 논쟁에서도 실증보다 일화가 우세했던 패턴이 반복돼 왔다.

그래서 저자는 두 가지 실증 과제를 제시한다. 첫째, 인간 리뷰어가 LLM 코드의 결함을 얼마나 잘 찾는지 — 탐지 능력·리뷰 속도·하루 지속량을 인간 코드 연구처럼 재현 가능하게 측정할 것. 둘째, LLM 생성물 리뷰가 인간 작성물 리뷰와 **질적으로 다른 문제**인지 확인할 것. 만약 기존 코드 리뷰 연구가 적용 안 될 만큼 다르다면 이 비판 자체가 무너지지만, 초기 증거는 오히려 LLM 코드 리뷰가 더 어려운 쪽을 가리키고 이 경우 비판은 강화된다.

## 댓글의 반론들 — 여기가 사실 더 흥미롭다

GeekNews/Lobste.rs 토론에는 실무자들의 반박이 길게 붙었는데, 원문 주장 못지않게 읽을 값이 있다(아래는 커뮤니티 의견이며 원문의 주장이 아니다).

- **속도가 유일한 목표는 아니다.** LLM은 개방적 도구라, 예전엔 기술부채 TODO로 남겼을 작업(속성 기반 테스트·퍼징·정형 기법, 잘못된 상태를 못 만들게 하는 타입 구조)을 제대로 구현하는 한계 비용을 크게 낮췄다. 다만 현실의 많은 회사는 이 도구를 '최저 품질 MVP 경쟁'에 쓰고 있어 아쉽다는 자기비판도 함께 나온다.
- **책임 소재가 본질.** PR 작성자가 소유권과 책임을 진다면 LLM 사용 여부는 중요하지 않다. 품질·정확성·일관성 기준을 충족하면 더 빠른 방식을 택하면 되고, 승인 기준이 같으니 AI 코드라고 더/덜 검토할 이유가 없다는 것이다. 코드는 여전히 소프트웨어의 최종 명세이며 사람이 소유·이해해야 한다는 점은 바뀌지 않았다는 지적도 있다.
- **400 LOC/H가 의심스럽다며 직접 계산한 사람도 있다.** 최근 6개월간 PR 173개·변경 13만 9천 줄을 검토했는데, 주 40시간 중 리뷰 비중을 15~25%로 잡으면 시간당 약 540~900줄이 나온다. 실제 처리량을 시간당 500~1,000줄로 추정하며, 출처 없이 제시된 400이라는 수치와 "어느 정도 가깝다"고 본다. (수치 출처 논문이 무엇인지 특정하지 못했다는 점은 원문·댓글 양쪽에서 약점으로 지적된다.)
- **"최근 3~6개월 새 모델이 확 좋아졌다"는 반론엔 재반박이 붙는다.** 그 말 자체가 최소 2년째 반복돼 왔다는 것이다. 그리고 "개인적 경험으론 충분하다"는 태도에 대해, 손 씻기 거부·사혈 옹호가 개인 경험을 근거로 삼았던 역사를 들어 증거 기준이 너무 낮다고 꼬집는다. 상대를 설득할 증거를 요구받자 "나는 이미 확신했으니 더 필요 없다"고 답하는 건 질문에 답한 게 아니라는 것.
- 실제로 최전선 모델이 코드량을 크게 늘려 검토 역량에 새 압박을 준다는 점은 회의론자도 인정한다. 공유 동작을 추출해 재사용할 상황을 못 알아채고 새 코드를 덧붙이는 **아키텍처 실수**, 그리고 그 새 코드가 "대체로 작동해서" 정리 없이 병합되기 쉽다는 위험, "가장 좋은 코드는 코드가 없는 것"인데 줄을 **삭제하자**고 제안하는 음의 기여는 아직 잘 못 본다는 관찰도 나온다.

## 왜 중요한가

이 논쟁은 "AI가 코딩을 잘하냐"의 문제가 아니다. **"사람이 다 리뷰하면 된다"는 안전장치가 실제로 안전한가**의 문제다. 만약 (1) 효과적 리뷰에 구조적 처리 한계가 있고 (2) LLM 코드에서 사람의 탐지력은 떨어지는데 확신은 오른다면, "리뷰로 커버한다"는 팀의 전제는 생산성 상한과 품질 착시를 동시에 안고 가는 셈이다. 특히 리뷰량이 실제 처리 능력을 넘어서도록 방치하면, 통과된 승인은 품질 보증이 아니라 피로 누적의 산물이 된다.

동시에 댓글 쪽 반론도 새겨둘 값이 있다. 결국 논쟁의 무게중심은 "AI냐 아니냐"가 아니라 **동일한 품질 기준·책임 소재를 구조로 강제하고 있는가**, 그리고 우리가 판단의 근거로 삼는 게 일화인가 측정인가로 옮겨간다. 원문의 최대 약점(핵심 수치 400 LOC/H의 출처 논문 미제시)과 최대 강점(확신-탐지 비대칭이라는 반직관적 위험)을 함께 쥐고 봐야 한다.

## 어떻게 써먹나

- **리뷰량을 처리 능력에 맞춰 캡을 걸어라.** "LLM이 뽑았으니 빨리 머지"가 아니라, 팀의 실측 리뷰 처리량(시간당 몇 백 줄)을 넘는 유입은 병목으로 인정하고 흐름을 제한한다. 유입량이 아니라 소화 가능량이 배포 속도를 정한다.
- **확신 착시를 구조로 막아라.** LLM 코드에서 "다 봤다"는 감이 실제 탐지와 어긋날 수 있으니, 감에 기대지 말고 체크리스트·정적 분석·속성 기반 테스트·퍼징처럼 사람의 주의력에 의존하지 않는 검증을 안전장치로 건다. (이는 "이해 못 하는 코드는 운영에 올리지 말고, 검증을 의지가 아니라 하네스로 강제하라"는 원칙과 맞닿는다.)
- **가장 검토하기 어려운 코드(셸·마이그레이션·권한·삭제 경로)는 LLM 전면 위임의 1순위가 아니라 마지막 후보로 둔다.** 오류 확률 × 검토 난이도 × 폭발 반경이 가장 큰 지점이기 때문이다.
- **PR 크기를 리뷰 상한(≈400 LOC/세션)에 맞춰 쪼갠다.** 버그 수정은 준비 커밋으로 분리해 독립 검토하고, 작성자가 인간이든 LLM이든 소유권·책임과 승인 기준을 동일하게 적용한다.
- **판단 근거를 팀 내부 데이터로 승격하라.** "내겐 효과 있었다" 대신, 우리 팀의 리뷰 처리량·결함 유출율·재작업 비용을 측정해 도구 도입 여부를 근거로 결정한다.
