한 보안 연구팀이 GPT5.6 Sol Ultra에게 최신 안정판 WordPress 소스를 던져주고, 인증도 필요 없는 상태에서 원격 코드 실행(RCE)까지 이어지는 공격 체인을 10여 시간 만에 완성시켰다. 사람이 쓴 비용은 토큰값 기준 약 25달러. 흥미로운 건 익스플로잇 자체보다, "무엇을 조사할지 정하는 사람"과 "그걸 실제로 뚫는 모델" 사이의 역할 분담이 어디로 이동하는가다.

## TL;DR

- GPT5.6 Sol Ultra가 최신 안정판 WordPress를 소스 코드만 보고(패치 diff·인터넷 단서 금지) 인증-전 SQL 주입 → 임시 관리자 권한 → 신규 관리자 생성 → 백도어 플러그인 업로드 → RCE로 이어지는 체인을 약 10시간에 완성했다.
- 비용은 월 200달러 구독의 주간 사용량 50%를 비례 계산한 약 25달러. 다만 이 숫자는 보조받은 토큰값일 뿐, 수년치 전문성과 수많은 실패는 빠져 있다는 반론이 함께 붙는다.
- 출발점은 WordPress 5.6의 Batch API 인덱스 불일치 버그이고, 여기에 oEmbed 캐시·customize_changeset·게시물 순환 참조·동적 훅을 연쇄로 엮어 익명 요청 중 관리자 신원을 잠깐 훔쳐 쓰는 게 핵심 트릭이다.

## 무슨 일이 있었나

연구팀은 OpenAI가 Cycle Double Cover 추측 해결에 썼다고 공개한 프롬프트를 보안 연구용으로 손봐서 GPT5.6 Sol Ultra에 물렸다. 실험 조건을 일부러 빡빡하게 잡았다는 점이 눈에 띈다.

- 최신 안정판 WordPress를 `main/`에 복제하고 `.git` 디렉터리는 삭제 — 변경 이력이나 패치 버전과의 diff를 못 보게 막았다.
- 종속 코드를 조사할 수 있도록 빈 `third_party/` 디렉터리를 준비.
- 프롬프트는 최대 4개 에이전트를 병렬로, 최소 6시간 동안 다양한 공격 경로를 유지하도록 지시. 입력 파싱·문자 집합·파일 업로드·오류 처리·직렬화·캐시·경쟁 조건·타입·대량 할당 등 표면을 넓게 훑게 했다.
- 특정 전략으로 에이전트가 몰리면 덜 탐색된 영역으로 재배치하고, 발견한 버그는 적대적 에이전트가 재검증하게 했다.
- 목표를 "MySQL을 쓰는 일반적인 프로덕션 배포에서 인증-전 RCE"로 명시해 비현실적 전제(공격자가 못 맞추는 조건)를 배제했다.

약 6시간 뒤 모델이 인증-전 SQL 주입을 찾아 실제 원격 서버에서 관리자 이메일을 수분 만에 추출·재현했고, RCE 승격을 추가로 요청하자 약 4시간 뒤 비밀번호 크래킹이나 오프라인 계산 없이 읽기 전용 SQL 주입에서 관리자 권한까지 올라가는 체인을 완성했다. 공개 전 주말 동안 운영자에게 업그레이드 시간을 줬고, 그사이 Calif과 Hacktron이 GitHub의 다른 PoC보다 먼저 전체 체인을 독립적으로 재현했다. 운영 인스턴스의 취약 여부는 wp2shell.com에서 확인할 수 있다고 한다.

## 체인이 어떻게 조립됐나

이 익스플로잇의 매력은 단일 버그가 아니라 여러 정상 기능을 조합해 만든다는 데 있다. 순서대로 풀면 이렇다.

**1) Batch API 인덱스 불일치 (WP 5.6).** Batch API는 한 요청으로 여러 가상 API 요청을 처리하는데, 성능을 위해 검증과 실행을 두 반복문으로 분리한다. 첫 반복문에서 모든 요청을 검증·정제하고, 둘째 반복문에서 권한·엔드포인트 콜백을 실행한다. 구현은 라우트 매칭 결과 `$matches`와 검증 결과 `$validation`의 같은 인덱스끼리 대응한다고 가정한다. 그런데 잘못된 요청이 `is_wp_error()` 분기로 들어가면 `$validation`에는 항목이 추가되지만 `continue` 때문에 `$matches`에는 추가되지 않아, 이후 `$matches`가 한 칸씩 밀린다. 결과적으로 **한 요청의 매개변수를 다른 엔드포인트의 검증 규칙으로 통과시킨 뒤, 원래 의도하지 않은 핸들러에서 실행**할 수 있다.

**2) `author__not_in` UNION 주입.** `GET /wp/v2/posts`는 특정 작성자를 제외하려고 내부 변수 `author__not_in`을 쓴다. 값이 배열이면 각 원소에 `absint`를 적용하지만, 스칼라 문자열이면 그대로 `implode`한 뒤 SQL `NOT IN` 절에 넣는다. 정상적으로는 공개 매개변수 `author_exclude`가 정수 배열이어야 하니 문제가 안 드러난다. 하지만 인덱스 불일치로 문자열 `author_exclude`를 이를 인식하지 않는 `DELETE /wp/v2/posts/1` 규칙으로 검증한 뒤 `GET`에 넘기면 주입이 성립한다. Batch가 GET 하위 요청을 막는 제약도 **재귀 Batch 호출**로 우회했다(바깥 Batch에서 method 검증을, 안쪽 Batch에서 `author_exclude` 검증을 각각 건너뜀). `0) OR 1=1 --` 같은 값으로 주입을 확인한 뒤 UNION 기반으로 임의 DB 값을 유출한다. 다만 비밀번호·토큰·API 키는 해시라, 관리자 비번이 약하지 않으면 유출만으로 계정 탈취까지 가진 않는다.

**3) 요청 내 게시물 캐시 조작.** WordPress는 한 요청 안에서 반복 참조되는 `WP_Post`를 메모리 캐시에 둔다. UNION 주입으로 가짜 게시물 행을 반환하면 ID·타입·상태·부모·본문 등을 공격자가 정한 값으로 캐시에 넣을 수 있다. 단 이 캐시는 요청이 끝나면 사라져, 이것만으론 지속성이 없다.

**4) oEmbed 캐시로 DB 행 만들기.** `[embed]` 결과는 `wp_posts`의 `oembed_cache` 타입 게시물로 DB에 저장된다. 상대 경로로 로컬 게시물을 임베드하면 HTTP 요청을 생략하는데, 참조 대상이 실제 존재하는지는 확인하지 않는다. 그래서 존재하지 않는 로컬 게시물을 임베드해도 `oembed_cache` 행이 생긴다. 이 행을 다시 SQL 주입으로 조회하면서 메모리상 타입을 `post` 등으로 바꾸면 DB와 캐시의 표현이 갈라지고, WordPress가 이를 조정하며 `wp_update_post()`를 호출한다. 이때 명시한 ID와 `post_content` 외 필드는 공격자의 메모리 값을 선호한다.

**5) `customize_changeset`으로 임시 관리자.** 테마 사용자 정의 초안은 `customize_changeset` 타입 게시물로 저장되고, `post_content` JSON에 변경값·타입·수행할 사용자 ID가 담긴다. changeset 적용 시 WordPress는 각 항목의 `user_id`를 읽어 `wp_set_current_user()`로 현재 사용자를 바꾼다. 즉 **`user_id: 1`인 changeset을 적용하면 익명 요청 중에도 관리자 신원을 잠깐 쓸 수 있다.** 문제는 악성 changeset JSON을 DB에 남길 별도 경로가 필요하다는 것.

**6) 게시물 부모 순환으로 본문 보존.** WordPress는 자기 자신이나 하위를 부모로 두는 순환을 금지하고, 순환을 발견하면 `post_parent`를 0으로 바꾸는 `wp_update_post()`를 호출한다. 이 호출은 ID와 `post_parent`만 지정하고 `post_content`는 덮지 않는다. 그래서 메모리상 게시물을 자기 자신을 부모로 갖는 `customize_changeset`으로 꾸미면, **순환 복구 과정에서 악성 changeset JSON이 그대로 DB에 기록**된다. 과거 날짜에 상태 `future`인 changeset을 만들면 WordPress가 이를 적용하며 `user_id: 1` 관리자 권한으로 설정을 바꾼다.

**7) 동적 훅으로 요청 전체 재실행.** 게시물 상태가 바뀌면 WordPress는 `"{$new_status}_{$post->post_type}"` 형태의 동적 액션을 실행한다. 메모리의 가짜 게시물은 상태·타입을 임의로 정할 수 있으니 원하는 액션명을 구성할 수 있다. 체인은 상태를 `parse`, 타입을 `request`로 조작해 **`parse_request` 훅**을 호출한다. 이 훅은 요청 생명주기 초반에 도는 것이라, 다시 부르면 원래 Batch 요청 전체가 처음부터 재처리된다. 재처리는 changeset이 만든 임시 관리자 신원이 유지되는 동안 이뤄져, 첫 실행에서 권한 부족으로 실패했던 관리자 전용 요청이 두 번째엔 성공한다.

**8) 두 요청으로 완성.** 최종 익스플로잇은 HTTP 요청 두 개다. 첫 요청은 지속 행(oembed_cache 3개)을 준비하고, 둘째 요청에서 여섯 개의 가짜 게시물(O/C/P/D/S/T — 각각 oembed_cache, self-parent customize_changeset, draft page, parse/request, 임베드 데이터 post, 외부 임베드 post)을 조립한다. 순환 감지가 연쇄로 트리거되며 악성 changeset이 DB에 박히고, 관리자 신원으로 `parse_request`가 재실행되어 Batch에 처음부터 포함돼 있던 **새 관리자 생성 요청**이 이번엔 성공한다. 그 계정으로 로그인해 백도어 플러그인 ZIP을 업로드하면 RCE에 도달한다.

## 왜 중요한가

가장 창의적인 지점은 재귀 Batch로 GET 제한을 우회한 것, 캐시와 changeset을 엮어 익명 상태에서 관리자 권한을 훔친 것, 가짜 게시물로 `parse_request`를 불러 요청을 통째로 재실행한 것이다. 연구팀은 "AI 없이 사람이 같은 체인을 10시간 안에 발견·완성하기는 불가능했을 것"이며, 서로 떨어진 코드 가젯을 하나로 잇는 능력에서 GPT5.6 Sol Ultra가 5.5보다 크게 발전했다고 평가한다. 방어자 입장에선 "여러 정상 기능의 조합으로 만든 체인은 단일 SAST 룰로 안 잡힌다"는 게 뼈아픈 교훈이다.

다만 원문 아래 댓글들은 서사에 상당한 견제를 건다. 이건 신뢰할 수 없는 외부 코멘트이므로 사실이 아니라 **제기된 반론**으로만 옮긴다. (1) 원 제목에 있던 "50만 달러"는 근거가 부족해 삭제됐고, 실제 그 금액이 지급됐다는 확증은 없다. (2) 25달러는 구독으로 보조받은 토큰값일 뿐, 수년치 업계 전문성·축적 자료·수많은 실패는 빠진 계산이라는 "성공 순간만 올리는 인스타그램식 서사" 비판. (3) LLM 출력을 실제 유효한 PoC로 검증·완성하는 데는 여전히 전문성이 필요하며, 그래서 같은 글이 더 일찍 안 나왔다는 지적. (4) 이게 진짜 신규 제로데이인지, 이미 알려진 클래스의 버그인지도 논쟁적이다. 한편 한 댓글은 실제 운영 사이트에서 `author_exclude` UNION 페이로드를 쓴 공격을 이번 주말에 목격했다고도 했다 — 방어 우선순위를 잡는 데 참고할 만하다.

## 어떻게 써먹나

- **WordPress 운영자:** 최신 안정판으로 즉시 업그레이드한다. 이미 재현 PoC가 여러 곳에서 나왔고 야생 공격도 보고됐다. 로그에서 `/wp/v2/posts`·`/wp/v2/widgets`에 대한 `author_exclude=...UNION...` 류 페이로드, 예상치 못한 관리자 계정 신규 생성, `wp-content/plugins`·`mu-plugins`에 정체불명 PHP 파일 유무를 점검한다.
- **개발자:** "검증과 실행을 두 반복문으로 분리하고 인덱스로 매핑"하는 패턴은 한쪽 배열에만 항목이 빠지는 순간 전체가 어긋난다. 병렬 배열 대신 요청 객체에 검증 결과를 직접 매다는 구조를 쓰라. 배열/스칼라 분기에서 스칼라 경로만 sanitize를 건너뛰는 코드는 전형적 주입 진입점이다.
- **보안 연구자·팀:** 이 사례의 실질적 시사점은 "모델이 기술적 익스플로잇 개발을 더 많이 맡을수록, 사람은 어떤 제품·공격 표면을 볼지, 시간을 얼마나 넣을지, 방향이 빗나갈 때 어떻게 교정할지를 정하는 메타-연구로 이동한다"는 것이다. 아직 AI가 잘 못하는 이 층위가 모델 능력이 올라갈수록 더 중요해진다.
