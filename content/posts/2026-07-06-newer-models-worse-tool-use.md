에이전트를 붙여 파는 사람이라면 한 번쯤 겪는 배신이 있다. "이번 모델이 더 똑똑하다"는데, 정작 내 도구 호출은 예전보다 더 자주 깨진다. `lucumr.pocoo.org`에 올라온 이 글은 그 배신을 재현 가능한 사례로 못 박는다. 결론 한 줄로 요약하면 — **모델이 좋아질수록 "내" 도구 스키마는 오히려 불리해질 수 있다.**

## TL;DR
- Pi의 `edit` 도구에서 Claude Opus 4.8·Sonnet 5가 스키마에 없는 가짜 키(`requireUnique`, `oldText2`, `matchCase`, `in_file` 등)를 `edits[]` 객체에 덧붙여 호출이 거부됐다. 이전 Anthropic 모델에선 안 보이던 회귀이고, `oldText`/`newText` 페이로드 자체는 바이트 단위로 정확했다.
- 가장 강한 가설은 무작위 저하가 아니라 **학습 산물**이다. 최신 모델이 Claude Code(평평한 `file_path`/`old_string`/`new_string` 스키마)나 그와 비슷한 하네스에서 강화학습을 받으며, 그 하네스의 관대한 보정에 기대는 습관까지 함께 학습해 다른 스키마가 분포 밖으로 밀려났다는 것.
- Anthropic의 strict(제약 디코딩) 도구 호출을 켜면 문제가 사라진다. 서버가 스키마상 허용되지 않은 키를 아예 샘플링하지 못하게 막기 때문으로 보인다. 하네스에는 프롬프트 예의가 아니라 문법 수준의 강제가 필요하다는 신호다.

## 무슨 일이 일어났나

발단은 Pi라는 에이전트 하네스의 `edit` 도구 이슈 추적이었다. 이 도구는 한 번의 호출로 여러 문자열 치환을 하려고 중첩 배열을 쓴다. 의도된 인자는 이런 모양이다.

```json
{
  "path": "some/file.py",
  "edits": [
    { "oldText": "text to replace", "newText": "replacement text" }
  ]
}
```

그런데 최신 Claude 모델이 이 `edits[]` 배열 안에 **스키마에 없는 필드**를 끼워 넣기 시작했다. 실패한 호출은 대략 이렇게 생겼다.

```json
{ "oldText": "...", "newText": "...", "requireUnique": true }
{ "oldText": "...", "newText": "...", "oldText2": "", "newText2": "" }
```

반복 실험에서 튀어나온 가짜 키의 목록은 다양하다 — `type`, `id`, `kind`, `unique`, `requireUnique`, `matchCase`, `in_file`, `forceMatchCount`, `children`, `notes`, `cost`, `oldText2`, `newText2`, `event.0.additionalProperties`까지. 핵심은 **실제 편집 내용(`oldText`/`newText`)은 정확했다는 것**이다. 모델이 무엇을 고쳐야 하는지는 정확히 알았는데, 객체를 닫는 마지막 순간에 말이 안 되는 키를 붙여 하네스의 검증에서 거부당했다.

작은 모델의 실수가 아니다. Opus 4.8에서 나타났고 Sonnet 5에서도 재현됐다. 반대로 이전 세대 Anthropic 모델에서는 같은 문제가 보이지 않았다. 즉 "더 좋은 모델이 이 특정 도구 스키마에서는 더 나쁘게 동작"한 것이다. (Fable은 분류기가 요청을 조용히 Opus로 낮출 가능성이 있어 테스트에서 제외됐다.)

## 왜 하필 도구 호출에서

글의 관점은 이렇다. LLM의 도구 호출은 마법 같은 함수 콜이 아니라 **텍스트 생성에 가깝다.** 모델은 대화 기록·시스템 프롬프트·도구 목록을 받은 뒤, 특수 마커가 섞인 큰 프롬프트 안에서 호출 형식을 "생성"한다. Anthropic의 내부 포맷은 공개돼 있지 않지만, `<invoke ...>` 류의 ANTML 마커가 유출되거나 공개 소통에 노출된 적이 있다. XML처럼 보이되 실제 XML이라기보다, 토큰화·학습에 편한 인밴드 신호에 가깝다. 최상위 문자열 파라미터는 인라인으로, 객체 배열은 이스케이프된 JSON 직렬화 형태로 들어가는 것으로 보인다.

구조화된 출력을 만드는 방식은 크게 둘이다.

1. **제약 없는 생성 + 사후 검증** — "스키마에 맞는 JSON을 내놔"라고 부탁한 뒤, 나온 결과를 나중에 검사한다.
2. **문법 제약(제약 디코딩)** — 샘플러 단계에서 문법을 위반하는 토큰을 아예 마스킹한다. 스키마가 `oldText`/`newText`만 허용하면 `in_file` 같은 키의 첫 토큰조차 나오지 못한다.

제약이 없으면 모델은 추상 계약(스키마)을 엄밀히 따르기보다 **학습된 관례**를 따라 생성한다. 그리고 이 회귀는 특정 지점에서 집중적으로 터진다. 수백 토큰짜리 `newText` 문자열을 닫은 직후, 모델이 객체를 `}`로 끝낼지 아니면 `, "..."`로 키를 더 붙일지 선택해야 하는 **고엔트로피 분기**다. 이 지점에서 Opus 4.8·Sonnet 5의 강한 사전분포가 스키마를 이긴다.

재현 조건도 시사적이다. "이 파일 고쳐줘" 같은 새 단일 턴 프롬프트에서는 재현되지 않는다. 모델이 파일을 읽고 진단한 뒤 여러 줄 편집을 구성한 **깊은 에이전트 이력**에서만 나온다. Petr Baudis의 실제 트랜스크립트를 이어가면 Opus 4.8이 약 20% 확률로 실패했고, 이력에서 thinking block을 제거하면 실패율이 절반으로 줄었다. 그리고 strict 도구 호출을 켜면 그 실행에서는 문제가 사라졌다.

## 가장 그럴듯한 원인: 하네스에 대한 과적합

글이 미는 가설은 "운 나쁜 성능 저하"가 아니라 **학습 산물**이다.

이전 세대 모델은 일부 도구로 학습됐지만, Claude Code 같은 사용자 하네스가 지배적 목표로 자리 잡기 전이었다. 반면 최신 모델은 Claude Code 또는 그와 매우 유사한 하네스를 포함한 후학습을 거쳤을 가능성이 크다. 문제는 그 환경에서 **성공적인 도구 호출뿐 아니라 "허용되는 실수"까지 함께 학습**했을 수 있다는 점이다.

여기서 Claude Code의 하네스가 얼마나 관대한지가 중요해진다. 축소된 코드를 보면 이 하네스는 들어오는 데이터에 매우 너그럽다.

- 모델의 보이는 텍스트에 `<invoke` 마크업이 새어 나오면 텔레메트리를 찍고 자체 상태 머신으로 재시도한다.
- 문자열 값 안의 깨진 `\uXXXX` 시퀀스·lone surrogate를 고치는 Unicode 복구가 있다.
- 파라미터 별칭을 받아준다. `Edit`은 `old_str`/`old_string`/`new_str`/`new_string`을 모두 받고, `path`를 `file_path`의 별칭으로 받는다.
- 예상치 못한 키는 조용히 필터링한다.
- 그리고 **strict 모드는 쓰지 않는다** (strict 모드가 도구 정의 복잡도 제한을 걸어 API 요청을 실패시킬 수 있어서로 보인다).

강화학습이 이런 관대한 하네스(또는 그 시뮬레이션) 안에서 일어난다면, **약간 틀린 도구 호출도 작업을 완료하고 보상을 받는다.** 그 결과 "정확한 스키마 준수"가 아니라 "관대한 파서가 봐주는 근사한 형태"가 강화된다. Claude Code의 `edit`은 Pi처럼 중첩된 `edits[]`가 아니라 `file_path`/`old_string`/`new_string`/선택적 `replace_all`의 평평한 구조다. 모델의 사전분포는 이 평평한 모양에 가까워지고, 다른 스키마를 제공하는 하네스는 점점 분포 밖으로 밀려난다. Opus 4.5 출시 무렵엔 다른 edit 도구에도 잘 적응했다는 점을 감안하면, 방향성이 있는 회귀로 읽힌다.

참고로 이건 Anthropic만의 이야기는 아니다. 대조군으로 OpenAI의 `gpt-oss`는 harmony 응답 포맷을 쓰도록 명시적으로 학습됐고, 그 포맷은 도구 호출 본문에 제약 경계를 알리는 마커를 넣는다.

```text
<|start|>assistant<|channel|>commentary to=functions.get_weather <|constrain|>json<|message|>{"location":"San Francisco"}<|call|>
```

`<|constrain|>json`은 추론 스택이 도구 호출 본문에서 JSON 제약 샘플링으로 전환할 경계를 쉽게 찾게 해준다. 호스팅 GPT 모델에는 사용자 도구 문법을 위해 LARK 문법을 넘기는 옵션도 있다. 글쓴이가 테스트한 Codex 모델에서는 이런 유형의 회귀가 보이지 않았다(접근 권한이 없는 5.6은 제외). 요는, 제약이 **어디서** 강제되는지가 결과를 가른다는 것이다.

## 왜 중요한가

- **도구 스키마는 중립적인 추상 계약이 아니다.** 어떤 모양은 후학습에서 본 것에 가깝고, 어떤 모양(긴 멀티라인 문자열 뒤 중첩 배열 안의 큰 이스케이프 JSON)은 모델에게 훨씬 어렵게 작동한다. 모델이 스키마를 "이해"하더라도, 압박 상황(깊은 이력·긴 출력)에서는 정확한 구조를 샘플링하는 데 실패할 수 있다.
- **한 하네스가 지배할수록 나머지가 그 기벽을 상속한다.** 후학습이 하나의 지배적 하네스에 몰릴수록, 다른 하네스는 그 하네스의 관대함·별칭·필터링을 전제로 깔아야 한다. "모델이 스키마를 지킨다"는 가정 위에 앱을 올린 사람에게는 조용한 지뢰다.
- **능력과 형식 충실도가 갈라진다.** 최신 모델이 문제 해결력은 좋아지면서 대체 스키마를 충실히 방출하는 능력은 나빠진다면, 그 격차를 메우는 책임은 모델이 아니라 하네스로 넘어온다. Lobste.rs 코멘트에서는 이 영향이 코딩 에이전트를 넘어, "안정적 도구 호출에 의존하는 모든 앱"으로 번질 수 있다는 우려도 나왔다 — 다만 이는 코멘터의 추정이다.

> 참고로 벤더 종속·비용 절감·프롬프트 캐싱 개선을 노린 의도적 설계라는 해석, 그리고 GPT 계열에서 긴 이력 후반에 `ls -la`가 `ls -ლა`로 깨졌다는 일화(openai/codex#7988)는 모두 Lobste.rs **코멘트의 의견·경험담**이다. 글 본문이 확인한 사실과는 구분해서 읽는 게 안전하다.

## 어떻게 써먹나

에이전트나 도구 호출에 의존하는 앱을 만든다면, 이 글은 세 가지 실무 지침으로 압축된다.

1. **가능하면 제약 디코딩/strict를 켜라.** Anthropic strict 모드나 문법 제약(LARK·grammar-aware decoding)이 있으면 이런 부류의 회귀는 근본에서 사라진다. 프롬프트로 "스키마 지켜"라고 부탁하는 건 형식 보장이 아니다 — 강제는 샘플러/파서 레벨에서 걸어야 한다.
2. **커스텀 도구 스키마를 지배적 하네스의 모양에 가깝게 설계하라.** 굳이 중첩 배열 안에 긴 멀티라인 문자열을 이스케이프해 넣게 만들지 말고, 평평하고 단순한 인자(예: `file_path`/`old_string`/`new_string`)를 우선하라. 모델의 사전분포와 싸우지 않는 스키마가 실패율이 낮다.
3. **관대한 보정 레이어를 하네스에 심어라.** Claude Code가 하는 것처럼 — 알 수 없는 키 필터링, 파라미터 별칭 수용, 타입 보정, Unicode 복구, 그리고 검증 실패 시 오류를 되먹여 재시도. strict를 못 켜는 환경이라면 이 방어층이 사실상 유일한 보험이다. 단, strict를 켤 수 있으면 이건 보조 수단이지 대체재가 아니다.
