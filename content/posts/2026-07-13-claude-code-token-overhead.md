## TL;DR

- **바닥값(floor)이 다르다.** Claude Code는 "OK라고만 답해" 같은 한 줄 요청에도 시스템 프롬프트·툴 스키마·주입된 스캐폴딩으로 **약 33,000 토큰**을 프롬프트가 도착하기 전에 먼저 쏜다. OpenCode는 약 7,000. Sonnet 4.5에서 4.7배, 최신 Fable 5에서는 Claude Code가 더 작은 시스템 프롬프트를 보내 3.3배로 좁혀진다. 이 격차의 대부분은 **툴 정의**다.
- **캐시 효율이 결정적으로 갈린다.** OpenCode의 요청 프리픽스는 모든 실행에서 바이트 단위로 동일해 재실행 시 캐시 쓰기가 0에 수렴한다. 반면 Claude Code는 세션 중간에 전체 프리픽스(~43k)를 통째로 다시 쓴다. 같은 작업에서 캐시 쓰기 토큰이 OpenCode의 **최대 54배**. 쓰기는 프리미엄 요금이다.
- **하지만 "항상 비싸다"는 아니다.** 72KB 지시 파일은 요청마다 +20k, 서브에이전트 2개 팬아웃은 121k→513k(4.2배)로 곱해지지만, 멀티스텝 작업에서는 Claude Code가 툴 호출을 한 번에 병렬 배치해 요청 수를 줄이는 덕에 **전체 총량이 오히려 OpenCode보다 낮게** 나온 사례도 있었다. 바닥은 높지만, 세션 전개가 최종 청구서를 결정한다.

## 본문

Systima가 Claude Code(2.1.207)와 OpenCode(1.17.18)를 **같은 모델·같은 머신·같은 작업**에 올려놓고, 하네스와 모델 엔드포인트 사이에 로깅 프록시를 끼워 "무엇을 보내고 무엇이 과금됐는가"를 API 경계에서 실측했다. 프록시는 두 가지를 기록한다 — 하네스가 실제로 내보낸 JSON 페이로드(시스템 블록·툴 스키마·메시지)와, API가 돌려준 usage 블록(입력·캐시 쓰기·캐시 읽기·출력 토큰). 페이로드는 하네스가 보낸 것의 그라운드 트루스, usage는 과금된 것의 그라운드 트루스다.

**바닥값 — "OK"라고 답하는 비용.** 작업은 22자짜리 `Reply with exactly: OK`였다. 그런데 첫 요청에 실려간 것은:

- **OpenCode**: 시스템 블록 1개(9,324자, "You are OpenCode, the best coding agent on the planet"으로 시작), 고전적인 코딩 툴 10개(20,856자), 그리고 프롬프트 22자. → 계측 ~6,900 토큰. 거의 최소한이다.
- **Claude Code**: 시스템 프롬프트 27,344자(3개 블록), 툴 27개(99,778자), 그리고 프롬프트 앞에 `<system-reminder>` 스캐폴딩 7,997자(에이전트 타입 카탈로그·스킬 카탈로그·유저 컨텍스트). → 계측 ~33,000 토큰.

두 하네스 모두 **지배적 항목은 툴 스키마**다. Claude Code ~33k 중 약 24k가 툴 정의, OpenCode ~6.9k 중 약 4.8k. Claude Code의 27개 툴에는 코딩 코어뿐 아니라 백그라운드 에이전트·오케스트레이션 스위트(CronCreate, Monitor, Task 계열, worktree 관리, 푸시 알림)가 통째로 들어 있다. 툴을 전부 끄고 시스템 프롬프트만 남겨도 Claude Code는 ~6.5k 토큰으로 OpenCode(~2.0k)의 3배가 넘는다. 남는 것은 톤 규칙·안전 지침·태스크 관리 지시·환경 설명 같은 "행동 독트린"이다.

**모델을 바꾸면 그림이 달라진다.** Fable 5로 바닥을 다시 재보니 격차가 좁혀졌는데, 이유가 흥미롭다. Claude Code의 시스템 프롬프트는 **모델 조건부**다 — Sonnet에는 27,787자를, Fable에는 10,526자만 보냈고 툴 스키마도 99,778→82,283자로 다듬어졌다(같은 27개 툴, 훨씬 적은 독트린). OpenCode의 페이로드는 두 모델에서 바이트 단위로 동일했다. 결과적으로 바닥 격차는 Sonnet의 4.7배에서 Fable의 3.3배로. 여전히 훨씬 배고프지만, **배수는 모델에 따라 달라진다**는 게 핵심이다.

**멀티스텝에서는 격차가 닫힌다(그리고 역전된다).** T3(write-run-test-fix 루프)에서 Claude Code는 파일 쓰기 2회+스크립트 실행 2회를 **단 한 번의 병렬 툴 라운드트립**에 몰아넣어 3개 요청, 누적 ~121,000 토큰으로 끝냈다. OpenCode는 턴당 정확히 툴 1개씩 호출해 9개 요청(+타이틀 콜 1), 누적 ~132,000 토큰. 바닥값이 매 요청마다 재전송되기 때문에 **총량 ≈ 바닥값 × 요청 수 + 대화 증가분**이라는 구조가 드러난다. 큰 바닥값을 가진 하네스가 공격적으로 배치하고, 작은 바닥값을 가진 하네스가 직렬로 풀면 같은 지점에 착지할 수 있다.

**설정이 프롬프트를 부풀린다.** 프로덕션 리포에서 가져온 72KB 지시 파일을 넣자 두 하네스 모두 요청당 20,000토큰 이상 늘었다(OpenCode 13,152→33,336, Claude Code 39,005→59,243). 여기서 실험 중 실제로 물린 함정 — Claude Code 2.1.207은 `AGENTS.md`를 **무시**하고 `CLAUDE.md`로 이름을 바꿔야만 읽어 첫 유저 메시지에 주입한다. OpenCode는 두 파일명 다 읽어 시스템 프롬프트에 주입한다. MCP 서버는 작은 것 기준 서버당 요청마다 ~1,000~1,400토큰(5개면 툴 개수가 27→69, 10→52). 실제 워킹 셋업이면 유저가 한 글자 치기도 전에 이미 **75,000~85,000 토큰** 깊이다.

**서브에이전트가 가장 빠르게 치솟는다.** 작업을 서브에이전트 2개로 팬아웃하자 Claude Code는 9개 요청(메인 세션 ~33k 바닥값 + 서브에이전트 콜 5개, 각각 3,554자 에이전트 프롬프트 + 27개 중 24개 툴), 누적 **513,000 토큰** — 직접 수행 시 121,000의 **4.2배**다. 서브에이전트마다 자기 부트스트랩 비용을 내고, 부모가 그 트랜스크립트를 다시 삼키기 때문이다. OpenCode의 서브에이전트 설계는 더 가볍지만(1,379자 프롬프트, 5개 툴) 게이트웨이에서 깨끗이 완주하지 못해 총량은 미확정으로 남겼다.

**캐시 안정성이 조용한 진짜 차이다.** 프롬프트 캐싱은 프리픽스가 안정적일 때만 값을 한다. OpenCode는 모든 요청·모든 실행에서 바이트 단위로 동일한 프리픽스를 내보내 반복 실행 시 캐시 쓰기가 0이었다. Claude Code는 세션당 **3가지 요청 클래스**(워밍업 프로브·메인 대화·서브에이전트 콜)를 내보내고 각각이 별도 캐시 엔트리라, 게다가 시스템 바이트가 같은 워크스페이스의 세션 간에도 달라진다. 파일 요약 작업에서 Claude Code는 5개 요청에 걸쳐 캐시 쓰기 53,839토큰(전체 ~43k 프리픽스 중간 재작성 1회 포함), OpenCode는 1,003. 재실행에서도 재현됐고(43,342 → 36,899), Fable에서도 거의 그대로(50,053 재작성, Sonnet 54배 대비 52배). 캐시 온도에 따라 같은 작업에서 Claude Code의 캐시 쓰기가 OpenCode의 **5.9~54배**를 오갔다.

## 왜 중요한가

토큰 오버헤드는 곧 **비용·지연·컨텍스트 예산**이다. 하네스 페이로드로 쓰인 토큰은 코드에 쓸 수 없는 작업 컨텍스트고, 이 바닥값은 매 턴 재전송되거나 캐시에서 재-읽힌다. 85k 부트스트랩은 200k 윈도우의 40% 이상을 매 요청 점유해, 컴팩션이 돌기도 전에 실제 코드가 들어갈 자리를 갉아먹는다 — 그리고 **컨텍스트 윈도우 소모는 캐시 할인이 전혀 줄여주지 못한다**. "사용량 대시보드가 Claude Code에서 유독 치솟는" 현상의 유력한 메커니즘이 여기다: 더 큰 프리픽스, 세션당 더 많은 별개 프리픽스, 그 프리픽스들의 더 잦은 재작성, 거기에 서브에이전트 팬아웃 배수.

다만 **저자가 Systima라는 점은 계산에 넣어야 한다** — 이들은 "LLM 비용 최적화"를 파는 컨설팅사이고, 이 글은 경쟁 제품을 벤치마킹한다. 글 자체는 한계에 솔직하다: 머신 1대, 작은 표본(T1 3회, 멀티플라이어 레인은 각 1회), 측정 경로에 낀 로컬 게이트웨이(핀한 모델을 **조용히 최신 스냅샷으로 바꿔치기**하기도 했다), 그리고 무엇보다 **품질은 재지 않았다**. 두 하네스 모두 채점된 작업을 전부 정확히 통과했으니 이 토큰 격차는 "동일 결과의 비용 차이"일 뿐, Claude Code의 백그라운드 에이전트·스킬·오케스트레이션이 더 어려운 실무에서 그 토큰값을 하는지는 별도 벤치마크가 필요하다. 숫자는 2026년 7월의 스냅샷으로, 지속되는 산출물은 "API 경계에서 측정하라"는 방법론 쪽이다.

## 어떻게 써먹나

- **지시 파일 파일명을 확인하라.** 무시된 지시 파일은 조용하다 — Claude Code 2.1.207은 `AGENTS.md`를 안 읽고 `CLAUDE.md`만 읽는다. 하네스가 실제로 존중하는 이름을 경계에서 확인하라.
- **MCP 부착을 경계에서 검증하라.** Claude Code는 print 모드에서 프로젝트 스코프 `.mcp.json`을 `--mcp-config` 플래그를 명시하기 전까지 조용히 무시했다. "붙었겠지"라고 가정하지 말고 페이로드를 봐라.
- **서브에이전트 팬아웃을 첫 번째 용의자로 봐라.** 세션이 예상 밖으로 무거우면 여기부터 보라 — 이 실측에서 단일 최대 배수였다. 위임은 강력하고 때로 옳지만, 공짜가 아니다.
- **API 경계에서 로깅하라.** "지난 화요일에 우리가 모델에 정확히 뭘 보냈나"에 데이터로 답하지 못하면, 어떤 모델이 실제로 응답했는지조차 모른다(게이트웨이가 모델을 바꿔치기해도 눈치채지 못한다). 재현 리그는 Node ~200줄짜리 HTTP 프록시면 된다.
