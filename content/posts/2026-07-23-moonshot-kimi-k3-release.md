## TL;DR

- Fireworks가 실제 에이전트 루프 형태의 작업 약 1,030개(SWE·터미널·알고리듬·다중언어·법률)로 Kimi K3와 Fable 5를 같은 하네스에서 돌린 결과, **종합 점수는 거의 동률**(대표 SWE에서 K3 92.4% vs Fable 92.6%)이었지만 **강점 영역은 서로 갈렸다**고 주장한다.
- 작업별로 더 싼 정답 모델을 고르는 **오라클 라우팅**은 전체 정확도 93%에 도달했고, 트래픽의 72~96%를 저렴한 K3로 보내면서도 품질은 단일 모델보다 높고 비용은 K3 단독에 근접 — 긴 루프에선 최대 약 50배 비용 효율이라는 게 핵심 메시지다.
- 단, 이 글은 **K3를 파는 추론 호스팅 업체(Fireworks)의 콘텐츠 마케팅**이고, '오라클'은 두 모델을 다 돌려본 뒤 답을 아는 상태에서 싼 걸 고르는 **이론적 상한**이다. 그걸 미리 예측하는 실전 라우터가 존재한다는 게 전부의 대전제다.

## 무엇을 측정했나

Fireworks는 Kimi K3와 Fable 5를 동일한 에이전트 하네스에 올려, 한 번의 질의응답이 아니라 여러 턴을 도는 실제 에이전트 루프 형태의 작업 약 1,030개를 시켰다. 구성은 이렇다.

- **SWE 460개** — 실제 저장소의 버그 수정에 가까운 작업
- **터미널 89개** — 보안·암호학·리버스 엔지니어링·시스템 관리 같은 장기 셸 조작 작업
- **알고리듬 100개** — LeetCode·AtCoder 유형
- **다중 언어 225개** — 6개 언어 구현 작업
- **법률 120개** — 변호사가 직접 채점하는 법률 에이전트 작업

포인트는 "한 벤치마크 점수"가 아니라 성격이 완전히 다른 다섯 워크로드를 따로 쟀다는 점이다. 뒤에 나오는 라우팅 논리 전체가 여기서 나온다.

## 종합은 비슷, 세부는 갈린다

Fireworks의 측정에 따르면 두 모델의 종합 성능 차이는 대체로 몇 퍼센트포인트 이내였다. 대표 SWE 결과가 K3 92.4%, Fable 92.6%로 사실상 같았다는 게 상징적이다. 그런데 안을 열어보면 각자 뚜렷하게 이기는 구역이 있었다는 게 이 글의 진짜 발견이다.

- **SWE 내부**: K3는 기호 수학·개발 도구 쪽, Fable은 웹·데이터 시각화 쪽에서 우세.
- **다중 언어**: Fable이 Java·Python·C++에서 앞서고, K3는 JavaScript·Rust에서 대등.
- **장기 터미널**: 수십 번 셸을 만지는 작업에서 K3가 강했다. Fable이 못 푼 7z 해시, FEAL 암호 분석, 유출 비밀정보 추적, 실제 취약점, 통제 불능 비동기 작업을 K3가 풀었다고 한다.
- **정확도+비용을 같이 보면** Fable은 다중 언어, K3는 터미널·법률에서 앞서고 나머지는 비등.

즉 "누가 더 세냐"는 질문 자체가 잘못 걸렸고, "이 작업엔 누가 싸게 맞히냐"가 맞는 질문이라는 프레이밍이다.

## 비용 격차는 어디서 나오나

Fireworks는 K3의 비용 우위가 토큰 가격·프롬프트 캐싱·작업당 투입량 세 군데서 나온다고 설명한다. 흥미로운 건 두 모델의 '작업하는 방식'이 정반대라는 대목이다.

- **SWE 한 건**: K3는 약 55턴·130만 토큰을 쓰는 반면 Fable은 약 21턴·13만 토큰으로 끝냈다. K3가 토큰을 10배 더 읽고도, 프롬프트 캐시 적중 덕에 실행 비용은 Fable보다 낮았다는 주장.
- **긴 터미널 작업**: 반대로 Fable이 약 64턴·150만 토큰까지 쓰며 때로 타임아웃에 닿았다.

여기서 실무 함정이 하나 드러난다. K3가 싸다는 건 '청구액'이 싸다는 뜻이지 '빠르다'는 뜻이 아니다. 실행 단계가 많으면 실제 처리 시간은 길어진다. **2초 안에 답해야 하는 대화형 작업이면 지연이 곧 비용**이고, **밤새 도는 대규모 백그라운드 에이전트면 청구액이 곧 비용**이다. 워크로드에 따라 유불리가 뒤집힌다.

## 조합의 마법과 '오라클'이라는 별표

두 모델을 작업마다 더 맞는 쪽으로 보내면, 두 모델의 중간이 아니라 각 단일 모델보다 높은 성능이 나왔다 — 전체 정확도 93%. 트래픽 72~96%를 싼 K3로 흘리면서도 품질은 위, 비용은 K3 단독에 가깝다. 긴 루프에선 최대 약 50배 비용 효율. 여기까지가 Fireworks가 팔고 싶은 그림이다.

그런데 이 라우팅이 **오라클 라우팅**이라는 걸 반드시 봐야 한다. 오라클은 각 작업을 모든 모델에서 다 돌려본 뒤, 정답을 낸 것들 중 가장 싼 걸 사후에 고르는 방식이다. 즉 **정답을 이미 아는 심판**이다. 실전 라우터는 작업을 미리 여러 모델로 돌려볼 수 없으니, 어느 모델이 싸게 맞힐지를 사전에 예측해야 한다. Fireworks 스스로도 "이걸 확정하려면 한 자릿수가 아니라 10배 규모의 추가 라우팅 데이터와 실환경 검증이 필요하다"고 단서를 달았다. 93%도 50배도 전부 이 이론적 상한 위의 숫자다.

## 우리의 판단: 이건 마케팅이지만, 그래서 틀린 건 아니다

먼저 이해관계를 깔고 가자. Fireworks는 오픈 가중치 모델을 빠르게 서빙해 파는 추론 호스팅 업체이고, K3 접근권을 판다. "우리가 파는 오픈 모델이 프런티어급이고, 심지어 조합하면 최고"라는 결론은 사업 모델과 정확히 일치한다. HN 댓글들이 곧바로 "콘텐츠 마케팅", "벤치마크 과적합", "직접 써보면 중국 모델이 느리고 토큰 효율이 형편없다"고 때린 이유다. 위의 92.4%·55턴·50배 같은 수치는 전부 **Fireworks가 측정한 주장**으로 읽어야지 독립 검증된 사실이 아니다.

동시에, 방법론과 결과를 공개했고 다른 데선 잘 안 보이는 '작업 성격별 모델 적합도'라는 결을 드러낸 건 실제 가치다. 호스팅 사업을 한다는 이유만으로 데이터를 공유할 자격까지 사라지진 않는다. 실사용 댓글 중에도 "K3는 예외적으로 프런티어에 가깝지만 매우 느리다", "복잡한 실서비스에서 Fable은 내 오류율보다 낮게 잘 돌더라" 같은, 이 글 방향과 얼추 맞는 증언이 섞여 있었다.

한 가지 더 창업자 관점에서 챙길 것: **데이터 거버넌스**. 댓글에서 지적됐듯 Kimi 약관상 학습 옵트아웃 선택권이 명확치 않고, 기업이면 별도 계약을 협의해야 한다는 얘기가 나온다. 코드가 학습에 들어가도 되는지는 벤치마크 점수와 별개의 도입 게이트다. 서구권 호스팅이나 ZDR(데이터 무보존) 제공업체 경유를 기다리는 게 현실적이라는 반응이 많았다.

## 왜 중요한가

지난 몇 세대의 습관은 "제일 센 모델 하나 골라서 다 태운다"였다. 이 글이 진짜로 던지는 건 그 습관을 깨는 프레임이다 — **최고 품질 AI는 단일 제공자가 아니라 여러 모델의 조합에서 나올 수 있고, 저렴한 오픈 모델을 기본값으로 두되 긴 꼬리의 어려운 작업만 비싼 모델로 넘기는 워크로드 맞춤 라우터가 품질과 비용을 동시에 개선할 수 있다.** 오라클이라는 별표만 걷어내면, 방향 자체는 지금 에이전트 스택을 짜는 사람이 진지하게 볼 만하다. 벤더 종속을 줄이고, 특정 모델이 갑자기 폐기돼도 갈아끼울 여지를 남긴다는 부수 효과도 있다.

## 어떻게 써먹나

- **기본값을 싼 모델로, 예외를 비싼 모델로.** 전량을 프런티어에 태우지 말고, 도메인/난이도로 라우팅 규칙을 세워 다수 트래픽을 저렴한 모델에 흘리는 구조를 실험해볼 값어치가 있다. 단, 오라클이 아닌 '사전 예측' 라우터라는 걸 잊지 말 것 — 실측으로 점진 튜닝해야 한다.
- **비용을 '청구액'과 '지연'으로 쪼개서 판단하라.** 대화형이면 저턴·저지연 모델을, 백그라운드 배치면 저청구액 모델을 우선. 같은 작업도 워크로드 성격에 따라 정답이 뒤집힌다.
- **도입 전 데이터 약관부터 확인.** 학습 옵트아웃/데이터 보존 정책은 점수와 별개의 필수 게이트다. 라우팅 게이트웨이(OpenRouter류나 자체 호스팅 게이트웨이)를 둘 거면 ZDR 여부를 라우팅 조건에 넣어라.
- 이 글의 오라클 패턴을 실전 역할 라우팅으로 옮긴 오픈소스 구현 사례(역할별 다중 제공업체 LLM 순위)도 커뮤니티에 돌고 있으니, 직접 규칙을 짜기 전 레퍼런스로 참고할 만하다.
