typedef-ai가 공개한 **fenic**은 PySpark/SQL식 데이터프레임 연산과 언어 모델 호출을 *하나의 쿼리 모델* 안에 녹여 넣은 쿼리 엔진이다. `select`·`filter`·`join`·`group_by`·`agg` 같은 익숙한 관계형 연산 옆에, LLM을 부르는 시맨틱 연산자를 나란히 놓는다. 라이선스는 Apache-2.0.

## TL;DR
- 관계형 데이터프레임 연산(`select`/`filter`/`join`/`agg`)과 LLM 시맨틱 연산자(`extract`/`classify`/`summarize`/`embed`/시맨틱 `join`)를 **같은 쿼리 모델**에서 타입·스키마를 가진 연산자로 다룬다.
- 지연 실행·캐싱 위에 **자동 배칭/레이트 리미팅/재시도(백오프)/타입 검사**를 얹어, 비결정적이고 비싼 추론 호출을 예측 가능하게 만들고 비용을 줄인다.
- 파이프라인 자체를 산출물로 남기고(행 단위 lineage·`explain`·쿼리별 토큰/비용), 명명된 테이블/뷰나 **MCP 도구**로 승격해 사람과 에이전트가 같은 파이프라인을 공유하게 한다.

## fenic가 실제로 하는 일

핵심 아이디어는 "비정형 텍스트를 타입 지정된 행(typed rows)으로 바꿔 반복 가능한 워크플로로 만든다"는 것이다. 문서·트랜스크립트·로그·eval 트레이스·티켓·테이블·API처럼 흩어진 입력을, 조회 가능한 구조화 컬럼으로 정규화한다. 이때 비정형 텍스트를 **Pydantic 스키마에 바인딩**해서 결과를 스키마가 있는 컬럼으로 되돌려 준다는 점이 특징이다. LLM에 "JSON으로 뽑아줘"라고 던지고 파싱을 손으로 방어하는 대신, 추출 결과가 처음부터 타입을 가진 데이터로 들어온다.

시맨틱 연산자는 별도 SDK 호출이 아니라 쿼리 모델에 **내장된 연산자**다. `extract`로 구조를 뽑고, `classify`로 분류하고, `summarize`로 요약하고, `embed`로 임베딩을 만들며, 정확한 키가 아니라 **의미 기반으로 행을 잇는 시맨틱 조인**까지 스키마·타입을 가진 연산으로 동작한다. Markdown·Transcript·JSON(`jq`)·HTML·임베딩을 일급 논리 타입으로 취급하고 PDF 파싱을 지원하며, S3와 Hugging Face의 CSV·Parquet도 읽는다.

성능·비용 면에서 눈여겨볼 설계는 **실행 순서 최적화**다. 일반(비-LLM) 필터를 시맨틱 필터보다 먼저 실행해 LLM에 도달하는 행 수를 줄인다. 여기에 자동 배칭, 레이트 리미팅, 재시도, 캐싱을 붙여 불필요한 모델 호출과 비용을 깎는다. fenic는 자체 쿼리 계획과 추론 실행 계층을 갖되, 순수 데이터 연산은 **Polars/DuckDB**에 위임하고 데이터 교환은 **Apache Arrow**로 하며 로컬에서 간단히 돌아간다. 즉 "추론 오케스트레이션은 직접, 무거운 관계형 연산은 검증된 엔진에" 라는 역할 분담이다.

또 하나의 축은 **관찰 가능성**이다. 파이프라인 자체가 산출물이며, 행 단위 lineage와 `explain`, 쿼리별 토큰/비용 지표로 내부를 뜯어볼 수 있다. 지연 실행과 캐싱 덕에 재실행이 가능하고, 완성된 파이프라인은 명명된 테이블/뷰 또는 MCP 도구로 승격된다. 원문의 표현을 빌리면 탐색 결과가 *"채팅 기록으로 사라지지 않고 코드/데이터/파이프라인으로 남"*는다.

에이전트 통합도 명시적이다. 코딩 에이전트용 `fenic skill install`과 정적 검사기 `fenic check`를 제공하고, 파이프라인을 카탈로그에 도구로 등록해 **MCP로 노출**함으로써 데이터 파이프라인을 에이전트가 호출할 수 있는 타입 지정 도구로 바꾼다. fenic는 스스로를 "에이전트를 위한 선언적 컨텍스트 엔지니어링"으로 정의하며, 무거운 배치 추론을 에이전트 런타임 밖으로 분리(decouple)해 더 예측 가능하고 반응성 좋은 에이전트와 나은 자원 활용을 목표로 한다.

## 왜 중요한가

지난 2년간 LLM 데이터 파이프라인은 대부분 명령형 스크립트(반복문 + API 호출 + 임시 파싱 + 손수 만든 재시도)로 쌓여 왔다. 이 방식은 재실행·검사·비용 추적이 어렵고, 탐색 과정이 노트북과 채팅 로그에 흩어져 재사용되지 않는다. fenic는 이 문제를 **선언적 데이터프레임**이라는, 데이터 엔지니어에게 이미 검증된 추상화로 되돌린다. 쿼리 옵티마이저가 관계형 연산을 재배치하듯, "값싼 필터 먼저, LLM 나중"을 엔진이 대신 해 주면 비용 최적화가 사용자 규율이 아니라 시스템 속성이 된다.

에이전트 관점에서 더 중요한 건 **배치 추론과 에이전트 런타임의 분리**다. 에이전트 루프 안에서 대량 문서를 즉석 처리하면 지연·비용·비결정성이 그대로 사용자 경험으로 튄다. 무거운 추론을 미리 컴파일된 타입 지정 파이프라인(=MCP 도구)으로 밀어내면, 에이전트는 잘 정의된 도구를 호출할 뿐이라 더 예측 가능해진다. "사람과 에이전트가 같은 파이프라인을 작성·검사·재사용한다"는 설계는, 프롬프트 엔지니어링을 버전 관리·리뷰 가능한 코드 자산으로 승격시키려는 시도로 읽힌다.

## 어떻게 써먹나

- **비정형 → 구조화 ETL**: 티켓·트랜스크립트·로그를 Pydantic 스키마로 `extract`해 조회 가능한 테이블로 만든 뒤, 일반 데이터프레임처럼 필터·집계한다. 파싱 방어 코드를 걷어낼 수 있다.
- **비용 민감한 대량 분류/요약**: 값싼 필터로 후보를 좁힌 뒤 시맨틱 연산자를 태우고, 쿼리별 토큰/비용 지표로 실제 지출을 추적한다.
- **에이전트용 도구화**: 검증된 파이프라인을 MCP 도구로 승격해, 코딩 에이전트가 런타임 밖에서 배치 추론을 호출하도록 한다. `fenic check`로 CI에서 정적 검증을 건다.
- **의미 기반 데이터 매칭**: 정확한 조인 키가 없는 두 데이터셋(예: 자유 서술 텍스트끼리)을 시맨틱 조인으로 잇는다.

한 가지 유의점: 원문은 fenic의 설계와 기능을 소개할 뿐 벤치마크·버전·정확도 수치를 제시하지 않는다. 시맨틱 조인의 정밀도, 자동 배칭의 실질 비용 절감폭, 대규모에서의 안정성은 직접 검증해야 할 몫이다.
