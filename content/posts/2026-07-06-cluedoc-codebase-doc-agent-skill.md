## TL;DR

- **Cluedoc**은 코딩 에이전트가 사람이 읽기 위한 상위 수준 문서를 스스로 작성·갱신하게 하는 Agent Skill이다. 시스템을 **기능(feature)의 트리**로 보고 기능마다 문서(paper) 하나를 붙인다.
- 문서는 서버·DB 없이 **코드베이스 안에 순수 Markdown**으로 존재하며, 에이전트의 **작업 루프 안에서 계속 최신 상태**로 유지된다.
- 랜딩 페이지 자체가 Cluedoc으로 쓴 Cluedoc 문서이고, **Flask·Cobra·Commander** 예시 문서도 함께 공개돼 있다.

## 무엇을 푸는가

`keunwoopark`이 공개한 Cluedoc의 출발점은 요즘 개발자라면 대부분 공감할 상황이다. 에이전트가 코드를 쏟아내고, 정작 나는 그 코드를 단 한 줄도 직접 타이핑하지 않았다. 코드베이스는 계속 바뀌는데 "이 시스템이 실제로 무슨 일을 하는지", "다음 수정이 안전한지"를 판단할 근거가 점점 옅어진다.

Cluedoc의 주장은 여기서 방향을 튼다. 에이전트가 대신 일해주는 세계일수록 **코드를 이해하는 일이 오히려 가장 중요한 일**이 된다는 것이다. 에이전트를 올바른 방향으로 몰고 가려면, 지금 만들고 있는 시스템에 대한 **최소한의 이해**가 사람 쪽에 반드시 남아 있어야 하기 때문이다. 문서화를 "다 만든 뒤에 하는 뒷정리"가 아니라, 에이전트를 조종하기 위한 **필수 계기판**으로 재정의하는 셈이다.

핵심 설계는 세 가지로 정리된다.

- **읽히기 위한 문서.** Cluedoc이 만드는 문서는 저수준 기술 디테일을 걷어내고 **상위 수준 개념에 집중**한다. 코드를 그대로 옮긴 자동 생성 API 레퍼런스가 아니라, 사람이 앉아서 읽고 시스템의 그림을 그릴 수 있는 글을 지향한다.
- **기능 트리 = 문서 트리.** 시스템을 기능의 트리로 모델링하고, **기능 하나당 문서(paper) 하나**를 대응시킨다. 문서 구조가 곧 시스템 구조를 반영하도록 만든 것이다.
- **코드베이스 안의 순수 Markdown, 루프 안에서 갱신.** 문서는 별도 서버도, 데이터베이스도 없이 **레포 안에 Markdown**으로 그냥 존재한다. 그리고 에이전트의 **작업 루프 안에서** 코드가 바뀔 때 함께 최신 상태로 유지된다. 문서가 코드와 같은 곳에, 같은 흐름 안에 있으니 "문서만 낡는" 고전적 실패를 구조적으로 줄이려는 접근이다.

증거 삼아 저자는 **랜딩 페이지 자체를 Cluedoc으로 작성한 Cluedoc 문서**로 만들어 두었다(도구로 도구를 문서화하는 도그푸딩). 추가로 **Flask, Cobra, Commander** 같은 실제 오픈소스에 대해 생성한 예시 문서들을 공개해, 결과물이 어떤 톤·구조로 나오는지 직접 확인할 수 있게 했다.

## 왜 중요한가

에이전트 코딩의 병목이 "코드를 얼마나 빨리 만드느냐"에서 "만들어진 코드를 사람이 얼마나 붙잡고 있느냐"로 옮겨가는 흐름을 정면으로 겨눈다. 대부분의 자동 문서화 도구가 코드 → 저수준 레퍼런스를 뽑는 데 그치는 반면, Cluedoc은 **사람의 멘탈 모델**을 타깃으로 잡고 상위 개념 문서를 만든다는 점에서 결이 다르다. 또한 서버·DB 없이 레포 안 Markdown으로 끝낸다는 결정은 도입 마찰을 거의 0으로 만든다 — 운영할 인프라가 없다는 건 팀에 붙이기 쉽다는 뜻이다.

주의할 점도 있다. 공개된 내용은 설계 철학과 예시 산출물 중심이고, 문서 품질·정확도나 규모 있는 코드베이스에서의 유지 비용에 대한 정량 근거는 아직 이 소개글 범위 밖이다. "루프 안에서 항상 최신"이 실제로 얼마나 지켜지는지는 직접 굴려봐야 확인된다.

## 어떻게 써먹나

- Agent Skill이므로, 이미 코딩 에이전트를 쓰고 있다면 스킬로 얹어 **feature 단위 상위 개념 문서**를 뽑아보는 게 첫 실험이다.
- 도입 판단은 예시부터: 공개된 **Flask/Cobra/Commander 문서**와 랜딩(=Cluedoc 자기 문서)을 읽고, 그 문서만 보고 시스템 구조가 머리에 들어오는지로 유용성을 가늠하라.
- 우리 스택에 붙일 때는 "코드 바뀔 때 문서도 같은 커밋/루프에서 갱신"이 실제로 강제되는지를 체크포인트로 잡는 게 핵심이다 — 이 부분이 무너지면 여느 문서화와 똑같이 낡는다.
