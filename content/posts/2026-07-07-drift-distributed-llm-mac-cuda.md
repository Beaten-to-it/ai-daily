## TL;DR

- DRIFT는 **LLM 하나를 디코더 레이어 단위로 쪼개** 여러 개인 기기에 나눠 실행하는 오픈소스 프로젝트로, Mac의 Apple GPU(MPS)와 PC의 NVIDIA GPU(CUDA)를 **한 모델 실행 안에 섞어** 쓴다.
- 핵심 설계는 노드 경계를 특정 ML 런타임이 아니라 **TCP + msgpack 중립 바이트 프로토콜**로 끌어올린 것 — 노드 간에는 모델도 KV 캐시도 아닌 **hidden state만** 오간다.
- 속도가 아니라 **정확성**이 우선순위로, "분산 결과 = 단일 머신 결과"를 검증하는 데 무게를 둔다. README 기준 Qwen2.5-1.5B-Instruct에서 패리티 게이트를 통과했다.

## 무슨 프로젝트인가

프론티어 모델은 점점 닫히고(비싸지고 접근이 제한되고), "내 컴퓨터에서 돌린다"는 로컬 모델은 실제로는 꽤 큰 GPU 메모리와 세팅을 요구한다. 모델 가중치가 열려 있어도, 그걸 충분한 규모로 **실행할 능력**은 여전히 일부 하드웨어·플랫폼에 몰려 있다. DRIFT(개발자 TaewoooPark)가 던지는 질문은 여기서 나온다 — 한 대가 모델 전체를 감당하지 못한다면, 여러 개인 기기가 **한 모델을 함께** 돌리면 되지 않나?

접근 방식은 모델 병렬화의 정공법이다. 트랜스포머의 디코더 레이어들을 노드별로 나눠 배치하고, 추론이 진행되면서 앞 노드의 출력인 **hidden state**를 다음 노드로 넘긴다. 여기서 중요한 건 "무엇을 보내지 않는가"다. 모델 가중치 전체나 KV 캐시를 전송하는 게 아니라, 레이어 경계의 활성값(hidden state)만 전달한다. 통신 계층도 PyTorch 텐서 객체나 CUDA 핸들 같은 런타임 종속 객체가 아니라 **TCP + msgpack 기반의 중립 바이트 프로토콜**로 처리한다. 이 "런타임에 묶이지 않은 노드 경계"가 프로젝트의 정체성이다.

## 주요 기능

원문이 밝힌 기능을 정리하면 다음과 같다.

- 하나의 LLM을 **디코더 레이어 단위로 자동 분할**
- **Mac MPS와 NVIDIA CUDA 혼합 실행**
- 노드 간 통신에 **TCP + msgpack** 사용
- **P2P 체인 모드**로 head 노드의 대역폭 병목 완화
- **X25519 + ChaCha20-Poly1305** 기반 암호화 와이어
- **Ed25519 서명 영수증**으로 각 노드가 실제로 그 레이어를 계산했는지 검증
- 노드가 중간에 죽으면 **re-split + replay** 기반 failover
- **OpenAI 호환 HTTP API** 제공

분할 대수는 이론적으로 디코더 레이어 수만큼 가능하다. 원문 기준 Qwen은 최대 28대, Gemma는 최대 35대까지 한 모델을 나눌 수 있고, **현실적인 스위트 스팟은 2~4대** 수준이라고 밝힌다. 즉 "수십 대 클러스터"보다는 "집에 있는 Mac 한 대 + 게이밍 PC 한 대"를 묶는 시나리오가 현재의 실용 영역이다.

## 비슷한 프로젝트와의 차이

이 문제를 푸는 선행 프로젝트로 원문은 Exo와 llama.cpp RPC를 든다.

- **Exo**: Apple Silicon끼리 묶어 로컬 클러스터처럼 쓸 수 있지만, 노드 간 통신이 MLX에 묶여 있어 Apple 생태계를 벗어나기 어렵다.
- **llama.cpp RPC**: 여러 백엔드를 활용할 수 있으나 ggml/llama.cpp 런타임에 붙은 RPC 방식이다.

DRIFT의 차별점은 노드 사이의 경계를 **특정 ML 런타임이 아니라 중립 바이트 프로토콜로 끌어올렸다**는 점이다. 그래서 원래 같은 분산 런타임에 넣기 어려운 조합 — 대표적으로 Apple MPS ↔ NVIDIA CUDA — 을 하나의 모델 실행 안에 담는 쪽에 초점이 있다. 구현 자체는 Python과 PyTorch 위에 있지만, "노드끼리 주고받는 계약"은 PyTorch에 의존하지 않게 잡혀 있다는 게 설계 의도다. 모델 로딩·실행은 Hugging Face Transformers, safetensors, PyTorch MPS/CUDA를 쓰고, 바깥으로는 Starlette/Uvicorn 기반 OpenAI 호환 API를 노출한다. "어떤 모델을 어떤 디바이스에서 돌리느냐"와 "노드들이 어떤 바이트를 주고받느냐"를 분리하려는 구조다.

## 속도가 아니라 정확성이 먼저

주목할 부분은 우선순위다. DRIFT는 속도를 앞세우는 프로젝트가 아니라, **분산해서 돌린 결과가 단일 머신 결과와 같은 답을 내는가**를 검증하는 데 무게를 둔다. README 기준 Qwen2.5-1.5B-Instruct에서 여러 패리티 게이트를 통과했고, Mac MPS와 NVIDIA CUDA를 섞은 실험도 포함되어 있다고 밝힌다. (다만 이 패리티 주장은 Qwen2.5-1.5B-Instruct라는 특정 모델 범위에 한정된 것으로 읽어야 한다 — 모든 모델·규모에서 정확성이 보장됐다는 뜻은 아니다.)

## 왜 중요한가

프론티어 모델이 개인 사용자에게서 멀어지는 흐름에 대해, DRIFT가 내놓는 답은 "개인의 리소스를 뭉쳐 실행 능력을 키운다"는 것이다. 흥미로운 지점은 이 프로젝트가 "AI 탈중앙화"를 토큰 경제나 거대 네트워크 서사에서 시작하지 않는다는 데 있다. 그 위에 무엇을 얹기 전에 먼저 필요한 건 **실행 계층** — 개인 기기들이 실제로 하나의 모델 실행에 참여할 수 있고(레이어 분할), 누가 어떤 레이어를 계산했는지 검증할 수 있고(Ed25519 영수증), 노드가 빠져도 복구되며(re-split + replay), 특정 벤더·데이터센터에 묶이지 않는(중립 프로토콜) 구조다. 이 실행 계층이 있어야 그 위에 더 큰 네트워크를 논할 수 있다는 순서 감각이, 흔한 "분산 AI" 담론과 구별되는 대목이다.

개발자 입장에서 실질적인 의미는, MPS와 CUDA를 한 실행에 섞는다는 조합 자체가 기존 분산 추론 스택에서 어려웠던 지점을 정면으로 겨냥한다는 점이다. 그리고 성능이 아니라 정확성을 게이트로 삼는 태도는, 분산 추론에서 가장 조용히 새기 쉬운 문제(디바이스·수치 차이로 인한 출력 드리프트)를 프로젝트 1순위로 놓았다는 신호다.

## 어떻게 써먹나

- **집에 흩어진 이기종 하드웨어 묶기**: 32GB Mac 한 대와 NVIDIA GPU가 달린 Windows/Linux PC 한 대처럼, 각각으로는 못 올리던 모델을 두 대에 레이어로 나눠 올려보는 시나리오. 현실 스위트 스팟이 2~4대라는 점을 감안해 "대규모 클러스터"보다 소수 기기 결합부터 시작하는 게 맞다.
- **OpenAI 호환 API로 얹기**: OpenAI 호환 HTTP 엔드포인트를 제공하므로, 기존에 OpenAI SDK로 짠 클라이언트·에이전트 코드를 base URL만 바꿔 붙일 수 있다. 로컬 분산 백엔드를 기존 앱 뒤에 끼워 넣는 실험이 쉽다.
- **정확성 민감 워크로드의 사전 검증 참고**: 분산으로 돌릴 때 단일 머신과 출력이 갈리는지 걱정된다면, DRIFT가 패리티 게이트를 어떻게 잡았는지(특정 모델 범위에서) 참고 지점이 된다.
