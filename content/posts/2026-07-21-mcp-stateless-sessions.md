# MCP가 '스테이트리스'로 간다 — AI 에이전트 인프라의 조용한 스케일 업데이트

## TL;DR
- MCP(Model Context Protocol)가 세션 ID를 다루는 방식을 서버 쪽에서 '스테이트리스(stateless)'로 바꾼다. 새 스펙은 5월부터 공개돼 있었고, TechCrunch는 기사 시점(7/20) 기준 다음 주에 반영된다고 전한다.
- 지금은 한 서버가 세션 ID를 발급하고 그 서버가 대화를 '기억'하는 구조라, 로드밸런서가 요청을 여러 서버에 뿌리는 실제 대규모 배포에서 골칫거리였다. 새 방식은 일반 웹서버처럼 서버가 상태를 안 들고 있어도 되게 만든다.
- 이 설명은 에이전트 인프라 스타트업 Arcade(2년차, 6월 6천만 달러 유치)가 내놓은 것으로, 창업자 Nate Barbettini는 "에이전트가 실패하는 건 모델이 약해서가 아니라 주변 인프라가 아직 안 됐기 때문"이라는 자사 관점에서 이 업데이트를 프레이밍한다.

## 무슨 일인가

MCP는 AI 모델이 외부 데이터 소스·서비스에 안전하게 접근하도록 해주는 상호운용 규격이다. TechCrunch의 표현을 빌리면 챗봇이 당신의 캘린더·데이터베이스·사내 도구에 손을 뻗게 해주는 '배관(plumbing)'으로, 연결마다 커스텀 파이프를 직접 까는 대신 표준 배관을 쓰게 해준다. 최종 사용자 눈에는 안 보이지만 생태계가 굴러가는 방식을 좌우하는 저수준 레이어다.

이번 변경의 핵심은 **세션 ID를 처리하는 방식**이다. 세션 ID는 서버가 "아, 이건 5초 전 그 대화랑 같은 놈이군" 하고 알아보게 해주는 작은 토큰이다. Arcade 창업자 Nate Barbettini가 정리한 현재 동작은 이렇다: Claude 같은 MCP 클라이언트가 서버에 처음 붙으면 "안녕, 나 Claude야, 버전은 이거고 이런 능력이 있어" 하고 인사를 보낸다. 서버는 자기 능력을 회신하면서 세션 ID를 하나 발급한다. 그 뒤로 클라이언트는 매 요청마다 그 ID를 실어 보내 "같은 대화"임을 알린다. ID가 만료되면 클라이언트가 그걸 눈치채고 새 ID를 받아 이어가야 한다.

문제는 스케일이다. Barbettini의 비유를 그대로 옮기면 — 수백만 사용자를 상대하는 서버를 로드밸런서 뒤에 두고 굴린다고 하자. 로드밸런서의 유일한 일은 매 요청을 그때그때 노는 서버로(때론 다른 리전으로) 넘기는 것이다. 그런데 지금 구조에선 이 서버 농장의 모든 머신이, 다른 머신이 발급한 세션 ID를 알고 있어야 한다. 불가능하진 않지만 상당히 성가시고, 로드밸런서와 협력하는 게 아니라 싸우는 꼴이 된다. 요컨대 지금의 MCP는 "한 서버가 너를 기억한다"를 전제하는데, 현실의 회사는 서로 대화하지 않는 수십 대 서버에 트래픽을 흩뿌린다. 그래서 누가 누구인지 추적하는 데 별도의 품이 든다.

새 버전은 이 세션 ID를 서버 쪽에서 더 느슨한 '스테이트리스' 방식으로 다룬다. 대부분의 평범한 웹사이트가 이미 그렇게 동작하는 것과 비슷하게, 서버가 대화 상태를 짊어지지 않아도 되게 만드는 것이다. 그 결과 시스템 유지가 한결 쉬워지고, 이론상 대규모 운영 비용도 싸진다는 게 요지다.

한 가지 attribution을 분명히 해두자. 이 명쾌한 설명과 "에이전트가 실패하는 진짜 이유는 모델이 아니라 인프라"라는 진단은 중립적 사실이 아니라 **Arcade의 포지셔닝**이다. Arcade는 AI 에이전트를 실제 회사 안에서 작동시키는 일 — Gmail·Slack·Salesforce 같은 도구에 안전하게 붙어 실제 액션을 수행하게 하는 것 — 을 사업 전체로 삼은 2년차 스타트업이고, 바로 그 전제(인프라가 병목) 위에서 6월에 6천만 달러를 유치했다. 이번 MCP 업데이트가 겨냥하는 지점이 정확히 자기네가 파는 문제와 겹친다는 점을 감안하고 읽는 게 맞다.

## 왜 중요한가

- **인프라가 병목이었다는 신호.** TechCrunch는 이 세션 ID 문제가 "스케일에서 MCP 서버를 돌리는 누구에게나 상당한 두통"이었고, 올해 에이전틱 AI에 쏟아진 하이프에도 불구하고 대규모 1st-party MCP 통합이 더 많이 나오지 못한 이유의 일부였다고 짚는다. 즉 모델 성능이 아니라 배관이 발목을 잡고 있었다는 얘기다.
- **속도의 비대칭.** 기사가 남긴 큰 그림은, AI의 모든 부분이 같은 속도로 달리지 않는다는 것이다. 모델 학습은 질주하지만 그 모델이 딛고 설 기술 인프라는 표준화 기구의 느린 합의('통나무 굴리기')에 묶여 있다. 진행은 되지만 조금 느릴 뿐이라는 것.
- **표준의 무게.** MCP는 특정 벤더 하나가 밀어붙이는 API가 아니라 여러 참여자가 합의하는 규격이다. 세션 처리 방식 같은 저수준 결정 하나가 어떤 회사가 실제로 대규모 통합을 출시할 수 있는지를 좌우한다.

## 어떻게 써먹나

- **MCP 서버를 스케일로 운영/계획 중이라면**, 로드밸런서 뒤에서 세션 스티키니스(sticky session)나 세션 ID 공유 저장소를 억지로 맞춰오던 부담이 새 스펙에선 줄어든다. 상태를 서버가 안 들면 임의의 서버가 아무 요청이나 받을 수 있어 오토스케일·다중 리전 배포가 평범한 무상태 웹서비스처럼 단순해진다. 마이그레이션 전 새 스펙(5월 공개분)에서 세션 처리 규정을 먼저 읽어두는 게 좋다.
- **에이전트를 사내 도구에 붙이려는 팀이라면**, 지금까지 "1st-party MCP 통합이 왜 이렇게 안 나오나" 싶었던 체감의 원인이 모델이 아니라 이런 운영 배관에 있었다는 점을 기억하자. 파일럿이 데모에서 막히는 게 프롬프트 탓이 아닐 수 있다.
- **벤더 평가 시**, "인프라가 진짜 병목"이라는 서사를 파는 회사(Arcade 등)의 주장은 이번 업데이트로 일부 표준 레벨에서 해소된다. 그들이 제공하는 가치가 '표준이 아직 못 메운 부분'인지 '표준이 곧 메울 부분'인지 구분해서 보라.
