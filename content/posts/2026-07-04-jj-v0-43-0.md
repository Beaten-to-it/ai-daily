Git 호환 버전 관리 시스템 Jujutsu(`jj`)가 v0.43.0을 냈다. 이번 판의 헤드라인은 새 서브커맨드 `jj run`이고, 그 대가로 오래 유예해 온 revset·설정 관련 호환성 파괴 몇 개가 실제로 삭제됐다. 업그레이드하려면 이 두 축을 같이 봐야 한다.

## TL;DR

- **`jj run`** 신설 — 여러 변경 집합(커밋)을 대상으로 같은 명령을 돌리되, 커밋마다 **분리된 전용 작업 복사본**을 쓰고 명령이 만든 변경·충돌을 하위로 전파한다. `jj run -- cargo check --all-features`, `jj run -- cargo fix` 식.
- **호환성 파괴 삭제** — revset/template의 `git_head()`·`git_refs()` 제거, `refs/heads/main` 같은 Git식 심볼을 리비전으로 더 이상 해석 안 함(`<name>` 또는 `<name>@<remote>` 써야 함), `ui.revsets-use-glob-by-default` 옵션 제거.
- **손상 버그 수정** — Intel Raptor Lake CPU와 aarch64에서 커밋은 성공 보고됐지만 이후 `git fsck`가 `corrupt loose object`로 깨지던 loose Git object 손상 문제를 고쳤다.

## 본문

### `jj run`: 커밋 단위 명령 실행

핵심 신기능은 여러 변경 집합에 같은 명령을 한 번에 적용하는 `jj run`이다. 요점은 **격리**다. 각 변경 집합이 서로 분리된 전용 작업 복사본을 받고, 그 안에서 명령이 실행된다. 명령이 작업 복사본을 고치면(예: 포매터가 파일을 쓰거나 `cargo fix`가 코드를 바꾸면) 그 변경과 충돌이 알맞게 하위 리비전으로 전파된다. 릴리스가 든 예시가 그대로 용도를 말해 준다.

```
jj run -- cargo check --all-features
jj run -- cargo fix
```

스택에 쌓인 커밋들이 **각각** 빌드·검사를 통과하는지 확인하거나, 스택 전체에 일괄 수정을 흘려보내는 작업이 자연스러워진다.

원문 댓글(Lobste.rs 인용)이 짚은, 자주 헷갈릴 지점 하나를 정리해 둔다 — `jj run`과 기존 `jj fix`는 겹쳐 보이지만 동작 모델이 다르다.

- `jj run`은 커밋마다 **전체 작업 복사본**을 만들고 그 안에서 명령을 통째로 실행한다. 느리지만 유연하다(테스트 스위트 실행처럼 파일 하나로 안 끝나는 작업).
- `jj fix`는 **개별 파일 내용을 명령에 파이프로 넘기고** 그 출력을 파일의 새 내용으로 삼는다. 포매터·린터처럼 파일 단위 필터에 맞고, 그만큼 빠르다.

즉 "각 커밋을 검증"은 `run`, "각 파일을 필터"는 `fix`다. 둘을 조합해 `run`으로 각 커밋 유효성 확인 후 `fix`로 포맷을 돌리는 흐름이 이 도구가 그리는 그림이다.

### 삭제된 호환성 (업그레이드 전 확인)

이번 판은 오래 deprecated였던 것들을 실제로 뺐다. 스크립트·설정·revset을 쓰던 사람은 깨질 수 있다.

- revset과 template에서 `git_head()`·`git_refs()` 함수 제거.
- `refs/heads/main` 같은 **Git식 심볼을 리비전으로 해석하지 않음**. 대신 bookmark/tag의 `<name>` 또는 `<name>@<remote>` 문법을 써야 한다.
- `ui.revsets-use-glob-by-default` 옵션 제거.
- `jj bookmark track`/`untrack`이 `<kind>:<bookmark>@<remote>` 패턴을 더 이상 안 받음. 단 `<bookmark>@<remote>` 심볼 문법은 **계속 지원**된다(관련 이슈 #9226).

### 새로 추가된 편의 기능

- `jj show --reversed` 플래그.
- 설정 파일을 `/etc/jj`에서도 탐색.
- `jj config gc` — `~/.config/jj/repos`에서 삭제·이동된 저장소의 설정을 정리(#9362).
- `jj gerrit upload`가 `git push -o`처럼 동작하는 `-o`/`--option` 지원.
- `jj git fetch`가 변경 ID 기준으로 다시 쓰인 리비전의 하위를 리베이스(불변 하위는 제외). 이전엔 스택에 bookmark 붙은 리비전이 여럿일 때 항상 리베이스되진 않았다.
- `forks()` revset 함수 — 자식이 2개 이상인 커밋을 반환.
- `colors` 설정이 `{ crossed-out = true }`로 취소선 스타일 지원.

### 수정된 문제

- **Windows 파일 identity** 조회 시 심볼릭 링크를 더 이상 따라가지 않아 Unix 동작과 맞춤. 이 검사는 작업 복사본에서 예약된 `.git`·`.jj` 디렉터리의 alias를 감지하는 데 쓰인다(#8924).
- 작업 복사본이 불변 상태일 때, jj가 **스냅샷 도중** 새 working-copy 리비전을 생성. 이전엔 불변이 된 직후에 생성했다(#7751, #9338).
- `jj git remote add`가 새 remote의 fetch URL 또는 유효 push URL이 기존과 정확히 같으면 경고(#413).
- **Intel Raptor Lake / aarch64 loose Git object 손상 수정**. 이전엔 jj가 커밋 성공을 보고했는데도 이후 `git fsck`가 `incorrect data check`·`corrupt loose object`·`missing blob`으로 실패하고, 뒤이은 jj 작업도 `corrupt deflate stream`으로 깨질 수 있었다.

## 왜 중요한가

`jj run`은 "스택 전체를 커밋별로 검증/수정"이라는, Git rebase-exec로는 번거롭던 워크플로를 일급 명령으로 끌어올린다. 커밋마다 격리된 작업 복사본 + 충돌 전파라는 설계는 jj의 "커밋은 언제나 다시 쓸 수 있다"는 모델과 잘 맞는다. 동시에 이번 판은 deprecated 제거를 실제로 단행했으니, 업그레이드는 기능 추가가 아니라 **깨질 수 있는 변경**으로 취급해야 한다 — 특히 revset·bookmark 문법을 스크립트에 박아 둔 경우. 그리고 특정 CPU에서 조용히 리포지터리를 오염시키던 loose object 손상 수정은, 해당 하드웨어 사용자에겐 기능보다 더 중요한 신뢰성 픽스다.

## 어떻게 써먹나

- **업그레이드 전**: 스크립트·설정에서 `git_head()`/`git_refs()`, `refs/heads/...` 리비전 참조, `ui.revsets-use-glob-by-default`를 검색해 `<name>@<remote>` 문법으로 치환.
- **CI-in-loop**: `jj run -- <테스트 명령>`으로 스택의 각 커밋이 독립적으로 통과하는지 검증. bisect 전에 스택 건전성부터 확인하는 용도로.
- **일괄 수정**: `jj run -- cargo fix`처럼 스택 전체에 자동 수정을 흘리고, 전파된 충돌만 손으로 정리.
- **Raptor Lake / aarch64 사용자**: 과거 `git fsck` 오류를 본 적 있으면 이 판으로 올려 재발 여부 확인.
