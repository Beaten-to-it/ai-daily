## 무엇이 있었나

GitHub.com에서 발생한 장애로 웹과 API 트래픽뿐 아니라 저장소 콘텐츠 다운로드, Pull Request, Issues, Actions, Webhooks 등 여러 기능이 영향을 받았다. 복구 발표 뒤에도 일부 Pull Request에 접근하지 못하는 동안 공식 상태 페이지에는 서비스가 정상으로 표시되는 문제도 이어졌다.

이번 사례는 GitHub가 단순한 Git 저장소를 넘어 코드 리뷰, 업무 기록, 자동화, 배포와 릴리스까지 담당하는 개발 플랫폼이 됐다는 점을 다시 드러냈다. 특히 자체 호스팅 러너를 운영하더라도 작업 배정과 인증을 담당하는 제어 기능이 GitHub에 남아 있으면 플랫폼 장애 때 CI 작업을 받지 못할 수 있다.

이에 따라 전면적인 서비스 이전보다 의존성을 기능별로 나누자는 주장이 제기됐다. 코드와 Git 이력은 별도 원격 저장소에 복제하고, 중요한 설계 결정과 운영 절차는 저장소 문서로 보존하며, 긴급 수정과 릴리스에는 GitHub Actions와 분리된 복구 경로를 마련하는 방식이다. 공개 프로젝트라면 GitHub를 발견과 기여를 위한 창구로 유지하면서 실제 개발 공간이나 백업 인프라를 분리하는 절충안도 가능하다.

## 왜 중요한가

한국의 개발팀과 오픈소스 프로젝트에도 핵심 질문은 ‘GitHub를 떠날 것인가’보다 ‘GitHub가 멈췄을 때 어떤 업무까지 중단되는가’에 가깝다. 저장소 복제본만 확보해도 코드는 보호할 수 있지만, 이슈의 논의 과정과 리뷰 기록, 자동화된 테스트, 패키징 및 배포 절차까지 곧바로 복구되는 것은 아니다.

GitHub를 다른 관리형 서비스로 옮기면 이전 부담은 비교적 작지만 단일 플랫폼 의존이라는 구조가 되풀이될 수 있다. 자체 호스팅은 데이터와 정책을 직접 통제할 수 있는 대신 백업, 보안, 업그레이드와 실행기 운영 비용을 부담해야 한다. 공개 오픈소스 프로젝트는 계정과 검색 노출, 기여 이력, 무료 다중 운영체제 CI 같은 생태계 효과도 고려해야 한다.

따라서 조직별로 리뷰 지연, 배포 중단, 긴급 복구 불능을 구분해 허용 가능한 장애 범위를 정하고, 필요한 부분부터 대체 경로를 검증하는 접근이 현실적이다. 중요한 것은 미러의 존재 자체가 아니라 실제 장애 상황에서 그 사본으로 개발과 릴리스를 재개할 수 있는지다.

## 확인 범위

GeekNews가 정리한 GitHub 장애의 영향 범위와 개발 인프라 의존성 분석, 이전 대안 및 완화 방안을 토대로 작성했다. 장애 원인을 AI 에이전트 사용 증가, 인프라 이전 또는 내부 구조 중 하나로 단정할 근거는 확인되지 않았으며, 개별 대체 서비스의 성숙도와 정책에 대한 평가는 프로젝트의 요구 조건과 조사 시점에 따라 달라질 수 있다.
