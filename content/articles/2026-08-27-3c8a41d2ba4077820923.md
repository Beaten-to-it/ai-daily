## 무엇이 있었나

AWS가 Amazon Bedrock AgentCore의 에이전트와 다른 AWS 계정에 있는 Amazon Bedrock Knowledge Bases를 연결하는 아키텍처를 소개했다. 예시 구성에서는 에이전트와 데이터 워크로드를 별도 계정에 두고, 지식 베이스가 Amazon Redshift Serverless의 구조화된 데이터를 조회한다. 원본 데이터를 에이전트 계정으로 복사하지 않는 방식이다.

AWS 설명에 따르면 지식 베이스의 리소스 정책은 계정 간 `Retrieve`와 `GetDocumentContent`를 지원하지만, 답변 생성까지 수행하는 `RetrieveAndGenerate`는 지원 작업에 포함되지 않는다. 이에 전용 도구가 데이터 계정의 최소 권한 IAM 역할을 AWS STS로 임시 인수한 뒤 `RetrieveAndGenerate`를 호출하도록 구성했다.

구현 방식은 두 가지다. 하나는 AgentCore Runtime에서 Strands Agents SDK 기반 Python 코드가 에이전트 실행 흐름을 관리하는 형태다. 다른 하나는 선언형 AgentCore Harness가 관리형 실행 흐름을 맡고, AgentCore Gateway와 AWS Lambda를 통해 지식 베이스를 호출하는 형태다. 전자는 오케스트레이션과 도구 동작을 세밀하게 제어할 때, 후자는 구성 중심의 관리형 운영을 선호할 때 적합하다는 설명이다.

AWS는 모든 요청에 에이전트가 필요한 것은 아니라고 강조했다. 검색 결과만 필요하면 계정 간 `Retrieve`를, 항상 하나의 생성 답변만 필요하고 도구 선택이나 다단계 추론이 없다면 애플리케이션 또는 Lambda에서 역할을 인수해 `RetrieveAndGenerate`를 직접 호출하는 방안을 먼저 검토하라고 권고했다.

## 왜 중요한가

국내 기업도 보안·조직·비용 관리 목적으로 AI 서비스 계정과 데이터 계정을 분리하는 멀티 계정 구조를 많이 사용한다. 이번 패턴은 데이터 복제 없이 계정 경계를 유지하면서 생성형 AI 에이전트가 통제된 기업 데이터에 접근하는 방법을 구체화했다는 데 의미가 있다.

특히 계정 분리 자체만으로 보안이 완성되는 것은 아니라는 점이 중요하다. 전용 교차 계정 역할의 권한을 특정 지식 베이스와 모델 자원으로 제한하고, 장기 실행 환경에서는 갱신 가능한 STS 자격 증명을 사용해야 한다. 또한 생성된 SQL과 답변은 비결정적일 수 있으므로 조회 건수·기간·정렬 조건을 명시하고, 중요한 업무 사실은 원본 데이터 및 직접 도구 응답과 대조해야 한다.

조직은 에이전트 도입 여부부터 판단한 뒤, 필요할 때만 코드 기반의 높은 제어력과 Harness 기반의 운영 편의성 사이에서 선택할 수 있다. 이는 불필요한 에이전트 복잡성과 운영 비용을 줄이는 설계 기준으로도 활용할 수 있다.

## 확인 범위

AWS ML 블로그에 공개된 아키텍처, 요청 흐름, IAM 경계, 두 AgentCore 구현 방식과 운영 권고를 확인했다. 두 방식은 AWS가 일반 제공되는 경로라고 설명했으며, 구체적인 배포 절차는 별도의 공개 GitHub 예제에 위임돼 있다.

다만 실제 환경의 권한 정책, 리전별 모델 지원, CLI 요구 버전, 비용과 성능은 계정 구성 및 서비스 변경에 따라 달라질 수 있다. 이 글에서는 예제 배포를 직접 재현하거나 생성 답변의 정확도와 두 방식의 성능을 독립적으로 검증하지 않았다.
