## 무엇이 있었나

벤저민 아계쿰과 파비오 산토스 연구진이 대규모언어모델(LLM)을 이용해 Infrastructure-as-Code(IaC)를 반복 수정할 때 기존에 통과했던 보안 검사가 다시 실패하는 현상을 분석했다.

연구진은 IaC-Eval 벤치마크의 시나리오 실행 기록 5,968건을 조사했다. 이 가운데 연속된 수정 단계 양쪽에 Checkov 검사 결과가 존재하는 전환 4,440건을 바탕으로 30개 CIS 보안 검사 항목의 변화를 추적했다.

포괄적인 판정 방식에서는 전체 시나리오의 13.8%에서 한 차례 이상 보안 회귀가 관찰됐다. 다만 여러 리소스가 함께 평가되면서 생기는 측정상 착시를 배제한 엄격한 방식에서는 비율이 3.3%로 낮아졌다. 연구진은 이 수치를 반복 수정 과정에서 발생하는 보안 회귀의 보수적인 추정치로 제시했다.

회귀 사례의 주요 원인은 리소스 구조 변경으로, 분류된 원인의 79.0%를 차지했다. 보안 회귀가 발생한 수정 단계에서는 코드 변경량이 2.6배 많았으며, 엄격한 판정 기준의 검사 결과 변동성도 4.9배 높았다. 포괄적 기준에서 발견된 회귀 가운데 36.6%는 평균 1.2회의 추가 수정 후 해소됐다. 연구진은 실험 조건에서 세 번째 반복 단계를 적절한 중단 시점으로 평가했다.

## 왜 중요한가

LLM 기반 코드 수정이 한 문제를 해결하면서 이미 충족한 보안 조건을 훼손할 수 있다는 점을 수치로 보여준 연구다. 특히 Terraform 같은 IaC는 클라우드 권한과 네트워크, 저장소 설정을 직접 정의하므로 작은 회귀도 실제 인프라의 보안 수준에 영향을 줄 수 있다.

국내 기업이 생성형 AI를 개발·운영 자동화에 도입할 때도 마지막 결과만 검사해서는 수정 과정의 보안 저하를 놓칠 수 있다. 각 반복 단계마다 보안 검사를 다시 수행하고, 변경량이 크거나 리소스 구조가 바뀐 경우에는 추가 검토하는 방식이 필요하다는 근거를 제공한다. 반복 횟수를 무조건 늘리는 것보다 적절한 중단 기준을 두는 것도 중요하다.

## 확인 범위

이번 기사는 arXiv에 공개된 논문의 서지 정보와 초록을 기준으로 작성했다. 논문은 ESEM 2026에 채택됐다고 명시돼 있으나, 여기에 제시된 수치와 결론은 해당 연구의 벤치마크·모델 구성·최대 5회 수정이라는 실험 조건에 한정된다.

엄격한 판정에서 회귀 비율이 크게 낮아진 만큼, 포괄적 기준의 결과를 모두 실제 보안 악화로 해석해서는 안 된다. 세 번째 반복이 최적이라는 결론 역시 모든 모델이나 실제 운영 환경에 그대로 적용된다고 확인된 것은 아니다.
