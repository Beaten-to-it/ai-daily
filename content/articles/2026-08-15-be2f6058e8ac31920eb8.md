## 무엇이 있었나

MCP 2026-07-28 사양에서 프로토콜의 중심 구조가 세션 기반 양방향 연결에서 상태 비저장 요청·응답 방식으로 바뀌었다. 초기화 절차와 `Mcp-Session-Id`가 제거되고, 요청 처리에 필요한 정보가 각 요청에 포함된다. 이에 따라 원격 MCP 서버를 로드밸런서 뒤에서 여러 인스턴스로 운영하기 쉬워졌다.

서버가 작업 도중 사용자 입력을 추가로 받아야 하는 상황에는 다중 왕복 요청(MRTR)이 도입됐다. 라우팅과 캐싱, 분산 추적을 위한 메타데이터도 보강됐다. 확장 기능은 코어와 별도로 개발하고 버전을 관리할 수 있는 정식 체계로 승격됐으며, MCP Apps와 Tasks가 이 구조를 활용한다.

도구 스키마는 JSON Schema 2020-12를 전반적으로 지원한다. 반면 Roots, Sampling, Logging은 폐기 예정으로 전환됐다. 기능을 제거하기 전에 최소 12개월의 유예 기간을 두는 공식 폐기 정책도 마련됐다.

Codex CLI에서는 0.147.0부터 새 사양 지원이 구현됐지만 현재는 기능 플래그를 켜야 한다. 새 사양을 지원하지 않는 서버에는 기존 초기화 방식으로 전환하는 호환 경로가 제공된다. Claude Code 역시 최신 방식의 서버 탐색과 기존 방식으로의 전환을 포함한 이행 작업이 진행 중인 것으로 소개됐다.

## 왜 중요한가

국내에서 MCP 서버를 구축하거나 운영하는 개발팀에는 인프라 구성이 단순해질 가능성이 크다. 세션 고정이나 공유 세션 저장소에 대한 의존을 줄이고, 일반적인 HTTP 로드밸런싱과 API 게이트웨이, 캐시, OpenTelemetry 기반 관측 체계를 활용하기 쉬워지기 때문이다.

다만 프로토콜 수준의 세션이 사라져도 애플리케이션 상태까지 없어지는 것은 아니다. 여러 도구 호출에 걸쳐 상태를 유지해야 한다면 식별자를 명시적으로 반환하고 다음 요청의 인자로 전달하는 식으로 서버와 도구를 설계해야 한다.

기존 구현이 세션이나 종전 Tasks API에 의존한다면 이전 작업이 필요하다. 새 구조의 이점은 클라이언트와 서버가 모두 2026-07-28 사양을 지원할 때 온전히 사용할 수 있으므로, 당분간은 구형·신형 프로토콜을 함께 지원하는 점진적 전환이 현실적인 선택이다.
