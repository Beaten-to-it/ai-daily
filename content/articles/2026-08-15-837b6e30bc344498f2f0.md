## 무엇이 있었나

GeekNews는 AI 코딩 도구를 활용한 개발 방식인 ‘넓게 만들고, 좁게 출시하기’를 소개했다. 처음부터 작업을 여러 PR로 나누기보다 하나의 브랜치에서 기능을 종단 간으로 구현하고, 데모나 미리보기 배포로 제품을 검증한 다음 실제 코드에 드러난 경계에 따라 작은 PR로 재구성하는 접근이다.

이 방식도 구현 전 설계와 검증을 전제로 한다. 새로운 구조라면 명세를 코드보다 먼저 공유하고, 구현이 끝난 뒤에는 각 PR이 독립적으로 검토·병합될 수 있도록 나눈다. 실제 의존성이 있을 때만 PR을 쌓으며, 기존 코드 삭제는 새 경로가 준비된 후 별도 PR로 처리한다.

AI는 구현과 브랜치 재구성에 드는 비용을 줄이지만, 미묘한 정확성이나 장기적인 API 설계, 제품 적합성을 판단하는 일까지 대신하지는 못한다는 것이 글의 핵심 전제다. 작은 PR은 사람이 AI 작성 코드를 읽고 이해하며 소유하는 과정에도 도움이 된다.

## 왜 중요한가

AI 도입으로 코드 생성 속도가 빨라져도 리뷰와 제품 판단에 필요한 시간은 같은 비율로 줄지 않는다. 따라서 구현 속도 자체보다 사람이 검토할 수 있는 단위로 변경을 정리하고, 잘못된 UI나 API 설계를 코드 리뷰 전에 발견하는 과정이 더 중요해진다.

이 접근은 백엔드와 프런트엔드를 함께 수정하는 기능이나 완성 전에는 적절한 경계를 알기 어려운 리팩터링에 활용할 수 있다. 작은 PR은 변경별 리뷰와 롤백을 쉽게 하지만, 의존 PR 수정에 따른 연쇄 리베이스 비용이 발생할 수 있다. 모든 PR을 한꺼번에 병합하면 리뷰 편의는 얻어도 점진적 출시 효과는 제한된다.

배포 순서가 엄격한 데이터베이스 마이그레이션이나 모든 변경을 동시에 내보내야 하는 기능에는 적용하기 어렵다. 결국 AI가 분할 작업을 지원할 수는 있어도 무엇을 언제 병합할지는 개발자와 팀이 결정해야 한다.

## 확인 범위

제공된 GeekNews 게시물에 정리된 개발 절차, 적용 사례, 장단점을 기준으로 작성했다. 게시물이 소개한 원 출처의 전문과 개별 사례의 실제 저장소·PR·운영 결과는 별도로 대조하지 않았으며, 댓글에 담긴 독자 의견은 확인된 방법론의 사실로 간주하지 않았다.
