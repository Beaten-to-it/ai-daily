## 무엇이 있었나

GeekNews가 소개한 소규모 실험에서 코딩 에이전트의 도구 선택과 성능이 작업 유형, 저장소, 검색 결과의 표현 방식에 따라 달라졌다. Claude 모델 3종에 텍스트 검색 도구인 grep과 코드의 정의·참조 등을 찾는 LSP 기반 도구를 제공했지만, 단순히 코드 위치를 찾는 작업에서는 대부분 grep을 사용했다. 의미 기반 탐색을 먼저 사용하도록 강제한 비교에서는 성공률이 100%에서 89%로 낮아졌다.

LSP 기반 탐색의 장점도 확인됐다. 전체 호출자를 찾는 작업에서는 실제 참조와 무관한 일치를 걸러내 정밀도 1.00을 기록했다. grep의 정밀도는 0.76이었다. 다만 실제 참조를 얼마나 빠짐없이 찾았는지를 나타내는 재현율은 두 방식 모두 약 0.66으로, 정밀도 향상이 탐색의 완전성까지 보장하지는 않았다.

도구가 반환하는 정보도 결과에 영향을 줬다. 여러 파일을 수정하는 이름 변경 작업에서 LSP 결과에 위치와 함께 소스 코드를 담자 첫 시도 성공률이 67%에서 83%로 올랐다. 후속 파일 읽기는 15.2회에서 3.2회로 줄었다. 같은 비교에서 grep의 첫 시도 성공률은 100%였다.

## 왜 중요한가

국내 개발팀이 코딩 에이전트에 새 도구를 연결할 때도 도구의 기능 목록만으로 효과를 판단하기 어렵다는 점을 보여준다. 정확한 코드 위치를 찾아도 에이전트가 내용을 확인하기 위해 파일을 반복해서 열어야 한다면 전체 작업 비용은 커질 수 있다. 검색 결과에 다음 판단에 필요한 코드가 포함되는지가 실제 성능을 좌우할 수 있다는 의미다.

수정 대상의 범위도 중요하다. 실제 코드 참조를 구별해야 하는 작업에서는 의미 기반 탐색이 유용하지만, 주석이나 문자열까지 바꿔야 한다면 텍스트 검색이 필요할 수 있다. 이번 결과는 도구 도입 효과를 실제 사용 여부, 작업 성공률, 토큰 소비량과 함께 평가할 필요성을 시사한다.

## 확인 범위

이 기사는 제공된 GeekNews 본문을 근거로 작성했다. 원 실험의 코드나 실행 기록을 별도로 검증한 것은 아니다.

소개된 실험은 소수의 Python·TypeScript 저장소와 작은 작업 집합을 대상으로 조건별 2~3회 실행한 예비 연구다. 토큰 사용량은 두 방식이 모두 성공한 경우에만 비교했다. 따라서 제시된 수치를 모든 코딩 작업의 기대 성능으로 받아들이기는 어렵다.

시험 대상은 LSP의 참조·정의·문서 심벌 기반 탐색이었다. LSP 자체의 이름 변경 기능, 진단, 코드 액션은 제외됐다. 편집 작업도 표준 SWE-bench 평가가 아니므로 LSP 전반의 우열이나 모델의 종합 코딩 능력을 판정하는 근거로 일반화할 수 없다. 모델이 학습 과정에서 익숙해진 도구를 선호한다는 설명 역시 검증된 원인이 아닌 가설이다.
