## 무엇이 있었나

NVIDIA의 AI 안전·보안 연구진은 AI 에이전트 기술 스택을 모델, 에이전트 하네스, 오케스트레이션 계층, 보안 런타임, 추론 인프라로 구분하고 각 계층에 필요한 보안 역할을 제시했다.

핵심 주장은 에이전트의 행동을 유도하는 통제와 실제 권한을 제한하는 통제를 분리해야 한다는 것이다. 프롬프트와 모델 안전장치, 하네스 로직은 에이전트가 무엇을 시도할지 조정할 수 있지만 강제력이 있는 보안 경계는 아니다. 최종 권한은 신원과 정책, 자격 증명, 격리, 감사 기록을 관리하는 런타임과 인프라에 둬야 한다는 설명이다.

NVIDIA는 최소 권한, 심층 방어, 명시적 승인, 격리, 감사 가능성 같은 기존 시스템 보안 원칙을 에이전트에도 적용할 것을 권고했다. 모든 외부 상태 변경을 정책 집행 지점에서 검사하고, 자격 증명은 작업 범위에 맞춰 짧게 발급하며, 에이전트와 하위 에이전트가 스스로 권한을 늘리지 못하도록 해야 한다는 내용도 포함됐다.

위험 수준은 격리된 사전 운영 작업부터 승인된 서비스 연동, 운영 환경 변경, 안전장치를 줄인 적대적 시험까지 네 단계로 나뉜다. 권한과 잠재적 영향이 커질수록 접근 범위를 좁히고, 작업 직전에 정책을 다시 평가하며, 감독과 복구 체계 및 독립적인 감사 기록을 강화하도록 제안했다.

## 왜 중요한가

국내 기업에서도 코딩과 업무 자동화, 클라우드 운영에 AI 에이전트를 연결하는 사례가 늘면 프롬프트 지침만으로는 충분한 통제가 어렵다. 에이전트가 읽는 문서나 메시지, 도구 결과에 악의적이거나 잘못된 내용이 포함되면 행동 경로가 바뀔 수 있기 때문이다.

따라서 운영 시스템에 에이전트를 투입할 때는 모델의 판단과 무관하게 파일 접근, 네트워크 요청, API 호출, 데이터 변경을 제한하는 별도 집행 계층이 필요하다. 특히 장기 자격 증명을 에이전트에 직접 제공하기보다 작업별 단기 권한을 발급하고, 중요한 작업에는 사람의 승인과 독립적인 검증을 두는 방식이 사고 범위와 복구 비용을 줄이는 데 도움이 된다.

## 확인 범위

이 기사는 NVIDIA Developer가 공개한 기술 블로그의 계층 구분, 보안 원칙, 위험별 운영 방안을 바탕으로 작성했다. 해당 글은 NVIDIA 연구진의 관점과 OpenShell 중심의 설계를 설명하며, 모든 AI 에이전트 제품에 적용되는 공식 산업 표준을 발표한 것은 아니다. 글에서 언급한 외부 기관의 개별 사고 사례와 NVIDIA 기술의 성능·보안 효과는 원 출처나 독립적인 평가 자료로 별도 검증하지 않았다.
