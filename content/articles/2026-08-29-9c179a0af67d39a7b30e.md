## 무엇이 있었나

AWS가 Amazon SageMaker Feature Store에 `BatchWriteRecord`와 `ListRecords` API를 추가했다.

`BatchWriteRecord`는 여러 피처 그룹에 걸쳐 한 번에 최대 25개 레코드를 기록한다. 레코드별로 성공 여부를 처리하는 부분 성공 방식을 채택했으며, 개별 TTL 설정과 기존 `PutRecord`의 이벤트 시간 기반 정렬 규칙도 지원한다. 처리되지 않았거나 오류가 발생한 레코드는 응답에 따로 반환되므로 해당 항목만 재시도할 수 있다.

`ListRecords`는 피처 그룹에 저장된 활성 레코드의 식별자를 페이지 단위로 조회하는 기능이다. DynamoDB 기반 Standard 계층과 Redis 기반 In-Memory 계층에서 모두 작동하며, 삭제됐거나 만료된 레코드는 결과에서 제외한다. 전체 피처 값이 필요하면 반환된 식별자로 `GetRecord`나 `BatchGetRecord`를 별도로 호출해야 한다.

## 왜 중요한가

이번 기능은 대규모 ML 피처 파이프라인의 운영 부담을 줄이는 데 의미가 있다. 기존에는 레코드마다 개별 API 요청이 필요했지만, 일괄 쓰기를 이용하면 연결과 호출 횟수를 줄일 수 있다. 다만 일부 레코드만 실패할 수 있으므로 재시도 로직은 전체 요청이 아니라 실패 항목을 기준으로 설계해야 한다.

레코드 탐색 기능은 데이터 정리와 삭제 검증에도 유용하다. 특히 별도의 오프라인 저장소가 기본 제공되지 않는 In-Memory 계층에서는 식별자를 잃어버린 레코드를 찾아내기 어려웠다. 이제 운영자는 활성 식별자를 열거한 뒤 고아 레코드를 정리하거나, 여러 피처 그룹에서 특정 사용자의 데이터가 삭제됐는지 점검하는 절차를 구성할 수 있다. 국내에서 AWS 기반 추천·이상거래 탐지·실시간 추론 시스템을 운영하는 팀에도 처리량 개선과 데이터 수명주기 관리 측면에서 직접적인 변화다.

## 확인 범위

AWS ML 블로그에 게시된 발표와 기술 설명을 기준으로 두 API의 기능, 제한, 저장 계층 지원 범위를 확인했다. `BatchWriteRecord`는 요청당 최대 25개 항목을 지원하고 트랜잭션처럼 전체 롤백하지 않는다. `ListRecords`는 한 페이지에 최대 100개의 식별자를 반환하며, 조회 도중 데이터가 변경되면 중복이나 누락이 생길 수 있고 결과 순서도 보장되지 않는다.

실제 리전별 제공 여부, 요금 영향, 환경별 성능 향상 폭은 제공된 자료에서 확인하지 않았다. 도입 전에는 사용하는 AWS 리전의 최신 문서와 서비스 할당량, IAM 권한, SDK 버전을 별도로 점검할 필요가 있다.
