## 무엇이 있었나

AWS가 온프레미스와 다른 클라우드에서 실행되는 AI 에이전트의 원격 측정 데이터를 Amazon Bedrock AgentCore Observability로 전송하는 구성 방법을 공개했다. AgentCore 런타임 밖의 에이전트는 관측성이 자동 설정되지 않기 때문에 별도의 계측과 인증, 라우팅 설정이 필요하다.

공개된 방식은 AWS Distro for OpenTelemetry(ADOT)의 자동 계측을 이용해 에이전트의 추론 과정과 도구 호출, 모델 호출, 지연 시간, 토큰 사용량 등을 수집한다. 수집한 데이터는 IAM 자격 증명과 SigV4 인증을 거쳐 Amazon CloudWatch의 OTLP 수집 엔드포인트로 보내고, AgentCore Observability 대시보드에서 세션과 추적 정보를 통합해 확인한다.

AWS는 Strands Agents로 만든 예제를 비AWS 서버와 Google Cloud Shell에서 시험했다. 두 환경의 에이전트가 전송한 세션과 추적, 스팬, 지연 시간 및 토큰 지표가 AgentCore 대시보드에 표시됐다고 설명했다. 같은 패턴은 OpenTelemetry와 호환되는 다른 에이전트 프레임워크에도 적용할 수 있다고 밝혔다.

## 왜 중요한가

기업이 AI 에이전트를 온프레미스와 여러 클라우드에 분산 배치하면 실행 환경마다 모니터링 체계가 갈라질 수 있다. 이번 구성은 서로 다른 환경에서 발생하는 에이전트 데이터를 한곳에 모아 성능과 비용, 도구 사용, 응답 흐름을 점검할 수 있는 방법을 제시한다.

하이브리드·멀티클라우드 환경을 운영하는 한국 기업에도 의미가 있다. 기존 배포 위치를 유지하면서 중앙 관측 체계를 마련할 수 있기 때문이다. 다만 외부 환경에서는 OpenTelemetry 환경 변수와 AWS 인증을 직접 설정해야 하며, 운영 환경에서는 장기 액세스 키 대신 IAM Roles Anywhere나 자격 증명 연동처럼 임시 인증 정보를 사용하는 방안을 검토할 필요가 있다.

## 확인 범위

AWS가 게시한 기술 안내에서 구성 요소, 설정 절차와 비AWS 환경의 검증 결과를 확인했다. 검증 사례는 Strands Agents를 사용한 비AWS 서버와 Google Cloud Shell에 한정돼 있다. Azure를 비롯한 다른 환경과 프레임워크에서도 같은 방식이 적용될 수 있다고 AWS는 설명했지만, 각 조합의 실제 성능과 호환성은 이 자료만으로 확인되지 않는다.

또한 이 방식은 Amazon Bedrock, CloudWatch, AWS X-Ray 사용에 따른 비용이 발생할 수 있으며, 구체적인 운영 비용이나 대규모 환경에서의 성능 수치는 제시되지 않았다.
