## 무엇이 있었나

AWS는 Amazon SageMaker AI에서 운영하는 자체 호스팅 모델과 Amazon Bedrock의 관리형 모델을 하나의 에이전트 워크플로에서 사용하는 구축 사례를 공개했다. 예시 시스템은 Bedrock 기반 오케스트레이터가 요청을 분류한 뒤 예산 관리 에이전트 또는 금융 분석 에이전트로 전달하는 구조다. 금융 분석에는 SageMaker AI에 배포한 Qwen 3.5 9B 모델을 사용하고, 전체 워크플로는 Amazon Bedrock AgentCore Runtime에서 실행한다.

AWS는 SageMaker AI의 OpenAI 호환 엔드포인트를 Strands Agents와 연결할 때 인증 토큰을 요청마다 갱신하는 방법도 제시했다. 특히 이 경로에서는 Bedrock 모델 호출과 달리 토큰 사용량이 자동으로 추적되지 않으므로, OpenTelemetry의 사용자 정의 `gen_ai.chat` 스팬을 만들고 Strands의 실행 지표에서 입력·출력 토큰 수를 가져와 기록해야 한다고 설명했다. 스트리밍 응답에서 토큰 정보를 받으려면 vLLM 설정에 사용량 반환 옵션도 추가해야 한다.

## 왜 중요한가

기업이 모든 작업을 하나의 범용 모델에 맡기지 않고 비용, 데이터 위치, 업무 특성에 따라 서로 다른 모델을 조합할 수 있다는 점이 핵심이다. 국내 조직도 민감하거나 전문화된 작업은 SageMaker AI의 자체 호스팅 모델로 처리하고, 다른 작업은 Bedrock의 관리형 모델에 맡기는 혼합 구성을 검토할 수 있다.

운영 관점에서는 모델 연결 자체뿐 아니라 비용과 지연 시간을 추적할 수 있는 관측성이 중요하다. 이번 사례는 모델 제공 경로에 따라 자동 계측 범위가 달라질 수 있으며, 누락된 토큰 지표를 별도로 보완해야 실제 운영 단계에서 비용 변화와 성능 저하를 파악할 수 있음을 보여준다. 동시 실행 오류를 피하기 위해 호출마다 새 에이전트 인스턴스를 생성해야 한다는 구현상 주의점도 제시됐다.

## 확인 범위

AWS가 공개한 기술 게시물에서 아키텍처, 배포 절차, 인증 방식과 관측성 보완 방법을 확인했다. 사용된 모델과 인스턴스 구성, 예시 토큰 수는 해당 데모 환경에 관한 것으로 다른 리전이나 워크로드에서 동일한 성능·비용을 보장하지 않는다. Bedrock 모델 지원 여부는 AWS 리전에 따라 달라질 수 있으며, 게시물의 금융 분석 기능 역시 투자 성과나 분석 정확성을 검증한 자료가 아니라 통합 방법을 설명하기 위한 사례다.
