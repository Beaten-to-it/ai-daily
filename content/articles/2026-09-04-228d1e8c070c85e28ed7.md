## 무엇이 있었나

AWS가 개발자 PC에서 실행되는 Codex를 고객 AWS 계정의 LiteLLM 게이트웨이와 Amazon Bedrock에 연결하는 구축 지침을 공개했다. 제시된 구조에서는 Amazon ECS의 AWS Fargate에서 LiteLLM을 운영하고, Codex의 Responses API 요청을 승인된 OpenAI 모델로 전달한다.

LiteLLM은 모델 인증과 라우팅, 사용자·팀별 키, 예산 및 호출량 제한, 사용량 기록을 담당한다. 파일 읽기나 명령 실행 같은 도구 작업은 게이트웨이가 아니라 개발자 PC의 Codex 샌드박스와 승인 정책 아래에서 계속 수행된다.

참조 구성에는 Application Load Balancer, AWS WAF, PostgreSQL용 Amazon RDS, AWS Secrets Manager, AWS KMS, CloudWatch, Amazon ECR 등이 포함된다. AWS는 텍스트 응답만 확인해서는 호환성을 판단하기 어렵다며, 이전 응답을 이용한 의미적 연속성, 스트리밍, 함수 호출까지 검증하는 테스트 절차도 제시했다.

운영 방식의 대안도 소개됐다. AWS 기본 신원 및 감사 기능만으로 충분하다면 IAM Identity Center를 통한 Amazon Bedrock 직접 연결이 더 단순하다. 자체 게이트웨이 운영 부담을 줄이려면 Portkey와 같은 관리형·하이브리드 방식도 검토할 수 있다.

## 왜 중요한가

기업이 코딩 에이전트를 조직 단위로 도입하면 모델 사용 권한과 비용, 요청량, 이용 주체를 일관되게 관리해야 한다. 이번 구성은 Codex의 로컬 실행 경계를 유지하면서 모델 요청 경로에는 중앙 정책을 적용하는 방법을 구체화했다는 점에서 의미가 있다.

한국 기업에도 데이터 처리 위치와 접근 권한, 비용 통제, 감사 가능성을 함께 설계할 수 있는 참고 사례가 된다. 다만 LiteLLM 방식을 선택하면 게이트웨이 가용성, 데이터베이스 수명주기, 버전 갱신, 장애 대응, 용량 계획을 조직이 직접 책임져야 한다. 배포 리전별 모델 제공 여부와 각종 AWS 자원의 비용도 사전에 확인해야 한다.

## 확인 범위

AWS ML이 공개한 기술 안내문을 기준으로 아키텍처, 배포 구성, 검증 항목과 운영상 선택지를 확인했다. 게시물은 미국 동부 버지니아 북부 리전에서 특정 게이트웨이 별칭을 사용한 실제 배포 및 Responses API 계약 검증이 통과했다고 설명한다.

다만 제시된 검증은 부하 시험이 아니다. 동시 에이전트 세션, 장시간 스트리밍, 요청 취소, 키 폐기, 장애 복구, 최대 예상 트래픽은 운영 도입 전에 별도로 시험해야 한다. 모델 가용성과 비용, Portkey의 라이선스·데이터 처리 조건 등은 계정, 리전, 계약 시점에 따라 달라질 수 있다.
