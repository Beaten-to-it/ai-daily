## 무엇이 있었나

GitHub Actions의 OIDC 토큰 발급 권한을 지금보다 세밀하게 제한해야 한다는 보안 제안이 나왔다. 현재 워크플로에 `id-token: write` 권한을 부여하면 작업이 실행 중 임의의 audience를 지정해 토큰을 요청할 수 있다. 이 때문에 같은 작업에서 실행되는 취약하거나 악성인 서드파티 코드가 원래 의도하지 않은 외부 서비스용 토큰을 발급받을 가능성이 있다는 지적이다.

제안의 핵심은 `id-token: [pypi]`처럼 작업마다 허용할 audience를 미리 선언하는 방식이다. 예를 들어 PyPI 배포 작업에는 PyPI용 토큰만 허용해, 해당 작업이 AWS STS용 토큰을 요청하는 상황을 발급 단계에서 차단하자는 것이다. 동적 audience가 꼭 필요한 경우에는 기존의 포괄적 권한을 유지할 수 있다는 구상도 함께 제시됐다.

이는 audience를 작업 정의에 정적으로 선언하는 GitLab CI/CD와 달리, GitHub Actions가 토큰 요청 시점에 audience를 선택하도록 한 차이에서 출발한다. 다만 이 내용은 GitHub가 발표한 기능 변경이 아니라, 현행 권한 모델을 개선하자는 외부의 제안이다.

## 왜 중요한가

OIDC는 CI/CD가 장기 보관된 비밀키 없이 PyPI, 클라우드, 서명 서비스 등에 워크로드 신원을 증명하도록 돕는다. 그러나 토큰 발급 권한의 범위가 넓으면 한 연동에서 침해된 코드가 다른 연동으로 공격을 확장할 여지가 생긴다.

오픈소스 패키지 배포와 클라우드 배포를 함께 자동화하는 한국 개발팀에도 직접적인 문제다. audience 허용 목록이 도입되면 최소 권한 원칙을 워크플로 선언에 반영하고, 서로 독립적인 외부 서비스 사이의 공격 전환 가능성을 줄일 수 있다. 다만 audience 제한만으로 모든 위험이 사라지는 것은 아니며, 외부 서비스가 audience와 워크플로·저장소 등 신원 관련 클레임을 올바르게 검증해야 한다.

## 확인 범위

제공된 GeekNews 기사에서 현행 GitHub Actions와 GitLab CI/CD의 audience 지정 방식, 제안된 권한 문법, 예상 보안 효과를 확인했다. GitHub가 이 기능을 도입하기로 결정했다거나 구체적인 출시 계획을 공개했다는 내용은 확인되지 않았다. 댓글에 제시된 대안과 평가는 공식 결론이 아닌 참여자 의견으로 구분했다.
