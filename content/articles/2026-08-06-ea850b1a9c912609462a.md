## 무엇이 있었나

AWS가 Amazon Bedrock AgentCore에서 구동하는 AI 에이전트에 사용자 PC의 로컬 MCP 도구를 연결하는 ‘MCP 브리지’ 구현 방식을 공개했다. 클라우드의 에이전트가 로컬 엑셀 파일이나 Git 저장소 등에 접근해야 할 때 생기는 통신 공백을 메우는 구조다.

구성 요소는 AgentCore 런타임, 브라우저 확장 프로그램, 로컬 MCP 브리지, MCP 서버 등 네 가지다. 에이전트가 보낸 MCP JSON-RPC 요청은 웹소켓을 통해 확장 프로그램에 전달되고, 크롬의 네이티브 메시징을 거쳐 로컬 브리지와 MCP 서버로 이동한다. 처리 결과는 같은 경로를 역순으로 돌아간다. 로컬 MCP 서버와 브리지 사이에서는 표준 입출력 방식이 사용된다.

접속에는 로컬 AWS 자격 증명으로 생성한 SigV4 서명 웹소켓 URL을 이용한다. AWS 설명에 따르면 이 URL의 유효기간은 5분이며, 자격 증명은 사용자 기기를 벗어나거나 브라우저로 전달되지 않는다. 브리지는 여러 요청을 동시에 처리할 수 있도록 비동기 큐를 사용하며, MCP 서버를 상시 실행되는 하위 프로세스로 관리한다.

AWS는 예제 코드도 함께 공개했다. 다만 시연용 구현에 포함된 보안 장치는 확장 프로그램 출처 제한, 단기 유효 웹소켓 URL, 프로세스 분리 등으로 한정된다. 실제 서비스에는 JWT 인증, 메시지 서명, 접근 가능한 디렉터리의 명시적 제한, 도구 호출 감사 기록, Amazon Bedrock Guardrails 등을 추가하라고 권고했다.

## 왜 중요한가

클라우드에 중앙 배포한 AI 에이전트와 사내 PC에 남아 있는 파일·도구를 연결할 수 있다는 점이 핵심이다. 국내 기업도 엑셀 중심의 재무 업무나 로컬 개발 저장소처럼 데이터를 곧바로 클라우드로 옮기기 어려운 환경에서 이 구조를 검토할 수 있다. 기존 표준 입출력 기반 MCP 서버를 수정하지 않고 연결할 수 있어 도구 확장 부담도 줄일 수 있다.

반면 클라우드 에이전트의 명령이 사용자 권한으로 로컬에서 실행된다는 점은 새로운 보안 경계를 만든다. 프롬프트 인젝션이나 과도한 파일 접근이 민감 정보 노출로 이어질 수 있으므로, 실제 도입 시에는 접근 허용 범위와 호출 기록, 사용자 승인 절차를 제품 설계 단계부터 구체화해야 한다.

## 확인 범위

아키텍처, 통신 흐름, 예제 구성과 보안 권고는 AWS가 공개한 기술 문서에서 확인했다. 예제 코드의 실제 동작, 운영 환경에서의 성능과 호환성은 별도로 검증하지 않았다. AWS가 언급한 사내 재무 AI 도우미의 이용 실적과 운영 경험 역시 회사 측 설명에 근거하며, 독립적으로 확인된 수치는 아니다.
