## 무엇이 있었나

AWS가 소스 코드를 분석해 아키텍처 다이어그램을 생성하고 검색 가능한 문서로 관리하는 자동화 방식을 소개했다. 핵심은 Amazon Bedrock AgentCore에서 실행되는 에이전트가 .NET 코드베이스를 분석하고 클래스·시퀀스·상태·컴포넌트·활동 다이어그램 등을 Mermaid 형식으로 만드는 구조다.

에이전트는 생성 결과의 문법을 검사하고 오류가 발견되면 스스로 수정한 뒤 SVG로 변환한다. 산출물과 설명 메타데이터는 Amazon S3에 저장되며, Amazon Bedrock Knowledge Bases가 이를 수집해 자연어 검색과 검색 증강 생성(RAG)에 활용한다. AWS CodePipeline과 CodeBuild를 연결하면 메인 브랜치에 코드가 반영될 때마다 문서 생성과 지식 기반 갱신을 실행할 수 있다.

AWS는 이 방식을 글로벌 금융 서비스 기업과 검증했으며, 전자거래 플랫폼의 여러 저장소에서 운영하고 있다고 밝혔다. 게시물에 따르면 해당 기업은 20개 저장소를 대상으로 매주 140개가 넘는 다이어그램을 자동 생성한다.

## 왜 중요한가

아키텍처 문서는 코드보다 늦게 갱신되기 쉬워 실제 시스템과 설명이 어긋나는 경우가 많다. 코드 변경을 문서 생성 파이프라인과 직접 연결하면 개발자 온보딩, 장애 분석, 보안 검토와 규제 감사에 필요한 최신 자료를 유지하는 부담을 줄일 수 있다.

특히 여러 마이크로서비스를 운영하거나 담당자 교체가 잦은 국내 조직에는 서비스 의존성과 메시지 흐름을 자연어로 찾을 수 있다는 점이 의미가 있다. 다만 생성형 AI가 만든 다이어그램이 코드의 의미와 운영 환경을 완전히 이해한다고 볼 수는 없다. 중요 시스템에서는 문법 검증뿐 아니라 설계자 검토, 접근 권한 통제, 민감한 소스 코드의 처리 정책도 함께 마련해야 한다.

## 확인 범위

AWS ML 블로그에 공개된 구성 요소, 처리 흐름, 사례와 AWS가 제시한 운영 성과를 확인했다. 실제 고객사는 공개되지 않았으며, 신뢰도·비용 절감·개발 생산성 등 정량 수치는 AWS와 고객사의 내부 측정 결과로 소개된 값이다. 독립적인 제3자 평가나 원시 측정 자료까지 확인된 것은 아니므로 다른 조직에서 같은 효과가 재현된다고 단정할 수 없다. 실제 비용과 모델 이용 가능 지역 역시 선택한 모델, 코드 규모, 실행 주기와 AWS 요금에 따라 달라질 수 있다.
