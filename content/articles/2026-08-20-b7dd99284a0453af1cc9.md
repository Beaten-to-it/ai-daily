## 무엇이 있었나

AWS가 해결된 IT 서비스 관리(ITSM) 티켓에서 지식 문서와 근본 원인 분석 자료를 생성하고, 기존 지식 기반까지 정비하는 ‘KnowledgeForge’의 설계와 구현 방식을 공개했다.

KnowledgeForge는 서로 연계된 생성·정비 시스템으로 구성된다. 생성 단계에서는 유사한 장애 티켓 묶음을 바탕으로 Amazon Bedrock의 Anthropic Claude Sonnet 4.5가 초안 문서를 만든다. 이때 고객별 Amazon S3 Vectors 인덱스에서 유사한 기존 문서 5개를 찾아 참고 자료로 제공한다. 기존 문서가 없으면 티켓 데이터만 사용하고, 생성된 절차에는 검토가 필요하다는 표시를 남긴다.

정비 단계에서는 문서를 유형별로 분류하고 중복 여부와 품질을 평가한 뒤, 기준에 못 미치는 내용을 개선한다. Amazon Titan Text Embeddings V2로 만든 1,024차원 임베딩과 Amazon S3 Vectors를 이용해 의미상 가까운 문서를 탐지한다. AWS가 제시한 초기 중복 판정 기준은 코사인 거리 0.05 이하, 즉 유사도 0.95 이상이며 상위 5개 결과를 비교하는 방식이다. 중복이 발견되면 무조건 새 문서를 버리지 않고 최신 문서를 남기고 오래된 문서를 비활성화한다.

전체 정비 과정은 AWS Step Functions의 분산 맵과 AWS Lambda로 조율한다. 문서 본문 대신 Amazon S3 위치 정보를 전달해 Step Functions의 상태 데이터 크기를 줄였으며, 고객별 배치 순서는 Amazon SQS FIFO 큐로 관리한다. 생성처럼 처리 시간이 긴 작업은 Amazon ECS와 AWS Fargate에서 수행한다.

품질 개선 전후에는 완전성, 실행 가능성, 구조, 일관성, 가독성 등 10개 항목을 가중 평가한다. 개선본의 점수가 원본보다 높을 때만 교체하며, 이미지와 링크는 임시 토큰으로 치환했다가 복원해 모델이 주소나 태그를 훼손하지 않도록 했다. 최종 게시 여부는 지식 관리자가 ServiceNow에서 검토하고 승인한다.

## 왜 중요한가

기업의 장애 대응 기록에는 증상과 원인, 실제 해결책이 남아 있지만 일반적으로 개별 티켓에 묻혀 재사용되기 어렵다. KnowledgeForge는 이 기록을 초안으로 전환하는 데서 그치지 않고, 중복 제거와 품질 평가, 사람의 승인까지 하나의 순환 구조로 연결했다는 점에서 의미가 있다.

국내 기업이 사내 헬프데스크나 고객 지원 지식 기반에 생성형 AI를 도입할 때도 참고할 만하다. 특히 고객별 벡터 인덱스·프롬프트·가드레일·암호화 키를 분리하고, 긴 본문 대신 저장 위치만 워크플로에 전달하며, 개선 결과가 실제로 나아졌을 때만 채택하는 방식은 데이터 격리와 운영 안정성을 함께 고려한 설계 사례다.

다만 자동화가 검토 책임을 대신하지는 않는다. AWS의 구조에서도 게시 결정은 사람이 맡는다. 또한 가드레일 API가 제한될 경우 가드레일 없이 다시 처리하도록 한 복원 전략은 가용성을 높이지만, 조직의 보안·규제 요구에 따라 실패 시 처리를 중단하는 방식이 더 적합할 수 있다.

## 확인 범위

AWS가 공개한 기술 설명을 기준으로 시스템 구성, 처리 흐름, 사용 서비스와 모델, 중복 판정의 초기 설정값을 확인했다. 성능 관련 결과는 AWS 내부 시험에서 관찰한 사례이며 보장된 서비스 수준이 아니다. 구체적인 처리량과 비용은 문서 크기, 모델 지연 시간, Amazon Bedrock 할당량 등에 따라 달라진다.

회로 차단기도 세 번의 연속 실패 뒤 작동하도록 설계됐지만, 실패 횟수가 실행 중인 Lambda 메모리에만 저장돼 동시 실행이나 여러 고객의 작업이 섞이는 환경에서는 항상 동작한다고 보장되지 않는다. 중복 판정 임계값 역시 AWS가 표본을 바탕으로 조정한 값이므로 다른 조직의 문서에는 별도 검증이 필요하다.
