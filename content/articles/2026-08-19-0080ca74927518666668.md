## 무엇이 있었나

Snowflake의 공개 저장소에서 누구나 작성할 수 있는 GitHub 이슈 제목을 통해 임의 명령을 실행할 수 있는 GitHub Actions 취약점이 발견됐다. 워크플로가 이슈 제목을 셸 명령에 직접 삽입하면서 명령어 주입이 가능해졌고, 접근 제한을 의도한 조건문도 이벤트 구조를 잘못 참조해 사실상 모든 이용자를 통과시켰다.

Wiz의 자율 보안 도구 Red Agent는 공격 문자열의 첫 실행이 실패하자 오류를 분석해 페이로드를 수정했고, 이후 GitHub Actions에 저장된 Jira 자격 증명을 확보해 유효성을 확인했다. 해당 자격 증명에는 Snowflake의 엔지니어링, 보안 규정 준수, 버그 바운티 관련 Jira 프로젝트를 읽을 수 있는 권한이 있었다.

취약점은 2026년 6월 18일 병합된 변경에서 도입됐다. 이 변경은 입력을 환경변수로 전달하고 `jq --arg`로 처리하던 기존 방식을 직접 문자열 보간으로 대체했다. 최종 커밋에는 Copilot Autofix가 공동 작성자로 기록됐으며, Copilot은 변경을 검사하고 문제가 없다고 판단한 것으로 전해졌다. 다만 실제 코드를 AI가 작성했는지는 확인되지 않았다.

Snowflake는 6월 23일 신고를 받은 당일 안전한 입력 처리 방식을 복원하고, 다음 날 노출된 Jira 토큰을 교체했다. 감사 로그 조사에서는 5일간의 노출 기간에 Wiz 외 제3자가 접근한 증거가 발견되지 않았다.

## 왜 중요한가

이번 사례는 AI 코딩 도구가 검토한 변경이라도 기존 보안 설계가 제거되거나 취약한 패턴이 재도입될 수 있음을 보여준다. 특히 GitHub Actions처럼 외부 입력과 조직 내부 자격 증명이 만나는 자동화 환경에서는 AI의 안전 판정만으로 보안 검토를 대신하기 어렵다.

한국 기업과 개발팀도 공개 이슈, 풀 리퀘스트, 댓글처럼 누구나 조작할 수 있는 값을 셸 명령에 직접 넣지 않아야 한다. 구조화된 데이터 처리와 환경변수 전달 방식을 유지하고, 워크플로 이벤트별 데이터 구조와 권한 조건을 실제 실행 환경에서 검증할 필요가 있다. 자격 증명의 권한과 유효기간을 최소화하면 침해가 발생했을 때 피해 범위도 줄일 수 있다.

또한 공격 자동화 도구가 실패한 페이로드를 스스로 수정해 짧은 시간 안에 자격 증명까지 검증했다는 점은 방어 속도의 중요성을 부각한다. 코드 병합 이후의 탐지와 대응뿐 아니라 병합 전 정적 분석, 외부 입력 추적, 비밀정보 접근 통제가 함께 작동해야 한다.

## 확인 범위

취약점의 발생 경위, 공격 방식, 접근 가능했던 Jira 권한, Snowflake의 패치와 토큰 교체, 감사 로그 조사 결과는 제공된 GeekNews 기사에서 확인했다. Copilot이 병합된 변경을 검사했다는 내용은 확인됐지만, 취약한 코드 자체가 AI로 작성됐는지는 불분명하다. 제3자 접근이 없었다는 판단 역시 Snowflake의 감사 로그 조사 결과에 근거하며, 본문에 제공되지 않은 독립 포렌식 자료까지 확인한 것은 아니다.
