## 무엇이 있었나

SQLite 취약점으로 등록된 CVE 6건을 실제 소스 코드와 대조하고 격리된 환경에서 재현한 결과, 보고서가 지목한 함수가 해당 버전에 없거나 코드 위치가 설명과 맞지 않는 사례가 확인됐다. 일부 개념 증명 코드는 정상적으로 끝났고, 나머지도 SQL 구문이나 JSON 파싱 단계에서 중단돼 주장된 use-after-free가 재현되지 않았다.

같은 계정이 작성한 권고문 55건을 조사한 결과, 54건은 조작된 내용으로 판단됐으며 나머지 1건도 실제 버그에 검증되지 않은 CVE 정보를 결합한 사례로 분류됐다. 그런데 이 가운데 일부는 NVD와 CISA 관련 데이터 보강 절차를 거치며 높은 위험 등급을 받았고, CVE-2026-51302는 한때 CVSS 10.0으로 평가됐다가 이후 7.6으로 낮아졌다.

## 왜 중요한가

CVE 점수에 따라 보안 티켓 생성과 패치 우선순위를 자동화하는 조직에서는 허위 정보도 즉시 운영 비용으로 이어질 수 있다. 존재하지 않는 함수나 재현되지 않는 오류를 조사하느라 시간을 쓰는 동안 실제 취약점 대응이 늦어질 가능성도 있다.

특히 AI 에이전트로 취약점 분류와 코드 수정을 자동화하는 환경에서는 입력 데이터의 신뢰성이 더욱 중요하다. CVE 등록 여부와 점수만으로 조치를 결정하기보다 공급자의 공식 보안 공지, 수정 커밋, 영향받는 버전 범위와 실제 재현 결과를 함께 확인해야 한다. 국내 기업과 공공기관 역시 규정 준수를 위해 CVE 기반 자동 대응 체계를 운용한다면 신규·미검증 권고문을 별도로 검증하는 절차가 필요하다.

## 확인 범위

GeekNews가 소개한 조사 내용에 따르면 공식 SQLite 릴리스를 Docker 컨테이너에서 빌드하고 AddressSanitizer를 사용해 제시된 PoC를 점검했으며, 대상 소스의 함수·행 번호와 버전 간 변경 내역도 대조했다. 그 결과 조사 대상 6건에서는 주장된 메모리 취약점이 재현되지 않았다.

다만 이 결론은 해당 조사에서 검토한 권고문과 버전에 한정된다. SQLite 전반에 취약점이 없다는 뜻은 아니며, 권고문이 실제로 어떤 생성 도구를 거쳤는지까지 직접 입증한 것으로 볼 수도 없다. 이 사안은 CVE 자체를 무조건 배제해야 한다는 의미보다, 새롭거나 출처가 불분명한 항목은 공식 공급자 정보와 재현 가능한 기술 증거로 교차 검증해야 한다는 사례로 해석하는 것이 적절하다.
