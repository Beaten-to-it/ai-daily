## 무엇이 있었나

구글이 Gemini를 활용해 GIF 처리 라이브러리 ‘giflib’를 C에서 Rust로 재작성한 시범 프로젝트 결과를 공개했다. 약 3,000줄 규모의 기존 코드를 한 번에 옮긴 뒤, C 호출부와 연결되는 FFI 계층의 메모리 관리 문제와 동작 차이를 반복적으로 수정했다. 안전하지 않은 코드는 전문가가 최종 검토했다.

구글은 새 구현이 기존 C 라이브러리를 대체할 수 있도록 ABI 호환성을 유지했다. 검증에는 3,000만 개가 넘는 GIF를 활용한 회귀 테스트와 6일 이상 진행된 2억 회 이상의 차등 퍼징이 동원됐다. 이 과정에서 LZW 디코더의 예외 사례와 구글 내부의 과거 패치에서 비롯된 범위 밖 쓰기 취약점도 발견했다고 밝혔다.

배포가 시작된 뒤 기존 giflib C 구현에서 힙 영역을 벗어나는 쓰기 취약점인 CVE-2026-26740이 보고됐다. 구글 설명에 따르면 이미 Rust 구현으로 전환된 시스템은 이 메모리 손상 문제의 영향을 받지 않았다. 실제 서비스에서는 기존 C 구현과 비교해 성능 저하가 관찰되지 않았고, 일부 서비스는 샌드박스를 제거하면서 이미지 디코딩의 꼬리 지연시간도 줄었다.

구글은 재작성한 코드를 `giflib-rs`라는 이름으로 공개했다.

## 왜 중요한가

이번 사례는 생성형 AI가 보안에 민감한 기존 코드를 빠르게 옮기는 데 활용될 수 있음을 보여준다. 특히 외부 입력을 처리하는 C·C++ 라이브러리를 메모리 안전 언어로 전환하면 개별 취약점을 사후 보완하는 데 그치지 않고, 특정 유형의 결함이 발생할 구조 자체를 줄일 수 있다.

다만 핵심은 코드 생성 속도보다 검증 체계에 있었다. 기존 구현과 결과를 비교하는 대규모 테스트, 장시간 퍼징, FFI 경계에 대한 전문가 검토, 장애 발생 시 되돌릴 수 있는 전략이 함께 필요했다. 오픈소스 의존성이 많은 국내 서비스와 소프트웨어 공급망에도 AI 기반 마이그레이션의 가능성과 도입 조건을 함께 보여주는 사례다.

## 확인 범위

내용은 구글 Bug Hunters가 공개한 프로젝트 설명을 기준으로 확인했다. 테스트 규모, 성능과 보안 효과는 구글의 내부 인프라 및 운영 관측 결과이며, 독립적인 재현 결과는 이 자료에 포함되지 않았다. 또한 대상이 비교적 작고 안정적이며 SIMD나 어셈블리 최적화가 없는 giflib였으므로, 같은 방식이 더 크고 복잡한 C·C++ 프로젝트에서도 동일한 비용과 성과를 낸다고 단정할 수 없다.

구글 역시 실제 데이터나 충분한 기존 테스트가 필요하며, 활발하게 개발되는 상위 프로젝트와 다른 언어의 포크를 유지하는 데 추가 비용이 발생할 수 있다고 설명했다.
