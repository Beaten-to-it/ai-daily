## 무엇이 있었나

AWS가 Amazon SageMaker HyperPod에서 대규모 언어 모델의 KV 캐시를 여러 추론 파드가 공유하도록 구성하는 계층형 아키텍처를 소개했다. GPU 메모리를 L0, 호스트 CPU 메모리를 L1, 여러 노드의 로컬 NVMe를 묶은 Curvine 분산 파일시스템을 L2 캐시로 사용한다. HyperPod의 지능형 라우팅 기능은 요청의 접두어와 캐시 상태를 바탕으로 재사용 가능성이 높은 파드를 선택한다.

AWS가 공개한 시험 배포에서는 약 1,925개 토큰으로 구성된 동일 요청을 서로 다른 노드의 파드에 순서대로 보냈을 때 두 번째 파드가 전체 토큰의 KV 캐시를 재사용했다. 이때 노드 간 L2 읽기에는 약 56ms가 걸렸다. 별도 벤치마크에서는 1,000개 이상 토큰의 일부 프롬프트에서 첫 토큰 생성 시간(TTFT)이 최대 2.7배 개선됐다. 4회 대화를 재생한 시험에서는 전체 처리 시간이 4.21초에서 3.25초로 줄었다.

구현에는 SageMaker HyperPod Inference Operator와 LMCache, Curvine의 FUSE·CSI 구성이 사용됐다. 현재 운영자 CRD가 Curvine 파일시스템을 L2 백엔드로 직접 지정하지 못해 배포 객체의 환경변수와 볼륨 마운트를 별도로 수정해야 한다. AWS는 장기 운영 환경에서는 이 과정을 웹훅이나 정책으로 자동화할 것을 제안했다.

## 왜 중요한가

LLM 추론에서는 긴 시스템 프롬프트나 RAG 문맥, 누적된 대화 기록을 반복해서 처리하는 비용이 크다. 여러 GPU 파드가 각자 캐시를 보유하면 요청이 다른 파드로 이동할 때 같은 내용을 다시 계산해야 한다. 공유 L2 캐시는 이런 중복 계산을 줄여 응답 지연과 GPU 메모리 부담을 낮출 수 있다.

국내 기업이 부서별 AI 서비스나 상담·검색증강생성 시스템을 AWS에서 운영할 때도 공통 프롬프트가 길고 요청 간 중복도가 높다면 활용 가능성이 있다. AWS는 이 구조를 통해 일부 워크로드를 P5보다 비용이 낮은 G6e 인스턴스에서 운영할 수 있다고 설명했다. 다만 실제 절감 폭은 모델 크기, 동시 요청 수, 프롬프트 중복률과 저장장치 구성에 따라 달라진다.

짧은 프롬프트에서는 원격 캐시 조회 비용이 재계산 비용과 비슷할 수 있다. 따라서 모든 요청에 동일한 효과를 기대하기보다 GPU·CPU·공유 NVMe 캐시와 요청 라우팅을 워크로드 특성에 맞게 조정해야 한다.

## 확인 범위

아키텍처 구성과 수치는 AWS가 공개한 기술 게시물 및 해당 시험 환경에서 확인된 결과다. 최대 2.7배 개선은 Qwen2-7B-Instruct와 두 개의 vLLM 복제본을 사용한 특정 벤치마크에서 나온 값으로, 일반적인 성능을 보장하지 않는다. 시험별로 사용한 GPU 인스턴스 조합도 달랐다.

또한 현재 구성에는 운영자 조정 루프가 수동 패치를 덮어쓸 수 있다는 제약이 있다. 실제 도입 전에는 사용 모델과 트래픽을 기준으로 캐시 적중률, TTFT, 장애 복구, 비용을 별도로 검증할 필요가 있다.
