## 무엇이 있었나

Cursor가 대규모 Git 호스팅을 위한 새 저장 시스템 ‘Continuity’를 소개했다. 이 시스템은 개별 Git 복제본이 아니라 S3 호환 객체 저장소의 쓰기 전 로그(WAL)를 최종 데이터 원본으로 삼는다. 로컬 NVMe에 있는 Git 저장소는 필요할 때 WAL로 다시 만들 수 있는 캐시로 취급한다.

푸시는 데이터가 WAL에 영구 저장된 뒤에만 성공한 것으로 처리된다. WAL 인덱스는 원자적 비교 후 교환(CAS)으로 갱신해 여러 푸시의 순서를 정한다. 읽기 복제본은 요청을 처리하기 전에 S3의 최신 상태를 확인하므로, 별도의 저장소별 합의 그룹 없이도 일관된 결과를 제공하도록 설계됐다.

저장소별 복제본 수도 트래픽에 맞춰 조정할 수 있다. 대형 모노레포에는 복제본을 대량 배치하고, 사용 빈도가 낮은 소형 저장소는 로컬 복제본을 하나만 두거나 완전히 제거할 수 있다. Cursor가 공개한 합성 부하 시험에서는 읽기 성능이 복제본 100개까지 선형적으로 증가했으며, 푸시 처리량은 S3 Standard에서 초당 최대 120건, S3 Express One Zone에서 초당 300건 이상으로 보고됐다.

## 왜 중요한가

AI 코딩 에이전트의 확산은 Git 인프라에 상반된 요구를 만든다. 대형 모노레포에서는 코드 생성과 CI 실행 증가로 읽기 부하가 커지는 한편, 작업용 소형 저장소가 짧은 시간 동안 대량 생성될 수 있다. 저장소마다 고정된 수의 복제본을 유지하는 전통적 구조는 전자에는 확장 한계가 있고 후자에는 비용 부담이 크다.

Continuity의 접근법은 데이터 내구성과 로컬 복제본 수를 분리한다. 국내에서 대규모 모노레포나 AI 에이전트 기반 개발 환경을 운영하는 기업에는 저장 용량과 읽기 처리량을 작업 특성에 따라 조절할 수 있다는 점이 의미가 있다. 기존 Git 저장소와 도구를 유지하면서 서버 측 저장 구조를 바꾼다는 점도 도입 장벽을 낮출 가능성이 있다.

## 확인 범위

이 기사는 GeekNews에 정리된 Cursor의 기술 소개 내용을 바탕으로 작성했다. Continuity의 구조, 일관성 보장 방식과 합성 부하 시험 수치는 해당 자료에서 확인했다. 다만 실제 서비스 환경의 장애 복구 시간, 비용 절감 폭, 장기간 운영 안정성 및 다른 Git 호스팅 구조와의 독립적인 성능 비교는 제시된 내용만으로 확인할 수 없다.
