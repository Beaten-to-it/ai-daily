## 무엇이 있었나

AWS는 Amazon Bedrock을 통해 OpenAI 모델을 사용하는 로컬 Codex 환경의 운영 지표를 OpenTelemetry와 Amazon CloudWatch로 수집·분석하는 참조 구성을 소개했다.

이 구성에서는 개발자 PC에서 실행되는 OpenTelemetry 수집기가 Codex의 API 요청 수, 응답 시간, 대화 턴, 토큰 사용량, 도구 호출 등의 지표를 받는다. 수집기는 사용자와 부서, 팀, 비용 센터 같은 조직 정보를 지표에 추가한 뒤 임시 AWS 자격 증명과 SigV4 인증을 이용해 CloudWatch의 지역별 OTLP 엔드포인트로 전송한다.

수집기가 로컬 호스트에서 작동하므로 모델 요청 경로에 중앙 프록시나 별도의 공개 수집 서버를 둘 필요는 없다. AWS가 제시한 참조 배포도 CloudWatch 대시보드를 만들 뿐 ECS 서비스나 로드 밸런서, VPC를 새로 구성하지 않는다.

대시보드에서는 최근 24시간의 활성 사용자, 대화 턴, API 요청, 토큰 사용량을 비롯해 모델·사용자·조직 단위의 이용 현황을 확인할 수 있다. 다만 AWS는 이 지표가 사용 추세와 운영 상태를 파악하기 위한 것이며, 실제 비용 정산에는 AWS Cost and Usage Reports 2.0 등 별도의 청구 자료를 사용해야 한다고 설명했다.

## 왜 중요한가

기업이 코딩 에이전트를 여러 개발 조직으로 확대할 때는 도입 여부뿐 아니라 이용 집중도, 장애 징후, 비용 배분과 개인정보 관리까지 함께 살펴야 한다. 이번 구성은 기존 Codex 사용 흐름을 크게 바꾸지 않으면서도 팀과 부서별 확산 정도, 도구 호출 증가, 요청 지연 같은 운영 신호를 AWS 환경에서 확인할 수 있는 방법을 제시한다.

한국 기업에도 사내 AI 개발 도구를 시범 운영에서 조직 단위로 확대할 때 참고할 만한 사례다. 특히 사용자별 지표는 직원 모니터링이나 개인정보 보호 문제로 이어질 수 있어, 경영진에게는 집계된 조직 단위 정보만 제공하고 개인 단위 대시보드는 승인된 운영·보안·재무 담당자에게 제한하는 방식이 필요하다.

이 방식은 관찰과 알림을 위한 구성이지 강제적인 예산 통제 장치는 아니다. IAM Identity Center가 사용자에게 임시 자격 증명을 직접 발급하므로, 로컬 텔레메트리만으로 토큰 한도를 넘긴 Bedrock 요청을 실시간 차단할 수 없다. 강제 차단이 필요하다면 요청 경로에 별도의 게이트웨이를 두는 설계를 검토해야 한다.

## 확인 범위

AWS ML 블로그에 공개된 아키텍처, 수집 지표, 배포 단계와 운영상 주의사항을 기준으로 확인했다. 구체적인 명령과 템플릿은 AWS가 언급한 공개 가이던스 저장소의 참조 구현을 전제로 한다.

실제 도입 비용은 데이터 수집량, PromQL 쿼리 규모, 리전과 계약 조건에 따라 달라질 수 있다. 또한 조직 속성의 정확성, 접근 권한, 보존 기간, 직원 모니터링 관련 정책은 각 기업이 별도로 검토해야 한다. AWS도 해당 글이 공개 가이던스 저장소를 바탕으로 한 구현 패턴이며, 별도의 공식 보증을 뜻하지는 않는다고 밝혔다.
